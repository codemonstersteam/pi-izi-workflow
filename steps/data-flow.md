# Data flow полосы до шага 9: что во что превращается

Что здесь: путь заказа от `TASK.md` до входа в шаг 9 — по шагу: вход, кто работает, наряд, выход,
гардрейл, цена. Форма — как у `steps/plan/data-flow.md`; шаг 2 разложен подробно в
`steps/brd/data-flow.md`, обоснование его конструкции — в `steps/brd/normalize-concept-research.md`.
Документ описывает полосу ПОСЛЕ переделки шага 2: то, как она должна работать.

Правило, вокруг которого построено всё: **скрипт считает то, что вычислимо, роль решает то, что
вычислить нельзя, гардрейл сверяет объявленное.** Ни одна проверка не решает, как должно быть: она
говорит «ты объявил X, а Y его не знает», и называет обе стороны.

**Обозначения.** 🟢 работает от старого · 🟡 переделано и разобрано с оператором · 🚧 переделка
не закончена · 🤖 роль писала машина · ✍️ роль вычитана оператором.

## 🟡 2 brd — заказ становится якорями

Четыре хода внутри одного шага; подробности и цифры — `steps/brd/data-flow.md`.

```
2A normalize  TASK.md → .agent/normalized.md          роль, наряд steps/brd/normalize/order.normalize.tpl
              строка на требование: verb | object | instrument | values
2B hits       таблица → слово · files · weight         скрипт, 0,56 с
2C gate       таблица + попадания → .agent/brd.md      роль, наряд steps/brd/gate/order.gate.tpl
              verdict · R1..Rn · analogue · subjects[]
2D spread     якоря и аналог → .agent/anchors.json     скрипт, 0,56 с
              файлы, пакеты, плотность; отдельно файлы аналога
```

Роль решает здесь ровно два вопроса: **что здесь аналог** и **решаема ли задача в этом
репозитории**. Всё остальное — арифметика по дереву файлов.

Гардрейл: вердикт из трёх · R-строка не пересказ заказа · созданная сущность в якорях · `analogue`
с ненулевым счётом · селективность каждого якоря в коридоре (доля помеченных файлов).

Три артефакта уезжают дальше, и каждый — свой потребитель: `subjects[]` и `anchors.json` в шаг 3,
`analogue` и файлы аналога в 3б, `normalized.md` в шаг 6, `R1..Rn` в шаг 11.

## 🟢 3 survey-plan — дерево файлов в клетки

```
вход     дерево проекта по границе steps/survey-plan/skip.mjs · subjects[] · anchors.json
скрипт   newPlan: клетка = подкаталог, потолки CELL_FILES 20 / CELL_BYTES 200 КБ;
         id клетки выводится из ПУТИ, поэтому добавленный файл двигает ровно одну клетку
         и кэш .izi/parts переживает правку
роль     нет
выход    .agent/survey-plan.json — клетки, помеченные якорями, gaps, cells
гардрейл клетка не превышает потолков; каждый якорь несёт found=yes|no
цена     0 токенов
```

Плотность из `anchors.json` решает форму клетки: клетка, где помечено больше половины файлов, — дом
предмета и идёт рою целиком; клетка с одним попаданием из двадцати отдаётся одним файлом,
микро-клеткой со своим id. Без этого 62 помеченных файла тянут за собой 256 — разбавление ×2,2.

## 🟢 4 scope — клетка становится частью карты

```
вход     focus.json · клетки
рой      до 8 ролей scout ✍️ одновременно; ширина — литерал workflows/izi.js
наряды   steps/scope/order.survey.tpl (обычная клетка) · order.spine.tpl (хребет)

```

Кэш `scope/cache.mjs`: клетка, чьи файлы не менялись, не перечитывается — id клетки от пути,
поэтому правка одного файла стоит одну клетку, а не весь обзор.

## 🟢 5 graph — части в одну карту

```
вход     graph-parts/*.xml · факты скрипта (рёбра, сьюты, хребет)
скрипт   mergeGraph — слияние независимо от порядка частей
роль     нет
выход    .agent/appgraph.xml
гардрейл judgeGraph: каждый якорь плана несёт found; узлы без пути и висячие рёбра названы
цена     0 токенов
```

**Единственное место полосы, где машина ловит выдуманный якорь:** слово, которого нет в коде,
приходит сюда как `found="no"`. Пропущенный якорь не ловится здесь ничем — его ловит селективность
на шаге 2.

## 🟢 6 intake — требование, обжаренное о карту

```
вход     appgraph.xml · .agent/brd.md · .agent/normalized.md · .agent/answers.md
роль     intake ✍️, четыре пласта — по наряду на пласт (order-a · b · c · d)
выход    .agent/frd.xml — use case с концами, поля, отказы, дельты, touched
гардрейл frd.mjs::checkFrd — тотален, возвращает ВСЕ блокеры сразу: состав, происхождение значений,
         узлы против карты, потраченные ответы оператора
цена     до intakeLoops кругов починки
```

Три документа на входе, а не один. Значение цитируется из `normalized.md`, колонка `values`:
`as {id}.glossary.json plus {id}.descriptor.json` становится `fit:` требования, а не вопросом
оператору о том, что он уже решил. `verb` + `object` дают use case, `instrument` — `touched`.

## 🟢 7 weight — вес изменения

```
вход     frd.xml
скрипт   newMode: MODE_TABLE — Added→minor · Changed→major · Removed→major · Fixed→patch;
         свёртка коммутативна, порядок дельт на вес не влияет
выход    .agent/mode
гардрейл Unknown — не вес, а отказ: полоса не идёт дальше «не смог классифицировать»
цена     0 токенов
```

Вес считается по ФОРМАМ дельт, а не по прозе: что изменение делает с существующим вызовом — решено
ролью на шаге 6, здесь только складывается.

## 🟢 8 ripple — что задето

скрипт   changeWidth — набор узлов работы; объявления, API, соседи
выход    .agent/ripple.xml

Набор узлов, посчитанный здесь, — тот же, по которому шаг 10 режет билеты: выражение объявлено один
раз и импортируется, а не переписывается.
