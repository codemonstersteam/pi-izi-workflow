# Шаг 9 — как работает алгоритм, фаза за фазой

Операционный контракт шага: что приходит на вход каждой фазы, что она обязана отдать и кто её
исполняет. Формулировки здесь НЕ ЗАВИСЯТ ОТ ПРОЕКТА: по ним пишется код, который работает на любом
репозитории. Замеры на живых формах, имена классов и цены прогонов — в `docs/design.md`.

**Единица плана — МОДУЛЬ (класс).** Use case — не владелец плана, а строка раздела
`закрывает: UC1 шаг 1`. Отсюда главное свойство: модуль лежит ровно в одной партии, один вызов роли
решает его один раз, и дубль невозможен по построению.

Роль участвует ровно в ОДНОЙ фазе из девяти — ④. Всё остальное считает скрипт за 0 токенов.

---

## ① Дерево модулей — скрипт

| | |
|---|---|
| **вход** | `.agent/frd.xml`, `.agent/ripple.xml` |
| **задача** | собрать состав изменения и то, что репозиторий знает о его модулях |
| **выход** | `modules[] = { path, ucs[], new: bool, deps[], level }` |
| **исполнитель** | скрипт, 0 токенов |

Состав берётся из FRD: пути стоят в `<scenario nodes>`. Рябь ОБОГАЩАЕТ найденное — `deps` и `level`
у тех модулей, которые уже существуют.

**Почему не наоборот.** Рябь — проекция карты, а карта построена ДО изменения: создаваемого модуля
в ней нет и быть не может. Состав, взятый из ряби, теряет ровно те модули, которых ещё нет, — а в
изменении, заводящем новые файлы, это может быть большая его часть.


**Отказ:** ни одного узла в сценариях FRD — планировать нечего, это дефект шага 6, а не шага 9.

---

## ② Партии — скрипт

| | |
|---|---|
| **вход** | `modules[]` |
| **задача** | разложить модули по пакету так, чтобы каждый попал ровно в одну партию |
| **выход** | `partitions[] = { slug, modules[], ucs[], neighbours[] }` |
| **исполнитель** | скрипт, 0 токенов |

Ключ партии — каталог пакета без хвоста `impl|mongo|rest|model`. Иначе `backup/IResourceSource.java`
и `backup/impl/ZipResourceSource.java` уедут в разные вызовы и разойдутся в решении.

`neighbours` — `<dep>` модулей партии из ряби, минус сами модули партии.

**Инвариант, проверяемый машиной:** Σ модулей партий = |modules|, пересечений нет. **Это и есть
доказательство невозможности дубля** — не гейт, не сведение, а свойство разбиения.

Партия вырождается там, где изменение маленькое: один модуль — одна партия, один вызов роли.


---

## ③ Карточка партии — скрипт

| | |
|---|---|
| **вход** | партия + `frd.xml` + `appgraph.xml` + `ripple.xml` + `design-graph.xml` |
| **задача** | срезать проекции: всё, что нужно ОДНОМУ вызову, и ничего больше |
| **выход** | `.agent/staging/parts/<slug>.txt` |
| **исполнитель** | скрипт, 0 токенов |

```
$START_MODULES    — <module> партии из карты; у создаваемых пусто, и это написано словами
$START_USECASES   — use case этих модулей ДОСЛОВНО: шаги, ветки отказа, дельты, поля
$START_NEIGHBOURS — <dep> партии из ряби, ПУТЯМИ: читай сам, правь минимально
$START_SAMPLE     — путь файла того же вида в репозитории (лестница, docs/design.md §3)
$START_CHECK      — команда сьюта и шаблон имени тест-класса
$START_DRAFT      — <module> партии из design-graph.xml, черновик прохода 9B
```

Каждая секция — ВЫРЕЗКА, не пересказ: байты те же, что на диске.

Карточка партии на порядок меньше, чем карта и FRD вместе: роль читает свой вопрос, а не репозиторий.


---

## ④ План партии — РОЛЬ, единственный вызов шага

| | |
|---|---|
| **вход** | карточка партии |
| **задача** | на КАЖДЫЙ модуль партии написать, как он меняется |
| **выход** | `.agent/staging/parts/<slug>.md` — 1-5 разделов |
| **исполнитель** | роль `core-designer`, `qwen3.6-27b`, `thinking: low`, права `read`+`write` |

```
## <путь модуля>  (новый | правится)
что это: одна фраза
поля: <имя>: <тип> — <зачем>          (класс данных; иначе «нет собственных»)
сигнатуры: <имя>(<параметры>) : <тип>
зовёт: <путь> — зачем                 (либо «нет»; строка ОБЯЗАТЕЛЬНА — из неё порядок работ)
по образцу: <путь> — что повторяем
закрывает: UC1 шаг 1 · UC4 шаг 2а
проверка: <команда> · <имя тест-класса>
```

**Что требуется от роли, и почему это ей по силам:** одно решение на вызов. Что менять, что общее и
где искать образец — решено скриптом до неё; ей остаётся написать, как меняется каждый модуль партии.
Живые замеры выполнимости — `docs/design.md`.

## ⑤ Гардрейл партии — скрипт

| | |
|---|---|
| **вход** | staging-файл + партия |
| **задача** | судить СТРУКТУРУ, не смысл |
| **выход** | блокеры построчно (пусто = зелено) → промоут в `docs/design/<slug>.md` |
| **исполнитель** | скрипт, 0 токенов |

| # | правило | какую ошибку роли ловит |
|---|---|---|
| 1 | раздел на каждый модуль партии | забыла модуль |
| 2 | ни одного модуля чужой партии | написала раздел по образцу или по соседу вместо модуля |
| 3 | каждый use case партии назван в «закрывает» | не показала, чем требование закрыто |
| 4 | у каждого раздела есть «проверка» И «зовёт» | тикет нечем закрыть; порядок работ не из чего строить |
| 5 | каждый путь в «зовёт» резолвится в модуль, соседа или файл карты | «зовёт» прозой — адрес не отличить от рассуждения |
| 6 | шаг закрывает тот, кто ВИДИТ его: текст шага называет модуль — значит закрыватель его зовёт | наряд, который исполнителю нечем проверить: живой прогон закрыл шаг требования `assertTrue(true)` |

Красный → блокеры едут роли в `FEEDBACK`, бюджет `LOOPS`. Зелёный → промоут.

Смысл не судится: «правильный ли это дизайн» читает человек на гейте.

## ⑥ Полнота — скрипт, после всех партий

| | |
|---|---|
| **вход** | все `docs/design/<slug>.md` + `frd.xml` |
| **задача** | убедиться, что требование покрыто целиком |
| **выход** | отказ с именами либо зелёный |
| **исполнитель** | скрипт, 0 токенов |

- каждый модуль изменения имеет раздел;
- каждый use case FRD назван хотя бы в одном «закрывает»;
- каждый шаг use case и каждая ветка отказа закрыты хотя бы одним разделом.

**Почему это вычислимо:** обе стороны нумерованы. FRD несёт `<step n="1">` и `<ext id="2a">`, роль
пишет `закрывает: UC1 шаг 1 · UC4 шаг 2а` — сравниваются два множества номеров.

Сегодня такой проверки в конвейере нет вовсе.

## ⑦ Порядок — скрипт

| | |
|---|---|
| **вход** | разделы всех партий + рёбра карты |
| **задача** | построить очередь работ |
| **выход** | топологический порядок модулей либо отказ с именами |
| **исполнитель** | скрипт, 0 токенов |

Рёбра — из ОБЪЯВЛЕННЫХ строк «зовёт:»: их писал тот, кто решал модуль. Из потока очередь не
выводится (D42: на классе данных стрелки потока и очереди противоположны). Для существующих модулей
добавляются рёбра карты — статику знает она.

Круг → отказ, и его чинит роль: строки писала она, значит есть что чинить.

**Почему правило 4 обязательно.** Роль пишет «зовёт» редко и часто прозой, если её не заставить: без
обязательности строки очередь работ выходит плоской, и тикеты режутся без зависимостей.
