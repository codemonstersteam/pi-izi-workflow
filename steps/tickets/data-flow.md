# Шаг 14 — как работает алгоритм, фаза за фазой

Операционный контракт шага: что приходит на вход каждой фазы, что она обязана отдать и кто её
исполняет. Формулировки здесь НЕ ЗАВИСЯТ ОТ ПРОЕКТА: по ним пишется код, который работает на любом
репозитории — команда проверки, имена модулей, язык и стиль приходят из артефактов, а не из этого
файла. Место шага в полосе — `docs/workflow.md` §3.14; замеры на живых формах — `docs/design.md`.

**Задача шага: нарезать план на тикеты для СЛАБОЙ модели** — так, чтобы шаг 15 раздавал их
механически, не читая тело, и запускал параллельно всё, что параллелится.

**Роли на шаге нет. Ноль токенов.** Все решения приняты раньше: что менять — шаг 6, как менять —
фаза ④ шага 9, в каком порядке — фаза ⑦, можно ли вообще — гейт 1. Здесь только раскладка.

**Тикетов два рода, и порядок между ними жёсткий: ТЕСТ раньше МОДУЛЯ.** Тест пишется по контракту
из плана, модуль — по тому же контракту, и модульный тикет не имеет права править тестовый файл.
Так подгонка теста под реализацию становится не вопросом добросовестности, а недоступным действием.

Приём взят из `implementation-ticket-writer` (внешний навык): машинный заголовок, минимальный
контекст, `blocked_by` как ребро графа, RED-first. Не взято то, что относится к гринфилду —
`scaffold`, `component-RED` на весь срез, `wiring`, `README`: полоса правит СУЩЕСТВУЮЩИЙ репозиторий.

## ① Разбор плана — скрипт

| | |
|---|---|
| **вход** | `task/<КЛЮЧ>/design/<партия>.md` — разделы, промоученные фазой ⑤ |
| **задача** | взять разделы такими, как их написала роль |
| **выход** | `Section[] = { path, body, calls, checks, closes }` |
| **исполнитель** | скрипт, 0 токенов — `steps/design/card.mjs::sectionsOf` |

Тот же разбор, которым судит гардрейл партии и собирает `PLAN.md` фаза ⑧. Второй разбор того же
текста — это тикет, нарезанный не из того плана, который утвердил оператор.

**Отказ:** ни одного раздела — резать нечего, шаг 9 не отработал.

## ② Владелец шага — скрипт

| | |
|---|---|
| **вход** | `Section[]` + очередь работ фазы ⑦ |
| **задача** | решить, КТО отвечает за каждый шаг use case |
| **выход** | `Map<шаг, модуль>` — ровно один владелец на шаг |
| **исполнитель** | скрипт, 0 токенов |

Один шаг требования проходит через несколько модулей, и все они честно называют его в «закрывает».
Если завести тест каждому, одно требование проверят трижды; если не завести никому — не проверят
вовсе. Владелец определяется по ГРАФУ, объявленному самой ролью:

```
1. закрыватель, которого ЗОВЁТ другой закрыватель того же шага (транзитивно), выбывает
   — его поведение наблюдается через зовущего
2. среди оставшихся владелец — ПОСЛЕДНИЙ в очереди работ
```

**Ни слова о видах модулей.** Правило не спрашивает, интерфейс это, класс данных или сервис: где-то
инженеры пишут интерфейсы, где-то нет, и распознавание вида по имени или по прозе — подгонка под
один проект. Модуль отпадает не потому, что «POJO», а потому что его зовёт другой закрыватель.

**Следствие:** модуль, за которым не осталось ни одного шага, тестового тикета не получает. Его
готовность — «собирается и используется тестом того, кто его зовёт».

**Отказ:** шаг, у которого после отсева не осталось владельца, — круг в объявлениях; его уже отверг
бы гардрейл фазы ⑦, и здесь это расхождение артефактов.

## ③ Тестовые тикеты — скрипт

| | |
|---|---|
| **вход** | владельцы шагов + `.agent/frd.xml` |
| **задача** | нарезать проверки так, чтобы каждая была подъёмна слабой модели |
| **выход** | `task/<КЛЮЧ>/tickets/<NN>-test-<модуль>-<UC>.md` |
| **исполнитель** | скрипт, 0 токенов |

**Единица тестового тикета — пара «модуль × use case»**, а не модуль. Модуль, закрывающий двадцать
шагов восьми use case, дал бы один неподъёмный тикет; разрезанный по use case — восемь тикетов по
две-четыре проверки.

Содержание проверок берётся из FRD и ниоткуда больше:

| источник | что даёт |
|---|---|
| `<step n>` шага, которым владеет модуль | happy-путь: что подано, что получено |
| `<ext id>` ветки того же use case | ветка отказа |
| `<failure code status client>` | код и текст отказа |
| `<field name type domain required>` | границы значений |
| строка «сигнатуры» раздела | имена, которые тест обязан звать |

Формула та же, что у всего репозитория (`standards/code.md`): **1 happy + Σ ветвей**.

## ④ Модульные тикеты — скрипт

| | |
|---|---|
| **вход** | раздел + его тестовые тикеты + очередь работ |
| **задача** | наряд на реализацию по тому же контракту |
| **выход** | `task/<КЛЮЧ>/tickets/<NN>-<модуль>.md` |
| **исполнитель** | скрипт, 0 токенов |

```yaml
---
id: <NN>
key: <КЛЮЧ ЗАДАЧИ>
branch: <имя ветки шага 13>
kind: module                      # module | test
wave: <номер волны>
blocked_by: [<id тестов этого модуля>, <id зовомых модулей>]
inputs:  [<путь образца>, <пути зовомых модулей>, <пути тестов>]
outputs: [<путь модуля>]
verify: <команда сьюта из строки «проверка»>
---
```

Тело — три секции, и каждая ВЫРЕЗКА, а не пересказ:

```
## Что делаем
<раздел плана ДОСЛОВНО: что это · поля · сигнатуры · зовёт · по образцу>

## Зачем — шаги, которые это закрывает
<UC> шаг <n>: <текст шага из FRD, дословно>

## Как проверить
<команда сьюта> · <имя тест-класса>
```

**Тестовый файл НЕ входит в `outputs` модульного тикета.** Исполнитель может привести модуль к тесту
и не может привести тест к модулю: это и есть соблюдение контракта, снятое с доброй воли.

**Модуль закрывается СВОИМИ тестами, а не именем из строки «проверка».** Роль называет один класс, а
тесты разрезаны по use case — класса с исходным именем никто не создаёт. Подстановка идёт в тот же
флаг, которым команду параметризовала разведка. Модуль, за которым не осталось ни одного шага,
закрывается сьютом целиком: «собирается и не ломает существующее».

## ⑤ Волны — скрипт

| | |
|---|---|
| **вход** | тикеты и их `blocked_by` |
| **задача** | сказать шагу 15, что можно делать одновременно |
| **выход** | `wave` у каждого тикета |

```
wave = 1 + max(wave того, кого ждём)
```

Тест своего модуля всегда на волну раньше него: модуль ждёт свой тест. Тикеты одной волны не связаны
ни прямо, ни транзитивно — шаг 15 поднимает их разом.

Изменение из N модулей укладывается в столько волн, какова длина самой длинной цепочки «зовёт», —
обычно это единицы, а не N.

## ⑥ Гардрейл — скрипт

| | |
|---|---|
| **вход** | тикеты + разделы + шаги требования |
| **задача** | судить раскладку, а не смысл |
| **выход** | блокеры (пусто = зелено) |

| # | правило | что ловит |
|---|---|---|
| 1 | модульный тикет на каждый раздел плана, и ни одного лишнего | работу, которую никто не исполнит |
| 2 | каждый шаг требования принадлежит ровно одному тестовому тикету | требование, проверенное дважды или ни разу |
| 3 | `outputs` непуст, и ни один путь не назван в двух тикетах | двух исполнителей на одном файле |
| 4 | `verify` непуст | тикет, который нечем закрыть |
| 5 | модульный тикет ждёт свои тесты; тестовый файл не в его `outputs` | подгонку теста под реализацию |
| 6 | каждый `blocked_by` резолвится, циклов нет | наряд, который никогда не станет готовым |

Смысл не судится: «правильно ли решён модуль» прочитал человек на гейте 1.

## ⑦ Что получает шаг 15

```
task/<КЛЮЧ>/tickets/
  01-test-<модуль>-<UC>.md   wave 0 ─┐
  02-test-<модуль>-<UC>.md   wave 0  ├─ тесты поднимаются разом
  03-test-<модуль>-<UC>.md   wave 0 ─┘
  04-<модуль>.md             wave 1 ─┐  модуль ждёт СВОИ тесты
  05-<модуль>.md             wave 1 ─┘
  06-<модуль>.md             wave 2     ждёт волну 1
```

Шаг 15 читает только заголовки: `wave` решает, что запускать разом, `blocked_by` — чего ждать,
`outputs` — что должно появиться, `verify` — чем закрыть. Тело читает исполнитель, не оркестратор.

**Две проверки, которые делают контракт исполнимым, а не декларативным:**

```
после тестового тикета   verify обязан быть КРАСНЫМ   ← зелёный значит, что тест ничего не проверяет
после модульного тикета  verify обязан стать ЗЕЛЁНЫМ  ← и тестовый файл при этом не изменён
```

Первая ловит пустой тест и тест «мимо» кода; вторая — незаконченную реализацию. Расхождение сигнатур
ловит компилятор языка, если он типизированный, и красный тест, если нет.

**Отказ шага 14 терминальный.** Роли нет — чинить некому: расхождение тикетов с планом означает, что
разошлись артефакты, и это разбирает человек.
