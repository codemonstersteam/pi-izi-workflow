# RTM — матрица трассируемости: концепция и целесообразность для solo

Источники: исследование и код ветки `step9-rework` (`steps/intake/rtm.mjs`, тикет 66
`redesign-backlog.md`, `steps/intake/docs/data-flow.md`, тикеты T76–T79), отчёты живых
прогонов `component-tests/quarkus-rest-json-app-v2-t1-3-27-08-test-plan.md` и PLAN.md
(solo v5) той же ветки, диагностика четырёх прогонов runbox (см. §4). Модели в отчётах и
настройках pi фигурируют как `qwen3.8-max` (сильная, планирование напрямую в чате) и
`qwen3.8-27b` (дешёвая, роли воркфлоу) — далее просто **max** и **27b**.

## 1. Концепция

**Requirements Traceability Matrix** — таблица «требование × модуль», каждая строка которой
связывает одно требование со всеми сущностями, которые его несут. Классика (IEEE 29148,
DO-178C): полнота трассировки **двусторонняя** —

- **FORWARD (ничего не упущено):** каждое требование имеет носителя — модуль, строку плана,
  тест. Требование без носителя будет потеряно при исполнении.
- **BACKWARD (ничего не выдумано):** каждый модуль изменения имеет требование-обоснование.
  Модуль без требования — либо мёртвый код, либо самовольное расширение масштаба.

Грамматия, реализованная в `steps/intake/rtm.mjs` (intake v2, тикет 66) — одна строка на
требование, размерности дописываются слоями конвейера:

```
R3 | scenarios: UC9 | owners: path/A.java, new/B.java(new, after=path/C.java) | contracts: …
```

Суд матрицы (`rtmJudge`) — чистая функция, два направления:

**FORWARD** — требование без `owners` и без `question` → блокер «требование никто не понесёт».
Два класса исключений, купленных живыми тупиками:

- *строки-свойства* (глаголы define/set/name/constrain) — «имя ключа», «формат» — ни один
  шаг UC не может их «нести», требовать владельца = требовать невозможного (живой круг 26.08
  на R15);
- *строки-ограничения* («не ломать существующее») — не действие, а гарантия; правильный
  носитель для них — нфр-строка: `carried req="R3" by="nfr:backward-compatibility"`
  (тикет T78, закрывший тупик 44 красных кругов / 269k токенов на FRUIT-1).

**BACKWARD** — четыре суда, каждый посажен на живой корень дефекта eddi-прогона (DOS-535):

| суд | правило | живой корень |
|---|---|---|
| b1 «зеркало слоя» | new-модуль по образцу P отзеркалирует ВСЕ каталоги пакета P (model/, mongo/, rest/, интерфейсы в корне) | недособранная квинтета: RestPromptSnippetStore создан, GlossaryConfiguration/IGlossaryStore/IRestGlossaryStore — нет |
| b2 «проводник» | new-сервису нужен со-владелец-звонящий из ДРУГОГО пакета | GlossaryService создан, MemoryItemConverter не назначен — подстановка мёртвым кодом, 5/7 функций |
| b3 «кластер» | существующий владелец из ядра чертежа едет вместе с соседями ядра (дедуп по файлу) | StructuralMatcher блокировал одно требование через 4 владельцев = 4 блокера вместо 1 |
| b4 «ответ назвал» | узел карты, названный в ответах оператора, обязан быть владельцем | ответ оператора назвал модуль, артефакт его «не услышал» |

## 2. Место RTM между BRD и FRD

Конвейер step9-rework (полный путь):

```
TASK.md
  → brd (нормализация: verb|object|instrument|values → R-строки, строки-ограничения — T79)
  → карта репозитория (graph, вычислимая скриптом)
  → intake: BRD × карта → FRD (six пластов: scenarios → owners → contracts → data-failures → coverage → critic)
  → RTM — ХРЕБЕТ intake: строки R × размерности (scenarios/owners/contracts)
  → F11: <carried> строк == строк OWED (разность R-id списков)
  → weight/ripple/tree … → PLAN
```

BRD отвечает «что заказано и чем это измеряется», FRD — «какими прецедентами, владельцами
и дельтами это живёт в коде». RTM — не третий артефакт рядом, а **проставка, по которой
судится соответствие**: R-строки берутся из BRD, колонки (узлы, дельты) — из FRD и карты.
Двусторонний суд матрицы заменяет «надежду на модель»: forward ловит потерянные требования,
backward — выдуманные и недособранные модули.

В solo (текущий `main`) роль BRD играет §1 ТРЕБОВАНИЯ плана (цитаты TASK → где закрыто),
роль FRD — §2 ИЗМЕНЕНИЯ + §3 СЦЕНАРИИ. То есть **зачаток RTM в PLAN.md уже есть** — это
колонка «Где закрыто» раздела 1 и колонка «Какое требование закрывает» раздела 2. Чего нет —
суда этой матрицы в обе стороны.

## 3. RTM на примере наших тестовых задач

**FRUIT-1 / SOLO-2 / ROP-1** (один и тот же текст заказа: «UI тянет весь список фруктов,
чтобы найти один. Нужен поиск по части имени, с ограничением на размер ответа. Существующие
вызовы ломать нельзя»). Матрица минимальна:

```
R1 «UI тянет весь список…»      | owners: fruits.html (Ф3) ИЛИ вопрос оператору
R2 «поиск по части имени»       | owners: FruitResource.java (Ф1), FruitResourceTest.java (Ф2)
R3 «ограничение размера ответа» | owners: FruitResource.java (Ф1: limit, DEFAULT_LIMIT)
R4 «не ломать нельзя»           | carried by="nfr:backward-compatibility" → §5 ГАРАНТИИ
```

Прогон `izi fast-трек` 27.08 прошёл именно эту матрицу: R1/R2 → FruitResource, одна дельта
`GET /fruits/search` Added, R3 закрыт UC2 + nfr + сценарием сосуществования. Знаменитый
тупик того же дня (44 круга) — forward-суд, требовавший владельца для строки-ограничения,
пока T78 не ввёл класс carried-by-nfr: концепция без классов исключений не живёт.

**EDDI DOS-535 (glossary)** — большой конец. R-строки порядка десяти, владельцев — 12+:
квинтета (модель/интерфейс/REST/хранение/сервис) + проводник MemoryItemConverter +
синк-кластер. Именно здесь работали backward-суды: b1 добрал три недособранных элемента
квинтеты, b2 назначил проводника (без него GlossaryService — мёртвый код). На 27b-классе
задач это не теория: модель-класс без владельца и конвертер без проводки — фактические
дефекты живого артефакта, механика старого intake их не видела.

## 4. Четыре прогона runbox: где RTM помог бы, а где нет

### 4.1 `quarkus-rest-json-app-v2-t1-3-27-08-test-plan-pi` — max, план напрямую в pi

26k токенов, 3,5 мин, чек-лист шести разделов 6/6, шесть открытых вопросов. Фактически max
выполнил forward-трассировку сам: дефолт limit, регистрозависимость, поведение при кривом
limit — всё стало вопросами, а не молчаливыми допущениями (izi-артефакт того же дня молча
взял `limit required="no"` без дефолта и без вопроса). **Вывод: сильной модели на малом
репо RTM-промпт не нужен — артефакт-спека уже извлекает трассировку. RTM нужен судом**
(дешёвый скрипт подтвердил бы 6/6, а на 27b — поймал бы потери).

### 4.2 `eddi-pi` — max, план (166k, 15 мин, Ф1–Ф29) и разработка по PLAN-exec.md (~450k)

29 строк Ф ↔ 29 коммитов, 12957 тестов зелёные, О1–О12 решены в коммитах. Судья (a)
«строка Ф ↔ коммит» прошёл бы в ноль. Но **никто машинно не проверял**: каждый ли сценарий
§3 получил тест (сценарий→тест 1:1 — только конвенция в наряде), каждая ли величина §4
дошла до кода, каждая ли гарантия §5 осталась аддитивной (судья (c) появился в проекте
после этого прогона). Это ровно forward-колонки RTM, продлённые до коммитов и тестов.
Backward-класс (b1/b2) здесь же родился: дефекты «модель без владельца» и «сервис без
проводника» взяты из eddi-артефактов живьём.

### 4.3 `quarkus-rop-test` — 27b, полный solo (28.08)

Прогон успешен: план → критик APPROVE → 5 вопросов → сверка с решениями → подтверждение →
Ф1/Ф2 от базлайна, 7/7 тестов, судьи зелёные. Но **вопрос про UI исчез**: в §1 строка
Т1 «UI тянет весь список» заявлена закрытой через Ф1+С1, при этом `fruits.html` не меняется
(§5.6 «файл не меняется») — требование «закрыто» созданием возможности, которой UI не
пользуется. Это классический forward-дефект матрицы: **Т без честного носителя** — ни
Ф-строки на UI, ни вопроса оператору. Сравните 4.4.

### 4.4 `quarkus-solo-op` — 27b, solo под оператором (27.08)

Тот же заказ — и вопрос прозвучал: В4 «Входит ли в эту итерацию правка `fruits.html`
(строка Ф3), или достаточно бэкенд-эндпоинта?». Оператор включил Ф3 — план закрыл R1
по-настоящему, коммит Ф3 существует. Разница между 4.3 и 4.4 — не модель и не промпт-спека
(они идентичны), а вариативность 27b: один прогон задаёт вопрос, другой молча трактует.
**Именно эту вариативность гасит вычислимый forward-суд**: «строка Т закрыта Ф-строкой или
вопросом, иначе красный» — правило, которое не зависит от настроения прогона.

Дефекты механики того прогона (сверка затирала РЕШЕНО, починка без FEEDBACK, пустой ответ
как отказ) — к RTM не относятся, но гвард РЕШЕНО (счёт «5 ответов = 5 меток до и после
сверки») — тот же класс мышления: инвариант-счётчик на срезе матрицы.

### Сводка по целесообразности

| применение RTM | max, малое репо | 27b, малое репо | 27b, большое репо (eddi-класс) |
|---|---|---|---|
| промпт-инструкция для планировщика | не нужен (извлекает сам) | подстраховка | нужен: §1↔§2 + carried-by-nfr |
| скрипт-судья §1↔§2 (forward) | дёшев, подтверждает | **ловит потерю Т — главная ценность** | обязателен |
| критик backward (b1/b2/b3) | избыточен | избыточен | нужен (мёртвый код, квинтеты) |
| судья верификации Т↔коммит↔тест | подтверждает | **закрывает «забыл сделать чётко по плану»** | обязателен |
| отдельный артефакт rtm.md в проекте | нет (цена) | нет | да (хребет intake) |

## 5. Ответ на вопрос 1: базовый промпт создания плана

**Да, но не как новый артефакт, а как правила закрытия внутри существующей спеки плюс судья.**

Артефакт-спека уже порождает матрицу (§1 ↔ §2). В `ext/spec/PROMPT.default.md` не хватает
трёх правил, каждое закрыто живым дефектом:

1. **Правило носителя (закрытие Т).** Каждый пункт §1 закрывается ТОЛЬКО строкой Ф раздела 2
   ИЛИ вопросом раздела 6. Ссылка «закрыто сценарием §3» без Ф-строки запрещена: сценарий
   описывает поведение, которое кто-то должен создать. Корень: Т1 в rop-test. Если
   требование описывает поведение файла, которого план не меняет, — это вопрос оператору,
   а не закрытие.
2. **Класс строки-ограничения (carried-by-nfr).** «Нельзя», «не ломать», «по образцу»
   закрываются поимённой строкой §5 ГАРАНТИИ с пометкой `nfr` в колонке закрытия §1 —
   у ограничения нет и не должно быть Ф-строки. Корень: тупик 44 кругов (T78).
3. **Двух-фильтровый триаж вопросов** (урок intake, стоит перенести в §6): (а) может ли
   код/карта ответить? — ответь сам, это не вопрос; (б) есть защитимый дефолт? — прими и
   запиши в допущения одной строкой `assumption | default | rationale`; вопросом становится
   только то, что пережило оба фильтра — решение владельца (trade-off, необратимость).
   Это и дешевле (меньше вопросов оператору), и честнее молчания.

Что НЕ переносить в промпт: обратные суды b1–b4 — они требуют карты репозитория, которой в
solo нет (планировщик читает репо глазами, карта не строится). Для eddi-класса их место —
чек-лист критика, не промпт планировщика: планировщик не должен думать слоями зеркал,
критик — должен проверить.

## 6. Ответ на вопрос 2: верификация сделанной работы

**Да — это сильнейшее применение: RTM продлевает судью (a) до полного замыкания петель.**

Сейчас судьи solve-станции проверяют: (a) Ф↔коммит, (b) тесты не переписаны, (c) гарантии
аддитивны. RTM-ракурс добавляет три вычислимые петли (все — разбор уже существующих
таблиц плана + git, ни одного нового артефакта):

1. **Т ↔ коммит (транзитивное замыкание §1→§2→git).** Каждая строка Т из §1 обязана дотянуться
   хотя бы до одного коммита через свои Ф-строки. Т без единого коммита = «машина забыла
   часть работы» — именно то, от чего вопрос сформулирован. На rop-test петля зелёная
   (Т2/Т3/Т4 через Ф1/Ф2); Т1 она бы не спасла (Ф1 существует) — поэтому нужна петля 2.
2. **Сценарий ↔ тест.** Каждый сценарий §3 с новым поведением — имя теста в коммитах или в
   диффе (сценарий→тест 1:1). На eddi-pi это единственная машина-проверка, которой не было:
   29 коммитов есть, а проверка «каждый сценарий получил тест» осталась на совести модели.
   Судья мягкий: сценарий без теста — блокер; тест без сценария — только заметка оператору
   (бывает законный рефакторинг-тест).
3. **Величина ↔ код.** Судья §4 уже требует источник при планировании; на solve зеркально:
   каждое число из §4 встречается в диффе (константа, ассерт) — иначе величина «испарилась».
   Дёшево: grep по диффу.

Отдельно — **инвариант РЕШЕНО** (уже живёт в сверке): число меток «→ РЕШЕНО» до и после
сверки равно; каждый РЕШЕНО-вопрос фигурирует в §2. Это тот же двусторонний счёт, что и
F11 в intake, — класс RTM-мышления уже принят, осталось распространить.

## 7. Конкретные правки промптов (черновики)

### `ext/spec/PROMPT.default.md` — раздел 1, после первого абзаца

```
Каждая строка Т закрывается ТОЛЬКО ссылкой на Ф-строку раздела 2 ИЛИ вопросом раздела 6.
Ссылка на один §3 без Ф-строки — не закрытие: сценарий описывает то, что кто-то должен
создать. Строки-ограничения («нельзя», «не ломать», «по образцу») закрываются поимённой
строкой раздела 5 с пометкой (nfr) — у ограничения нет Ф-строки. Если пункт описывает
поведение файла, который план не меняет, — это вопрос оператору, а не закрытие.
```

### `ext/spec/PROMPT.default.md` — раздел 6, вместо последнего абзаца

```
Что тебе неизвестно, проходит два фильтра, прежде чем стать вопросом: (1) может ли ответить
код репозитория? — ответь сам из кода, это не вопрос; (2) есть защитимый дефолт? — прими его
и запиши в раздел 4 строкой «(допущение)». Вопросом становится только решение владельца:
trade-off, необратимый выбор, политика. У каждого вопроса — рекомендация.
```

### `steps/plan-check/order-critic.tpl` — пункт 1 заменить, добавить пункт 8

```
1. ТРЕБОВАНИЯ: каждая строка — цитата из TASK; закрытие — Ф-строкой раздела 2 или вопросом
   раздела 6 (строка-ограничение — строкой раздела 5 с (nfr)). «Закрыто сценарием §3» без
   Ф-строки — БЛОКЕР: сценарий описывает работу, которую никто не делает.
8. NEW-МОДУЛИ: у каждого нового модуля-сервиса назван тот, кто его вызовет (проводник);
   у модуля по образцу — что отзеркалировано от образца. Сервис без звонящего — мёртвый
   код, БЛОКЕР.
```

### `steps/plan/judge.ts` — новое правило судьи плана (вычислимое)

- Разобрать колонку «Где закрыто» §1: каждая ячейка обязана содержать `Ф\d+` или `Q\d+`/
  «Вопрос», либо строка Т помечена `(nfr)` и ссылается на §5. Иначе блокер
  `Т<№> без носителя: нет Ф-строки и нет вопроса`.
- Обратный разбор §2: колонка «закрывает» непуста и её Т-ссылки существуют в §1. Иначе
  блокер `Ф<№> без требования`.

### `steps/execute/judges.ts` — продление судьи (a)

- После сверки Ф↔коммит: транзитивно Т→Ф→коммит; Т без коммитов — блокер.
- Сценарии §3 (строки «С\d+»/«Сценарий») без упоминания теста в диффе — блокер с адресом
  сценария; тесты без сценария — заметка, не блокер.
- Числа §4 (значения-токены) — grep по диффу; отсутствующие — блокер «величина не дошла
  до кода».

## 8. Чего RTM не решает (честные границы)

- **Без карты репозитория backward-суды скриптом невозможны** (b1/b2 считают каталоги и
  рёбра вызовов). В solo нет шага graph; строить его ради судей — возврат конвейера,
  который solo сознательно упростил. Компромисс — пункт 8 критика выше (судит модель,
  по чек-листу, дёшево).
- **Победа max-модели на микро-задачах остаётся.** 26k напрямую против 138k конвейера —
  никакая RTM-механика этого не отменит. RTM сужает зону, где дешёвая модель проигрывает
  дорого́й: потери требований и мёртвые модули перестают зависеть от удачи прогона.
- **Счётчики не читают смысл.** Судья «Т закрыт Ф-строкой» гарантирует наличие строки, не
  её правдивость (Ф-строка может врать о контракте) — это остаётся критику и оператору.
  RTM — это нижняя граница качества, не его верхняя.
