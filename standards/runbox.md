# pi-runbox — как гонять izi-конвейер в песочнице

Записка себе. Дата: 2026-08-11, дополнена 2026-08-12. Ветка харнеса: `main`
(`izi-pi-v2`, полоса `task → brd → survey-plan → scope → graph → intake → weight → ripple → design`
— девять шагов, срезы по S26).

## Роли каталогов

`SANDBOX` = `~/IdeaProjects/codemonstersdev/sandbox`.

| Каталог | Что это |
|---|---|
| `$SANDBOX/quarkus-rest-json-app-v2-t{1-3,2,3}` | **ЭТАЛОНЫ**, по одному на задачу (см. «Формы и что на них проверено»). Готовая форма: quarkus-приложение + `TASK.md` + установленный харнес + `git`. В них **не гоняем** — только копируем. |
| `$SANDBOX/runbox/<та же форма>` | **ПРОГОННЫЕ КОПИИ**. Здесь запускается `pi` и пишется `.agent/`. Расходник, но переживающий перезагрузку: раньше копия жила в `/tmp`, и 11 авг упавший прогон разбирать было нечем — система вычистила `/tmp` вместе с тем, что прогон написал в проект. |
| `$SANDBOX/runbox/<форма>/.agent/prev/` | Куда `newRun` уносит состояние прошлого прогона — и куда РУКАМИ кладут артефакт-улику «до» перед починкой (файлы `*-before-s25.*`, `*-before-s26.*`: по ним видно, что именно чинил срез). |
| `$SANDBOX/runbox/{prev-runs,s21-artifacts}` | Замороженные артефакты старых прогонов. Только чтение: сравнивать «как было». |
| `~/IdeaProjects/codemonstersdev/izi-pi-v2` | Сам харнес. Расширение подключено к `pi` **по пути** (`~/.pi/agent/settings.json` → `packages`), поэтому правка `ext/` видна без переустановки — но нужен рестарт сессии `pi`. |
| `~/.pi/workflows/projects/<форма>-*/sessions/*/runs/<runId>/` | Журнал прогона: `journal.json` (что реально звалось и что вернуло), `summary.json` (запуски ролей, токены), `result.json`. **Единственный источник фактов** — печати запускающей модели не верить. |

## Формы и что на них проверено

Одна форма — одна задача. Разные задачи вскрывают разные правила, поэтому старые формы не
переписываются под новую работу: их артефакты — улики.

| Форма | `TASK.md` одной строкой | Чем полезна / что на ней доказано |
|---|---|---|
| `t1-3` | поиск фруктов по части имени с ограничением ответа | Базовая. Одноузловое изменение: маршрут сценария в ОДИН шаг, поэтому правила 3 и 4 шага 9 на ней не срабатывают вовсе. Годится проверять вырожденный случай и шаги 1-8. Прогоны: `cffa2e65` (шаг 3), `c4fde2f3`/`06c4172c` (граф и кэш), `682b6a71` (вес), `e4ebbca9` (рябь). |
| `t2` | новый эндпоинт «один фрукт по имени» + карточка на существующей странице | ДВУСТОРОННЕЕ изменение: страница и эндпоинт обязаны сойтись форматом ответа. Единственная форма, где шов правила 4 шага 9 (`out(k) ∈ in(k+1)`) срабатывает на живых контрактах. Прогоны: `ffe8cb7b` (первый зелёный шаг 9), `b857d4a0` (встал на шаге 7 — дыра «новый модуль», починена S26), `90cfe19f` (зелёный после S25: вход маршрута назван, правило 7 сработало живьём). |
| `t3` | ОТДЕЛЬНАЯ страница карточки, список не переделывать | Заводит НОВЫЙ файл неизбежно — единственная форма, которая проверяет `<delta new="yes">` (S26, правило F3n шага 6). Кэша `.izi/parts` у неё нет: разведка идёт с нуля. |

Заводя новую форму: копировать чистый эталон, заменить `TASK.md`, `node bin/install.mjs --to=…`,
закоммитить. **Задача должна вынуждать нужную ветку, а не позволять её** — на `t2` роль дважды
решала одну задачу по-разному, и ветка нового файла случайно не активировалась.

## Новый прогон — с нуля

```bash
SANDBOX=~/IdeaProjects/codemonstersdev/sandbox
FORM=quarkus-rest-json-app-v2-t3                    # какая задача гоняется — см. таблицу форм
rm -rf $SANDBOX/runbox/$FORM                        # каталог-расходник в runbox, не cwd терминала
cp -R $SANDBOX/$FORM $SANDBOX/runbox/
cd $SANDBOX/runbox/$FORM && pwd && ls -l workflows/izi.js && pi   # затем в чате: /izi
```

Запускать в **обычном терминале** (не в пейне herdr): `env | grep HERDR` должен быть пуст, иначе
агенты уйдут в herdr-транспорт и потеряют наряд — см. предусловие 4.

Если харнес в ветке менялся — сначала обновить **эталон**, а копию делать уже с него:

```bash
cd ~/IdeaProjects/codemonstersdev/izi-pi-v2 && node --test          # красное — прогона нет
node bin/install.mjs --to=$SANDBOX/$FORM            # в ЭТАЛОН; и вторым вызовом в runbox-копию,
node bin/install.mjs --to=$SANDBOX/runbox/$FORM     #   если она уже создана и её не пересоздают
cd $SANDBOX/$FORM && git add -A && git commit -m "harness: <срез>"
```

Повторный прогон в той же копии без пересоздания: `git clean -fd && git checkout .` внутри копии —
и СРАЗУ переустановить харнес (`node bin/install.mjs --to=$SANDBOX/runbox/$FORM`). В копии харнес
лежит рабочими изменениями, а не коммитом, поэтому `git checkout .` откатывает его к версии, с
которой копию сделали: 12 авг так уехали разом четыре среза, и прогон пошёл бы по старой программе
молча. Проверка одной строкой перед запуском: `grep -c allOf workflows/izi.js` в копии — ноль значит
старый харнес.
Руками чистить `.agent/` больше не нужно — прогон делает это сам первым действием (`newRun`):
`answers.md`, `pending.json` и остатки `staging/` уезжают в `.agent/prev/`, артефакты и кэш
`.izi/parts` остаются. Ответ прошлого прогона в новый не переезжает намеренно: его значения —
законный источник чисел для `checkBrd`/`checkFrd`, а на вопрос ЭТОГО прогона он не отвечает. **Никогда** `rm -rf` каталога, в котором стоит
терминал или `pi` — процесс падает на `uv_cwd`; чистим содержимое, а не сам `runbox/`.

## Как вести прогон — навык, а не память

`standards/live-run.md` — навык наблюдения за прогоном. Что делать перед запуском, что выводить каждые
3 минуты и по каким признакам искать ошибку В ТЕКСТЕ, а не в модели: повторившийся блокер, не
падающее число блокеров, справка за справкой, два правила против друг друга, инструкция против
состояния. Он проектно-независим и о формах ничего не знает — формы и их улики живут здесь.

Перед прогоном читаются ОБА: этот файл говорит, ЧТО за форма и какие у неё грабли; соседний — КАК
вести прогон и за чем смотреть.

## Перед каждым запуском — три условия

1. **Рестарт `pi`.** Расширение читается на старте сессии, `workflows/izi.js` — на каждом прогоне.
   Симптом старой сессии: `<имя> is not defined` (воркфлоу уже зовёт функцию, которой в сессии нет).
   Сейчас расширение `v1.11.0`: `readText answers brdForm frdForm budgets herdrStatus newRun
   checkTask checkBrd promote setPending clearPending survey cells digest reuse remember checkPart
   buildGraph graphMap checkFrd weight ripple design`. Роли резолвятся из каталогов срезов
   репозитория: `gilb` (steps/brd), `scout` (steps/scope), `intake` (steps/intake), `designer`
   (steps/design) — файл роли лежит В РЕПОЗИТОРИИ, а не в копии формы, поэтому правка роли тоже
   требует рестарта сессии, но не переустановки формы.
   `pi install ./ext` НЕ нужен: расширение подключено по пути (`~/.pi/agent/settings.json` →
   `packages` → `…/izi-pi-v2/ext`), правка видна после рестарта сессии и только после него.
2. **Глобальная копия роли не должна перекрывать репозиторий.** Хост склеивает роли так:
   `{...роли расширения, ...роли ~/.pi/agent/pi-extensible-workflows/roles}`
   (`pi-extensible-workflows/packages/core/src/validation.ts:269`) — **последний слой побеждает**.
   Лежавшая там `gilb.md` от 6 авг тихо подменяла роль из ветки; 10 авг переименована в
   `gilb.md.bak-20260810`. Проверка перед прогоном:
   `ls ~/.pi/agent/pi-extensible-workflows/roles/` — `*.md` там быть не должно.
3. **`pi` стартует ИЗ каталога прогона.** Хост читает скрипт как `resolve(context.cwd, scriptPath)`
   (`pi-extensible-workflows/packages/core/src/validation.ts:801`), где `context.cwd` — каталог
   старта сессии, а не то, куда ты перешёл потом. Симптом промаха 10 авг:
   `Cannot read workflow script file workflows/izi.js: ENOENT … open '/Users/mac/workflows/izi.js'`.
   Улика: имя каталога сессии — `ls -t ~/.pi/agent/sessions | head -1` должно кончаться на
   `-sandbox-runbox-quarkus-rest-json-app-v2-t1-3--`, а не быть `--Users-mac--`.
4. **Пейн herdr — НЕ гонять в нём, пока не починен транспорт.** 10 авг прогон в herdr дошёл до
   шага 4 и упал: скауты не получили наряд, первое сообщение агента —
   `"Continue the task from the current session state."`. Наряды в `state.json` были полными
   (c0 — 3123 б, c1 — 3628 б), но пану они передаются файловым меншеном
   `@/tmp/pi-herdr-prompt-*.txt` (`packages/extensions/herdr/index.ts:259`, файл создаётся в
   `createCommandFiles` и удаляется в `close()`) и в сессию не доехали; executor дослал
   continuation (`index.ts:432`). Зелёный прогон 8 авг шёл с `transport=local, hooks=[]` — там
   первое сообщение агента и есть наряд. Сравнение транспорта:
   `node -e 'require("<run>/state.json").agents.forEach(a=>console.log(a.role,a.attemptDetails[0].transport,a.attemptDetails[0].setup.hookNames))'`.
   Побочный симптом: `gilb` в herdr выживает, потому что сам читает `TASK.md` с диска, — зелёный
   шаг 2 не доказывает, что наряды доезжают.

## Retry — жать каждые 5 секунд, иначе прогон стоит (15 авг)

**`openrouter/qwen/qwen3.6-27b` обрывает почти каждый длинный вызов роли.** Симптом одинаковый:
модалка `Subagent "<роль>" failed · Provider error: This operation was aborted` с тремя пунктами —
`Retry`, `Change model`, `Abort workflow`. Это не дефект конвейера: после `Retry` роль отрабатывает,
логика не страдает. Цена в другом — **прогон стоит, пока модалку не закрыли**, и на длинных проходах
(`router`, `designer`, `intake`) обрывы идут подряд. За четыре прогона 15 авг их было от 5 до 9 на
прогон.

Поэтому модалку сторожит скрипт, а не человек: **проверка каждые 5 секунд**, нажатие только когда в
пейне одновременно видно `Subagent "…" failed` и `→ Retry`.

```bash
S=izi-t2
while true; do
  tmux has-session -t $S 2>/dev/null || break
  P=$(tmux capture-pane -p -J -t $S -S -25)
  if grep -q 'Subagent ".*" failed' <<<"$P" && grep -q '→ Retry' <<<"$P"; then
    tmux send-keys -t $S C-m; sleep 3
    grep -q '→ Retry' <<<"$(tmux capture-pane -p -J -t $S -S -25)" && tmux send-keys -t $S C-m
  fi
  sleep 5
done
```

Три вещи, которые стоили времени:

1. **Enter доезжает только как `C-m`.** `tmux send-keys … Enter` модалка не видит (в пейне
   предупреждение `tmux extended-keys is off`). Проверять по исчезновению `→ Retry`, а не по факту
   отправки.
2. **Не открывать TUI `/workflows`, пока идёт прогон.** Если retry прилетит поверх открытого TUI,
   ввод в чат умирает и прогон приходится перезапускать целиком. Смотреть только read-only:
   `tmux attach -t izi-t2 -r`.
3. **Обрыв ≠ красный чек.** В `summary.json` каждая перезапущенная роль появляется ОТДЕЛЬНОЙ
   записью `role×1`, а не как `role×2`: `router×3` в списке агентов может означать три обрыва
   провайдера, а не три круга починки. Круги смотреть по `journal.json` —
   `function/design/<n>` с `ok:false`.

## Как поменять модель ролей

Три места, и они перекрывают друг друга в этом порядке — снизу вверх побеждает верхнее:

| где | что задаёт | когда читается |
|---|---|---|
| `steps/<срез>/<роль>.md`, поле `model:` во frontmatter | **побеждает всё** | старт сессии `pi` |
| `<каталог прогона>/.pi/pi-extensible-workflows/settings.json` → `modelAliases` | проект, если он доверенный | старт сессии |
| `~/.pi/agent/pi-extensible-workflows/settings.json` → `modelAliases` | машина: `routing` · `execution` · `judgment` | старт сессии |

**Правильный способ — один:** в роли стоит `model: execution` (ИМЯ алиаса, без слэша), а модель
выбирается в машинных настройках. Тогда смена модели это одна строка в одном файле.

```bash
# поменять модель всех ролей
node -e 's=require(process.env.HOME+"/.pi/agent/pi-extensible-workflows/settings.json")' # посмотреть
# правим modelAliases.execution → нужная модель, затем ОБЯЗАТЕЛЬНО рестарт pi
```

**Три ловушки, каждая стоила прогона 13 авг:**

1. **Роль с прописанной моделью молча игнорирует алиасы.** Все пять ролей несли
   `model: openrouter/qwen/qwen3.6-27b`, и правка `modelAliases` не делала ничего — дважды подряд.
2. **Алиас на модель, которой нет у сессии, тоже молчит.** Поставил `openrouter/google/gemini-3.6-flash`,
   а сессия знает только `gemini-3-flash-preview` и `qwen3.6-27b` — исполнение откатилось на qwen без
   единого сообщения. Список доступного лежит в `snapshot.json` прогона, поле `models`.
3. **В статусной строке `pi` видна модель ЧАТА, а не ролей.** Она может быть gemini, пока все роли
   идут на qwen. Экран не противоречит неверному предположению ничем.

**Единственная честная проверка — по диску, после старта роли:**

```bash
R=$(ls -td ~/.pi/workflows/projects/<форма>-*/sessions/*/runs/*/ | head -1)
node -e 'console.log([...new Set((JSON.stringify(require(process.argv[1]+"/state.json")).match(/"model":"[^"]+"/g)||[]))])' "$R"
# и что вообще было доступно сессии:
node -e 'console.log(require(process.argv[1]+"/snapshot.json").models)' "$R"
```

## Что ждать в логе (форма t1-3, 17 файлов)

```
budgets: loops=3 questions=3 checkpointRetries=2 maxParallel=8 (defaults)
run: состояние прошлого прогона убрано в .agent/prev — ответов 2, staging 0, открытый вопрос
                                                  (в чистой копии вместо этого: `run: .agent чист`)
herdr: off — pi запущен не в пейне herdr …        (вне herdr это НОРМА, прогон идёт)
survey-plan: files=17 bytes=27857 cells=2 edges=4 [java:edges:9 (unknown):no-rules:8]
scope: батч spine root
scope: cells=2 modules=15 gaps=0 cache-hit=0
graph: modules=15 components=2 isolated=5 levels=4 edges=8 suites=2 surface=4
graph: не найдено в репозитории — toggles, branching, contract, integrations
```

Раскладка роя посчитана на реальном дереве: `spine` (README.md, pom.xml) и `root` (15 файлов) →
**один батч, два скаута параллельно, задействованы оба наряда** — `order.spine.tpl` и
`order.survey.tpl`. Клетки зовутся `spine`/`root`, а не `c0`/`c1`: с S17 id выводится из ПУТИ, а не
из порядка, — иначе кэш нечего было бы держать.
Отсев ожидаемый: `mvnw`/`mvnw.cmd` по `SKIP_FILES`, `.mvn/` как точечный каталог, `TASK.md` и
`izi.config.json` как входы харнеса.

Артефакты успеха шагов 1-5: `.agent/brd.md`, `.agent/survey-plan.json`, `.agent/graph-computed.xml`,
`.agent/graph-parts/{spine,root}.xml`, `.agent/appgraph.xml`.

**Хвост полосы (шаги 6-9), добавлен 12 авг.** Лог:

```
intake: карта <N> Б на <M> узлов, потолок 115000 Б — едет роли целиком
intake: deltas=1 unknown=0 scenarios=2 touched=2
weight: mode=minor из GET /fruit/{name} (Added) (дельт 1)
ripple: design=needed узлов 3 из 17 (затравок 2, mode=minor)
design: узлов 2, маршрутов 4, списков юнитов 2 → .agent/design-graph.xml + .agent/data-flow.md
izi: полоса кончилась на шаге 9. Поставка — артефакты .agent/; рабочее дерево НЕ трогать
```

Артефакты успеха шагов 6-9: `.agent/frd.xml`, `.agent/mode` (одно слово), `.agent/design`
(`needed|skip`), `.agent/ripple.xml`, `.agent/design-graph.xml`, `.agent/data-flow.md`. Последний
несёт ДВЕ секции: `$START_FLOW id=` на сценарий и `$START_TESTS path=` на узел — вторая и есть
`<dod>` будущего тикета.

**Красный чек шага 9 — это НЕ сбой:** блокеры едут роли в фидбек, она переписывает артефакт, и
`designer×2` в `summary.json` при зелёном итоге означает, что рельса починки отработала. Смотреть
`function/design/2` в журнале: номер правила в тексте блокера (`docs/data-flow.md` §6) говорит, что
именно не сошлось.

**Что на шаге 9 стоит прочитать ГЛАЗАМИ** (машина проверила состав и стыки, но не смысл):
слова `delta` у узлов; первая строка каждого `$START_FLOW` — чем сценарий запущен; список
`$START_TESTS` — примешь ли ты его как определение готовности тикета.

**Что в этом прогоне ново и потому может покраснеть** (грамматика частей поднята 2→3, кэш
`.izi/parts` промахнётся с причиной `grammar 2→3` и скауты перепишут части):

| проверка в `appgraph.xml` | зачем |
|---|---|
| `<artifact name="rest-json-quickstart" root="."/>` | седьмой ответ хребта, роль пишет его впервые |
| у обоих `<suite>` непустой `match` | иначе `FruitResourceIT` уедет командой юнитов и выполнит **ноль тестов зелёным** |
| `FruitResourceIT` → `suite="component-native"`, `FruitResourceTest` → `suite="unit"` | ради этого и поднималась грамматика |
| `pkg="org.acme.rest.json"` у java-модулей | адрес модуля |
| 15 `<module>`, 2 `<component>`, 5 `<isolated>`, `levels="4"` | иерархия посчитана из рёбер |
| `<systems/>` пуст, `<subject name="search" found="no"/>` | «нет» — это ответ, а не молчание |

`P6 spine: <suite …> shares path=…` или `P1 spine: <artifact> is missing` — это гардрейл сработал
верно, а роль не ответила: чинить формулировку наряда `order.spine.tpl`, не правило.

## Диагноз

Печати запускающей модели **не верить**. Факты лежат на диске:

```bash
R=$(ls -td ~/.pi/workflows/projects/<форма>-*/sessions/*/runs/*/ | head -1)
node -e 'const s=require(process.argv[1]+"/summary.json");
  console.log(s.state, s.usage.agentLaunches, s.usage.tokens, s.agents.map(a=>a.role+"×"+a.attempts).join(" "));
  const j=require(process.argv[1]+"/journal.json");
  for (const [k,v] of Object.entries(j.completed||{})) console.log(k, JSON.stringify(v.value).slice(0,200))' "$R"
# journal.json.completed — ключи вида function/<имя>/<n>: что реально звалось и что вернуло.
# Формы `j.completed` не угадывать: у journal.json ТРИ верхних ключа — completed, awaiting, decisions.
cd $SANDBOX/runbox/$FORM && git status --short   # что прогон написал в проект (должно быть пусто:
                                                 #   до шага 15 полоса файлы проекта НЕ трогает)
```

Промежуточное состояние роли лежит в `.agent/staging/` — гардрейл судит **его**, в чистовик
(`.agent/brd.md`, `.agent/graph-parts/`) файл попадает только после зелёного чека.
Вопрос оператора приходит обычным сообщением в чат; ключ вопроса машина берёт из
`.agent/pending.json`, ответ пишется в `.agent/answers.md` тулом `izi_answer`.

**runId после `izi_answer` не набирать по памяти.** Прогон `d0740969-…-cb2b15ae7210` (11 авг) встал
на `brd-q2` на пять минут: модель переставила две буквы в UUID (`ae`→`ea`), получила `not pending`,
затем `run not found` — и «сверяла» свою же опечатку сама с собой. Хост в сообщении паузы runId не
повторяет (`host.ts:629`), а `prompts/izi.md` прямо велит его ВСПОМНИТЬ. Лечение до правки харнеса:
подтверждать паузу из TUI `/workflow` (`enter` на прогоне → run actions), где id вводить не надо, —
либо копировать id из имени каталога прогона, а не из головы.

## Где искать, чем это всё описано

Не пересказывать по памяти — в репозитории `izi-pi-v2` на каждый шаг заведён свой док, и правило
живёт ровно в одном месте:

| Вопрос | Где ответ |
|---|---|
| порядок шагов, карточка каждого, раскладка файлов | `docs/workflow.md` §1-§3 |
| зачем полоса устроена так | `docs/concept.md` |
| правила приёмки шага 6 (F1..F7, F3n) | `docs/intake.md` §4 |
| вес по SemVer (шаг 7) | `docs/weight.md` |
| флаг дизайна и подграф (шаг 8) | `docs/ripple.md` |
| грамматика дизайн-графа, маршрут, семь правил гардрейла (шаг 9) | `docs/data-flow.md` §4-§6 |
| карточка шага 9, разбор его расхождений и живые улики | `docs/design.md` |
| что отложено ВСЛУХ и при каком событии вернуться | `docs/triggers.md` |
| текущая работа и её состояние | `backlog.md` (пусто = срез закрыт) |
| как писать код, роль, воркфлоу | `standards/{code,role,workflow}.md` |

Правило проекта, из-за которого этот список короткий: **одно правило — одно место**. Если ответ
нашёлся в двух файлах, один из них устарел, и это дефект, а не удобство.

## Мелочи, о которые уже спотыкались

- **Двоеточие в `description:` роли роняет ВЕСЬ прогон** на валидации метаданных, до единого токена:
  YAML читает `«: »` внутри незакавыченного скаляра как вложенный маппинг
  (`Invalid role frontmatter: Nested mappings are not allowed in compact mappings`). 12 авг это
  стоило запуска шага 9; шов теперь в `steps/design/design.test.mjs`.
- В `.gitignore` формы есть eclipse-правило `bin/` — каталог харнеса `bin/` на диске есть, но вне
  индекса. На прогон не влияет, в `git status` не появится.
- Бюджеты: файла `izi.config.json` в форме нет, значит `DEFAULT_BUDGETS`. Неизвестный ключ в этом
  файле — отказ прогона, не тихое умолчание.
- `TASK.md` формы: «UI тянет весь список фруктов… нужен поиск по части имени, с ограничением на
  размер ответа, существующие вызовы ломать нельзя» — задача заведомо с дыркой (размер лимита),
  то есть вопрос оператору на шаге `brd` ожидаем, а не является сбоем.
