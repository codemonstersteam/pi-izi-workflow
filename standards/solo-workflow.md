# Standard: воркфлоу solo — как обязан выглядеть код

Что здесь: требования к целевому виду воркфлоу solo. Дизайн и data-flow — `PLAN.md`;
этот файл — ПРАВИЛА, которые код обязан соблюдать, с обоснованиями, купленными живыми
прогонами 26–27.08.2026 (quarkus FRUIT-1, eddi DOS-535, сравнения pi-напрямую).

## 1. Распределение и установка

| правило | обоснование |
|---|---|
| Всё живёт в ПАКЕТЕ `ext/` (функции, команда, роли, судьи); `pi install ./ext` — один раз на машину | нативная модель pi-extensible-workflows; прежний bin/install.mjs копировал харнесс в каждый проект — это «лишние файлы» |
| В проекте оператора — НОЛЬ харнесс-файлов: только его TASK.md [+ его PROMPT.md] и рантайм `.agent/` | проект не должен знать о конвейере |
| Полоса — INLINE-СКРИПТ в команде (`ext/prompts/solo.md`), вызывающий каталог-функции | `scriptPath` резолвится от cwd проекта (validation.ts:801) — файл скрипта в проекте был бы харнесс-файлом; inline-скрипт персистится в run и резюмится |
| Роли — из `roleDirectories` пакета | то же |
| Команда `/solo` = ОДИН tool call `workflow({name:"solo", script:…, args:{key, stopAfter}, foreground: true})` | см. §2 |

## 2. Запуск: foreground, чат-модель — кнопка

В фоне каждый вопрос оператора стоит ХОД чат-модели (follow-up триггерит её для
`workflow_respond`). В foreground прогон — прикреплённый tool call: модель отзвала и не
зовётся; вопросы — TUI `ui.input` через хост-функцию `ask` (0 токенов); результат печатает
карточка. Поэтому: **только foreground**; чат-модель = ~100 токенов на кнопку, её последний
ход. Файловый фолбэк ask (question.txt/answer.txt) обязателен — включается сам, когда TUI
недоступен.

## 3. Станции

```
draft → critic → approve(оператор) → solve → done
```

- **draft**: роль planner (`tools: [read, bash, write]`, thinking high) получает
  артефакт-спеку ДОСЛОВНО (PROMPT.md проекта или дефолтную из пакета) + TASK.md, сама
  читает репозиторий, пишет staging-план. НЕТ карт/срезов/чертежей — срезы проиграли
  живому коду в обоих сравнениях (T74: проводник/квинтета/синк-кластер потеряны срезами).
- **critic**: роль (read) судит смысл по чек-листу шести разделов + выборочная сверка с
  кодом; ≤3 блокера с адресом строки. Вопросы раздела 6 плана → ask-рельса → answers.md →
  круг draft.
- **approve**: ask «прочитай .agent/PLAN.md — согласен?»; reject → круг draft с причиной.
- **solve**: роль dev (`read, bash, edit, write`), наряд — ТРИ ПРАВИЛА (доказано живым
  прогоном: минимального промпта достаточно, трассировка в коммитах рождается сама на
  структурированном плане): 1) итерация = строка Ф = коммит; 2) величины из §4, гарантии
  §5 нерушимы; 3) существующие тесты не переписывать. Одна сессия без разрезания —
  кэш держит экономику (eddi: 23M cache reads на 28 строк).

## 4. Судьи (скрипт — вычислимое, роль — смысл)

| код | что проверяет | красное |
|---|---|---|
| draft-judge | 6 разделов заголовками; таблицы 1–2 парсятся; каждая цитата раздела 1 — подстрока TASK; каждый путь раздела 2 существует (`test -e`) или помечен «новый» с образцом; колонка источника раздела 4 непуста | круг починки draft |
| solve (a) | каждая строка Ф ↔ коммит (`git log` от старта станции) | круг solve с адресом строки |
| solve (b) | существующие тест-файлы в диффе только расширены (добавление строк допустимо, удаление/правка — нет) | круг solve |
| solve (c) | дифф аддитивен по списку гарантируемого §5 | круг solve |

Абсолют (b) корректен, потому что спека раздела 2 требует: строка Ф, меняющая поведение
существующего теста, обязана иметь строку плана на изменение этого теста. Спор закрыт на
фазе планирования.

## 5. Спека плана (PROMPT)

Шесть разделов, порядок фиксирован: ТРЕБОВАНИЯ (цитаты дословно → где закрыто, включая
ограничения) · ИЗМЕНЕНИЯ (файл \| A/C \| контракт \| требование; новый — с образцом;
**строки упорядочены по зависимостям**; **легальная правка существующего теста — отдельная
строка**) · СЦЕНАРИИ (до/после, пути и параметры) · ВЕЛИЧИНЫ (значение + источник, ничего
«по умолчанию» без источника) · ГАРАНТИИ (что не ломается, поимённо) · ОТКРЫТЫЕ ВОПРОСЫ
(вместо молчаливых допущений, с рекомендацией).

## 6. Обратная связь план←код

dev вправе править PLAN.md при найденном баге плана — только с обоснованием в коммите;
судья перечисляет такие правки в итоговой карточке оператору. Существенное (поведение/
требование/гарантия) — СТОП и вопрос, не молча.

## 7. Тесты и приёмка

- Юниты судей — на фикстурах-строках, обе стороны каждого правила.
- Компонентный тест станции — мок-роли (next/fold напрямую), tmp-cwd; швы: потерянная
  цитата → круг; правка существующего теста без строки плана → красный (b); Ф без
  коммита → красный (a).
- `node --test` зелёный целиком — до любого живого запуска.
- Живой proof: чужой проект, в корне до запуска только TASK.md; после — `.agent/`,
  PLAN.md, коммиты; после кнопки — ноль ходов чат-модели; Ф↔коммит 1:1; тесты проекта
  зелёные руками принимающего.

## 8. Бюджеты и метры

Целевые (эталоны живых прогонов, допуск ±30%): план quarkus-класса 26k/3,5 мин; план
eddi-класса 166k/15 мин; разработка 42k/5,5 мин (quarkus) и ~450k/~1 ч (eddi).
Превышение — повод искать дефект текста, а не поднимать бюджет.
