Концепция, из которой режется backlog. Ничего нового в полосу не добавляется — переезжает ОДИН уже
написанный шаг и заводится ОДИН вызов уже написанных чистых функций.

## 2 · Судья 1 — критик FRD (роль)

**Предмет.** `.agent/frd.xml` против `TASK.md` и `.agent/brd.md`: доехало ли требование целиком и не
появилось ли в нём того, чего оператор не говорил.

**Место.** Сразу после зелёного `checkFrd`, ДО шага 7. Номер шага остаётся 11 (переезжает шаг, не
нумерация).

**Что уже есть.** Роль `steps/review/critic.md`, шаблон `steps/review/order.tpl`, гардрейл
`steps/review/review.mjs`, вызов `workflows/izi.js:1264`, вердикт-грамматика `.agent/review.xml`.
Решение о переезде записано в `docs/workflow.md:110` и `:190` как TOBE. На прогоне eddi
`.agent/review.xml` НЕ СУЩЕСТВУЕТ — критик не звался ни разу.

**Что меняется.** Предмет (был план — станет FRD) и место (было после шага 10 — станет после 6).
Аргумент, почему план больше не судит роль, — в §3: план судит доказательство.

**Вход:** `TASK.md`, `.agent/brd.md`, `.agent/staging/frd.xml`, `.agent/answers.md`.
**Выход:** `.agent/review.xml` — `verdict="Pass|Reject"` и блокеры с кодами.
**Reject** кладёт блокеры в `.agent/answers.md` и перезапускает `intake` — тот же рельс, которым
работает `rework` гейта 1; счётчик кругов общий с `intake`.

**Коды, которые он обязан выносить** (каждый куплен живым прогоном):
- `requirement-not-carried` — требование BRD/TASK, не доехавшее ни `<usecase>`, ни `<scenario>`, ни
  `<nfr>`, ни `<delta>`. Улика: «существующий вызов остаётся без изменений» на форме `t2`, два
  прогона подряд, разные формулировки, один исход.
- `invented-value` — значение словаря или `fit`, которого нет ни в `TASK.md`, ни в значениях ответов.
  Улика: `resourceURI` в `Glossary` с `source="brd.md"` при BRD «only id + version + terms».
- `open-question` — `<question>` без ответа, с которым FRD идёт дальше по полосе. Улика: два вопроса
  eddi, один из которых машина потом ответила сама сигнатурой наряда 08.
- `goal-not-delivered` — `<post>` use case, не покрытый объединением его же шагов. Код уже существует
  в грамматике `review.mjs` (F9 `checkFrd` его читает как `rewind`).

## 3 · Судья 2 — сухой прогон нарезки (скрипт)

**Предмет.** План (`task/<KEY>/design/*.md` + очередь работ), до гейта 1.

**Механизм.** `tickets({ dry: true })` — тот же `ticketsOf` + `checkTickets`, файлы не пишутся,
возвращаются `blockers[]`. Красный означает: по этому плану исполнимый набор нарядов не нарезается.

**Почему это доказательство, а не мнение.** Судит и режет ОДИН И ТОТ ЖЕ код. Расхождение «проверили
одно — нарезали другое» физически невозможно, вердикт воспроизводится на сохранённых артефактах за
0 токенов.

**Почему это возможно на шаге 10 — проверено по коду.** `ext/index.mjs::tickets.run` читает:
`task/<key>/design/*.md` (шаг 9), `.agent/frd.xml` (6), `.agent/appgraph.xml` (5), `.agent/ripple.xml`
(8). Из шагов 12–13 берутся ровно две вещи: `gate1.json` как РАЗРЕШЕНИЕ (`ext/index.mjs:2247`) и имя
ветки в заголовок наряда — косметика. Ни одного ФАКТА нарезки после гейта не появляется.

**Красный возвращает ДИЗАЙНЕРУ (шаг 9), не оператору.** Оператор на гейте 1 видит план, про который
уже доказано, что он нарезается.

**Правила, которые становятся правилами ПЛАНА** (сегодня они либо косметика наряда, либо не
существуют):
1. каждый `<step>` каждого use case принадлежит ровно одному разделу плана;
2. use case, чей актёр входит путём, получает границу; use case без пути — НЕ получает, и это
   блокер плана, а не молчание (улика: UC5 eddi — единственный без внешней проверки);
3. класс теста раздела принадлежит юнитовому сьюту карты (улика: `RestImportServiceIT`);
4. волны строятся (нет цикла; тип, названный в сигнатуре, кем-то объявлен);
5. `<field in="E">` имеет раздел, который его напишет (улика: `AgentConfiguration`);
6. шаг, несущий ошибку, имеет в плане её КОД и СТАТУС; use case имеет предусловие; набор имеет
   закрывающий прогон внешнего сьюта — иначе исполнителю нечем закрыть работу.
