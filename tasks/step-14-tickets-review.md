## 2. Блокирующее: задача НЕ будет выполнена

### Д1. Никто не заводит привязку глоссария к агенту

FRD объявляет поле `<field name="glossaries" in="AgentConfiguration" …>`, но **дельты на
`configs/agents/model/AgentConfiguration.java` нет** → шаг 9 не написал раздел → шаг 14 не нарезал
наряд. Файл в поставке не участвует вообще.

Что от этого рассыпается:

| Наряд | Шаг требования | Чем не выполним |
|---|---|---|
| 16 GlossaryService | UC5/2, UC5/3 | `getAllByAgentId(String agentId)` неоткуда взять список глоссариев агента |
| 20 LlmTask | UC5/1 | «reads agent configuration and extracts glossary references» — поля нет |
| 17 RestExportService | UC6/2 | «extracts glossary references» — выбрать «referenced by the agent» не по чему |
| 22 RestImportService | UC7/4 | «glossary references in agent config restored» — восстанавливать некуда |

Улика из живого репозитория, объясняющая, ПОЧЕМУ это проглядели: сниппеты в eddi **глобальны** —
`LlmTask.java:214` кладёт `promptSnippetService.getAll()` в `templateDataObjects` для всех агентов, и
поля `snippets` в `AgentConfiguration` НЕТ. Решение оператора «Глоссарий — reference в agent config,
как snippets» описывает механизм, которого в проекте не существует; «подставляем только глоссарии,
привязанные к агенту» требует завести его с нуля. FRD поле объявил, дельту — нет.

**Адрес: шаг 6.** Объявленное поле чужого модуля обязано порождать дельту на этот модуль, иначе
словарь данных обещает то, чего не построит ни один наряд.

### Д2. Тикет 20 не говорит, откуда взять agentId

`getAllByAgentId(String agentId)` — а в «What you call» у `IConversationMemory` стоит одна строка
`public interface IConversationMemory`, без единого метода. Слабая модель выдумает способ достать
идентификатор агента из памяти разговора.

**Адрес: шаг 14 (facts).** У интерфейса из карты собрано объявление, но не члены — для класса
(`DocumentDescriptor`) члены едут, для интерфейса нет.

## 3. Существенное

### Д3. Граничные наряды 05/06/07 называют не тот канал

Все три несут «How to call it — ONLY through the program boundary: HTTP /glossarystore/glossaries».
Фактически: экспорт — `@Path("/backup/export")` + `{agentId}`, импорт — `@Path("backup/import")`,
удалённая синхронизация идёт вообще не через локальный REST. Наряд UC6 требует проверить экспорт
через ручку CRUD глоссариев — так тест не написать.

Причина: у актёра `api-client` один `via`, и шаг 14 подставляет его в каждый UC этого актёра.
**Адрес: шаг 14** (канал брать из шага UC, где путь назван дословно) **или шаг 6** (`via` на UC, а не
только на актёра). Первое дешевле: `UC6 step 1` уже несёт «client requests agent export».

### Д4. Тикет 22: ворота гоняют тест, который сьют исключает

`outputs: RestImportServiceIT.java`, ворота `./mvnw test -Dtest=RestImportServiceIT`, а в `pom.xml`
у surefire стоит `<excludes>**/*IT.java</excludes>`; `*IT.java` — сьют failsafe (`./mvnw verify`).
Ворота либо не гоняют ничего, либо падают по чужой причине. В том же наряде образец теста назван
`RestImportServiceTest.java` — наряд противоречит сам себе.

Имя пришло из строки `verify` плана (шаг 9 написал `-Dit.test=RestImportServiceIT`). Шаг 14 научился
переписывать КОМАНДУ из карты, но имя класса берёт у роли как есть.
**Адрес: шаг 14** — имя своего теста обязано подходить под `match` юнитового сьюта (`*Test.java`),
иначе это блокер, а не наряд.

### Д5. Модель Glossary шире решения оператора

Тикет 09 объявляет `Glossary(String id, Integer version, List<Term> terms, String resourceURI)` —
четыре поля. TASK.md: «поля Glossary ресурса — только id + version + terms». Образец
`PromptSnippet.java`, который тот же наряд велит списать, не несёт **ни одного** из них: id, версия и
resourceURI живут в `AbstractResourceStore`/`DocumentDescriptor`. Наряд даёт две несовместимые
инструкции сразу.

**Адрес: шаг 6** — `<field name="resourceURI" in="Glossary">` появился в словаре данных вопреки
явному решению оператора.
