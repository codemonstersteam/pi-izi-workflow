## Два дефекта прогона `79650c98`

**Д4 — `{UNCHECKED}` подаётся роли и не читается ни одним правилом.** Наряд честно передал
`fruits.html — своей команды нет; закрывают: mvn test · mvn verify -Pnative`, и роль промолчала —
имея на это право: R5 считает строки `{OWED}`, а таблицу непроверяемых узлов не считает никто.
Полнота реализована для одной таблицы из двух, то есть вторая таблица — пожелание.

Промежуточная починка уже стоит: строка `witness:<path>` в `owedItems`, закрываемая обычным
`<covers>`. Она **слабее нужного**: назвать УЗЕЛ легко, это не решение. Решение — назвать КОМАНДУ.

**Д3 — привязку `covers` не судит никто.** В `.agent/review.xml` прогона:
`<covers item="S1" node="scenario:S2"/>` — сценарий S1 живёт на ресурсе (`frd.xml`,
`nodes="…FruitResource.java"`), узла `scenario:S1` в плане нет вовсе; `<covers item="UC2/2a"
node="scenario:S2"/>` — ветка в этом сценарии не живёт. R5 проверяет, что строка закрыта один раз и
что `node` есть в плане. Что узел имеет к строке ОТНОШЕНИЕ — не проверяет никто.

Важное для общей картины: инструкция роли на этом прогоне была уже узкой — чек-лист данными, id
машинные. Узость правды не купила. Покупает её счёт.

## Что сделать

### R6 — таблица непроверяемых узлов получает своё правило

Строки `witness:` уходят из `owedItems` — вместо них отдельное правило над отдельной таблицей, как
и сами таблицы в наряде отдельные.

Каждый `code`-узел плана с пустым `check` закрыт ровно одним из двух:
- `<witness node="…" cmd="…"/>`, где `cmd` **дословно** одна из команд его закрывающих сценариев;
  машина сверяет по `plan-index.json` — команда копируется из списка, не сочиняется;
- блокер `unverifiable-node` с этим узлом.

Молчание — красная форма. Два `<witness>` на узел — красная форма: одна команда, одна строка.

Ложный `witness` остаётся возможен: судить, ИСПОЛНЯЕТ ли команда узел, машина не может. Это
названный остаток риска, а не недоделка — триггер «второй наблюдённый промах».

### R7 — привязка `covers` к строке

Строка чек-листа закрывается узлом, который может иметь к ней отношение:
- строка-сценарий `Sx` — только `scenario:Sx` либо узел из `nodes` этого сценария FRD;
- строка `UC*/…` (`post`, ветка `ext`) — только `scenario:` сценариев этого use case либо их узлы;
- строка `nfr:…` и строка узла вне FRD — как сегодня (любой узел плана): у первой адресата в FRD
  нет, вторая сама себе адрес.

Операнды уже в `parseFrd`: `scenario.uc`, `scenario.nodes`.

Наблюдённая ложь `S1 → scenario:S2` краснеет. Ложь `UC2/2a → scenario:S2` формально переживает R7 —
сценарий S2 принадлежит UC2. Это признаётся честно: её добивает срез B, если он будет взят.

### Наряд `steps/review/order.tpl`

Блок `{UNCHECKED}` переписывается с вопроса на действие: назови команду ДОСЛОВНО. Сегодня блок
спрашивает и не даёт куда записать ответ — отсюда и молчание живьём. В схему добавляется
`<witness node cmd/>`, в CONSTRAINTS — три строки (R6, R7, и что witness не даёт судить о красноте
команды: это по-прежнему шаг 16).
