## Что снял ЖИВОЙ прогон — `e90d9ce1`, eddi, задача Glossary

Первый живой прогон среза на монолите. Дошёл до шага 3b за 0 токенов разведки, упёрся в потолок и
задал вопрос — то есть рельса сработала ровно там, где обещано. И тем же вопросом себя и похоронила.

| снято / изменено | улика |
|---|---|
| **правило отбора «якорь во ВХОДЕ» по тексту файла** → якорь НАЗЫВАЕТ файл (путь), `steps/focus/focus.mjs::names` | якоря прогона `glossary · GlossaryConfiguration · eddi://ai.labs.glossary · export · import`; `import` — ключевое слово java, назвал 83 входа из 84 (`pending.json`: «Якоря выбрали 83 срезов — 719 КБ») |
| **оценка кандидата включала клетки ВСЕХ помеченных сирот** → сироты набираются в бюджет и ограничены потолком | все 12 кандидатов вопроса стоили 685–689 КБ при конусах 34–69 узлов: ни один ответ не менял итог |
| **рельса вопроса целиком** (B9 сжался до одного вызова, снялись `FOCUS_QUESTION`, `ASK_CANDIDATES`, `refused`, ветка `ask` в `ext`) | решение оператора «машина выбирает сама». Дефект оценки её НЕ убивал — с починенным правилом якоря вопрос был бы из двух кандидатов |
| `surface` = путь + имена `api`/`decl` | проверено на живом дереве: даёт тот же выбор, что один путь. Код без замера снят |
| `dropped.bytes` | никем не потреблялся |

Починка проверена теми же якорями на том же дереве: **2 конуса из 84, 12 клеток из 283, 108 файлов
≈ 43 КБ, не влезло 0** — выбраны `IRestImportService` и `IRestExportService`.

Артефакты прогона заморожены: `sandbox/runbox/b11-first-attempt/`.

## Что сняла критика — второй прогон, по КОДУ полосы

Первый критик судил концепт; второй читал `workflows/izi.js`, `ext/index.mjs` и `steps/*` и мерил
план ими. Снято и слито:

| снято / слито | почему |
|---|---|
| адрес узла в карте: `<slice id …>` и `slice="s1 s4"` | машинного потребителя ноль — `parseMap`, `newRipple`, `newPlanIndex` его не читают; обоснование было про порядок чтения РОЛЬЮ, а это `order.tpl`, а не байты в файле с потолком 115 КБ. Замер «157 из 385» остаётся: он говорит форму атрибута, когда потребитель появится |
| требование «id среза не ездит между прогонами» | исчезло вместе с адресом: id живёт один прогон, порядок нужен только переспросу |
| `items[]` в возврате `focus` | поле уже занято смыслом «вопросы пакета»: `askOperator` ждёт ответ на каждый элемент, шаг умер бы `err("question")` |
| B2 отдельным коммитом | коммит «константа, которую никто не вызывает» — только строка в журнале; едет с потребителем |
| B7 и B8 двумя коммитами | между ними полоса КРАСНАЯ: `buildGraph` читает части по плану |
| закрытие триггера 6 вместе с планом | бухгалтерия впереди наблюдения; триггеры пишутся по фактам B10/B11 |

Добавлено тем же прогоном: `readFocus` одним парсером · `marked` из `files[].subjects` вместо имён
якорей · узлы из плана, а не из computed · `ASK_CANDIDATES` · `charge()` в фазе · `found="outside"` ·
антецедент `newGraph` · замер Б/узел в B11.

**Отвергнутое предложение второго критика — снять рельсу вопроса целиком** (в v1 перебор потолка =
`err("blocked")` с перечнем кандидатов, оператор правит якоря и перезапускает). Довод против —
арифметика самого замера: типовой набор якорей даёт 132 КБ при потолке 115, то есть рельса
срабатывает НЕ гипотетически, а на первом же живом прогоне eddi (B11), ради которого весь срез и
затевался. Без неё B11 кончается `blocked`, и полоса не доходит туда, где вставала. Цена рельсы
при этом сбита втрое: константный стем, `evidence` вместо сборки текста, `charge()`, потолок списка
— всё это правки, а не новые сущности.

**Отвергнутое предложение первого критика — считать фокус внутри функции хоста `survey`, без нового шага.**
Довод разобран в §4 концепта: замер §2b показал, что вопрос оператору нужен на ТИПОВОМ наборе якорей
(132 КБ выше потолка), а рельса вопроса живёт в программе — значит нужен шаг. Плюс шаг 3 утверждает
покрытие, шаг 3b выбирает: сложив их, инвариант покрытия становится нечем проверять.
