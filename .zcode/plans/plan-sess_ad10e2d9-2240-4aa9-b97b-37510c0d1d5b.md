1. СТРУКТУРА (ветка workflow-solo, паттерн step9-rework — «шаг = папка: промпты + скрипты»):
   steps/plan/        — planner.md (роль), order-plan.tpl (наряд: спека+TASK+PREVIOUS+FEEDBACK), judge.ts (судья шести разделов: цитаты-подстроки, пути существуют/образец, источники), plan.step.ts (голова: next/fold), *.test.ts, component/
   steps/plan-check/  — critic.md (роль-критик), questions.ts (извлечение открытых вопросов раздела 6; ВПИСЫВАНИЕ ответов оператора в план: строке вопроса дописывается «→ РЕШЕНО: <ответ>»), card.ts (синтез плана + ссылка), plan-check.step.ts (голова: критик → вопросы в чат → ответы в план → карточка → checkpoint), тесты
   steps/execute/     — dev.md (роль), judges.ts (a: Ф↔коммит; b: тесты только расширены, lostLines-токены; c: гарантии §5), execute.step.ts, тесты
   ext/ — TypeScript (pi грузит .ts через jiti; node 26 исполняет TS для тестов): index.ts (регистрация), engine.ts (soloStart/soloNext/soloFold — читаемый станционный цикл), ask.ts (вопрос В ЧАТ + ожидание), answers.ts/result.ts (из истории, грамматика обменов), registry.ts (STEPS=['plan','plan-check','execute'], ROLES, MODULES id→голова)
   prompts/solo.md — inline JS-скрипт (сандбокс хоста — только JS): простой ROP-цикл по глаголам role/ask/checkpoint/say/done

2. ВОПРОСЫ ОПЕРАТОРУ ИЗ ЧАТА (шаблон step9-rework: pending.json + izi_answer):
   - ask.ts: вопрос → .agent/pending.json (номера+тексты) → pi.sendMessage(followUp, display) — вопрос ВИДЕН В ЧАТЕ с инструкцией «ответь сообщением по номерам»; параллельно файловый фолбэк question.txt/answer.txt (T60)
   - новый инструмент solo_answer (аналог izi_answer): чат-модель зовёт его с ответом оператора; сверка по НОМЕРАМ против pending.json; пишет answers.md exchange-грамматикой; возвращает таблицу «вопрос → ответ» для показа оператору
   - поллинг answers.md в ask; таймаут → ПЕРЕСПРОС под новым именем (фикс дырки «пустой ответ = reject»), не отвержение
   - ПОДТВЕРЖДЕНИЕ плана = checkpoint хоста: модалка Approve/Reject В ПАНЕЛИ pi (из чата); Reject → переспрос причины через тот же чат-канал → FEEDBACK в plan

3. ПОСЛЕДОВАТЕЛЬНОСТЬ plan-check (по требованию):
   критик APPROVE → открытые вопросы раздела 6 → В ЧАТ (с рекомендациями, по номерам) → оператор отвечает в чате → solo_answer кладёт на диск → questions.ts ВПИСЫВАЕТ решения в PLAN.md → карточка в чат: ссылка на план + синтез (N требований · N строк/файлов · сценарии · величины · гарантии) → checkpoint «запускаем execute?» → Approve → execute (dev по строкам Ф, судьи a/b/c) → done-карточка.

4. ТЕСТЫ: юниты судей/вопросов/карточки рядом (*.test.ts), компонентные на каждую голову (component/, мок-события), шов реестра ROLES (объявленное на диске есть); node --test зелёный целиком (Node 26 strip-types; без enum/декораторов — простой TS).

5. КОММИТЫ по волнам: (а) остановка+структура+TS-скелет, (б) ask-из-чата+solo_answer, (в) plan-check целиком (вопросы→план→карточка→checkpoint), (г) execute+тесты, (д) живой перезапуск proof на quarkus-solo-test (пауза видна в чате; ответы вписаны в план; подтверждение модалкой) — приёмка с оператором.
