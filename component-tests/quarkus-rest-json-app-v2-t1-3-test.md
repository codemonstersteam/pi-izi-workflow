## Оценка: это много

**Времени и токенов на такую задачу — МНОГО, и вот почему:**

1. **Задача тривиальная** (3 строки заказа, репозиторий из нескольких файлов, один новый
   endpoint в одном файле), а конвейер прогнал её через полную механику: 15 вызовов LLM,
   ~203k биллинговых токенов, ~45 мин. Синьор сделал бы это в 20 строк кода за минуты.
2. **Главный множитель — прогонarchitecture-ная, а не размер задачи.** intake сделал 9 вызовов
   (6 пластов + вопрос + починка + критик) на артефакт в 2 КБ; каждый пласт несёт весь
   накопительный артефакт и форму роли — отсюда 701k cached: кэш честно съедает повторы, но
   арматура платит фиксированную цену независимо от размера заказа.
3. **Аномалия data-failures — 23 мин** на пласт, который на eddi занимал минуты: сеть уже
   деградировала перед отказом (провайдер умер в 18:47, а этот вызов шёл 18:22–18:45).
   Без него чистое время 22 мин — уже сопоставимо с осмысленным.
4. **xhigh thinking** на qwen3.8-max удлиняет каждый вызов; для сценариев-владельцев-
   контрактов на задаче такого размера хватило бы low.

**Что нормально:** цена детерминизма. Гардрейлы поймали реальный спор владельцев (Fruit vs
FruitResource — правильный вопрос!), RTM-суд направил починку, критик продвинул файл только
после полного суда. На большой задаче (eddi: 1854 файла, 16 требований) та же механика стоит
тех же ~200k токенов — там она окупается; на микрозадаче — нет.

**Рекомендации:** (1) T72 — разрезы вывода (критик пишет только вердикт, слои — файлами):
минус 4-6× вывода на каждом накопительном пласте; (2) thinking=low для простых пластов
(scenarios/contracts/coverage на маленьких нарядах); (3) подумать о маршруте «маленькая
задача» — repo < N файлов и требований < M → прогон intake одним вызовом с тем же судом.
