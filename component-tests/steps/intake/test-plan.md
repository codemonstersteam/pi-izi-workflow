# Ручная приёмка шага 6 (intake v2): план

Что здесь: порядок ручной проверки шести подшагов шага 6 на настоящей задаче eddi (DOS-535).
intake v2 — прожарка над двусторонней матрицей трассируемости, подшаги с говорящими именами.
Проверяет ОПЕРАТОР глазами. Устройство шага — `steps/intake/data-flow.md`.

**Правило приёмки.** Подшаг закрывает оператор, не зелёный тест. Расхождение живого ответа с
эталоном (`etalon-eddi/expected.md`) разбирается ВМЕСТЕ; чинить молча запрещено.

---

## Раскладка каталога подшага

`component-tests/steps/intake/<n>-<имя>/`

```
in/                    ВСЁ, ЧТО УШЛО В ПОДШАГ (входы с диска)
  <входные файлы>      что подшаг читает — байт в байт как в живом прогоне
  order.<имя>.md       наряд ЦЕЛИКОМ (из state.json живого прогона)
out/                   файлы, которые подшаг написал
  frd~<имя>.xml        артефакт подшага (слой, дописанный к предыдущим)
  <машинные выходы>    rtm.md, intake-b0.json — что положил скрипт
meta.json              вердикт, круги, цена
```

Наряд лежит во ВХОДЕ — это user-сообщение, ушедшее в модель. Форма роли (system) — в
`steps/intake/intake.md`. Ответ модели — сам артефакт (модель пишет staging инструментом
write). `request.json` не лежит: живой прогон шёл через хост, не через `bin/ask.mjs`.

## Подшаг 1 — `1-scenarios` (требование → use cases)

```
вход     in/TASK.md (заказ, 15 решений) · in/brd.md (R1-R16 + аналог) · in/answers.md
наряд    order.scenarios.md ~18К
роль     intake, модель execution → qwen3.6-27b
выход    out/frd~scenarios.xml — use cases, актёры, шаги, ветки отказов
суд      F1 (актёр/гарантия/шаги) · F6c (разные концы)
цена     один вызов ~90 с
```

**Что смотрит оператор:** каждое R имеет use case; ветки отказов различны; решения оператора
(TTL=Caffeine, merge по URI, ID генерирует система) видны в шагах; `error="none"` на всех
`<ext>` — data-failures даст им коды.

## Подшаг 2 — `2-owners` (каждое требование → модуль-владелец)

```
вход     in/brd.md · in/answers.md (решения о владельцах) · in/appgraph.xml (карта)
         in/graph-computed.xml (типы + рёбра) · in/anchors.json (файлы аналога)
скрипт   ДО роли:   b0Of → intake-b0.json (кандидаты: шаг×карта, IDF, via-edge, спорность)
                   + blueprintOf (чертёж ядра аналога) + skeleton rtm.md
         ПОСЛЕ роли: writeRtmFromArtifact → rtm.md (матрица, СКРИПТОМ)
наряд    order.owners.md ~35К: {CANDIDATES} топ-4/шаг + {BLUEPRINT} + {TYPES} + {ANALOGUE}
         + two-filter триаж + леджер допущений
выход    out/frd~owners.xml (owner-строки) · out/rtm.md (матрица) · out/intake-b0.json
суд      F17a (шаг без владельца/вопроса) · F17b (узел существует) · F17c (спорный→вопрос)
         F17d (функция аналога унаследована)
цена     один вызов ~4 мин
```

**Что смотрит оператор:** все шаги закрыты; новые файлы несут after= (образец из чертежа);
споры уведены вопросами с поимёнными кандидатами.

```
вход     staging/frd~owners.xml (предыдущий слой) · appgraph.xml (срез ролей/api)
наряд    order.contracts.tpl ~15К: {OWNERS} машиной + {MAPSLICE} + {DELTA_FORMS}
выход    frd~contracts.xml: + <delta> <scenario> <touched>
суд      F2/F3/F4/F7/F10/F14/F17e

```

**Что смотрит оператор:** каждый владелец имеет дельту; сценарии проходят через узлы;
`Added` на существующем файле — законно (рост контракта), дерево переведёт в `Changed`.

с реальными статусами; ветки `<ext>` получили `error="CODE"`.

## Подшаг 5 — `5-coverage` (carried + двусторонний суд матрицы)

```
вход     staging/frd~data-failures.xml · brd.md (R-id) · rtm.md · answers.md
         anchors.json · appgraph.xml · graph-computed.xml
скрипт   rtmJudge: forward (R без владельца; exemption для define/set/name)
         + backward: зеркало слоя, точка вызова, кластер (ДЕДУП по файлу), ответ назвал
наряд    order.coverage.tpl: {OWED} список R-id
выход    frd~coverage.xml: + <carried req by>
суд      F11 (разность списков) · F8 + rtmJudge
маршрут  rtm:-блокеры → owners (FEEDBACK), coverage повторяет суд
цена     один вызов + круги owners-починки при rtm-блокерах
```

**Что смотрит оператор:** каждая R-строка матрицы заполнена или закрыта вопросом; колонки без
строки-обоснования названы; carried-строки на каждое R.

## Подшаг 6 — `6-critic` (исполнимость, ≤3 блокеров)

```
вход     staging/frd~coverage.xml (весь артефакт) · answers.md
наряд    order.critic.tpl: рубрика 4 пункта (плейсхолдеры, образец, ответы, полнота)
выход    frd~critic.xml: + <critique verdict>  → promote → .agent/frd.xml
суд      Полный суд всех правил + зелёный критик → promote
цена     один вызов
```

**Что смотрит оператор:** вердикт APPROVE; если REJECT — ≤3 блокеров с номером рубрики и
элементом; каждый ответ оператора потрачен (виден в артефакте).

## Что НЕ проверяется этим планом

- Юниты и компонентные тесты — линия `node --test` зелёная перед прогоном.
- Живой pi с чат-моделью — прогон идёт headless-раннером (`bin/run.mjs`).
- Вес/рябь/дерево — станции после intake, по отдельному решению оператора.
