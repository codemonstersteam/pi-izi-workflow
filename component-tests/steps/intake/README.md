# Приёмка шага 6 (intake v2): план

Что здесь: порядок ручной проверки подшагов шага 6 на живой задаче eddi (DOS-535), int**ake v2** —
прожарка над двусторонней матрицей трассируемости (`rtm.mjs`), подшаги с говорящими именами
(`scenarios → owners → contracts → data-failures → coverage → critic`).

**Правило приёмки** — то же, что у шага 2: подшаг закрывает оператор; расхождение с эталоном
разбирается ВМЕСТЕ; чинить молча запрещено. Конвейер репозиторно-общий — eddi-имена живут только
здесь и в `etalon-eddi/`.

---

## Раскладка каталога подшага

`component-tests/steps/intake/<n>-<имя>/`

```
in/                    ВСЁ, ЧТО УШЛО В ПОДШАГ (входы с диска + наряд целиком)
  <входные файлы>      что подшаг читает — байт в байт как в живом прогоне
  order.<имя>.md       наряд ЦЕЛИКОМ, собранный кодом подшага (из state.json живого прогона)
out/                   файлы, которые подшаг написал
  frd~<имя>.xml        артефакт подшага (стaging, слой за слоем)
  <машинные выходы>    rtm.md, intake-b0.json — что положил скрипт
```

Наряд лежит во ВХОДЕ: это user-сообщение, ушедшее в модель. Форма роли (system) — в
`steps/intake/intake.md`. Ответ модели — сам артефакт (модель пишет инструментом write прямо
в staging). `request.<роль>.json` здесь НЕ лежит: живой прогон шёл через хост, а не через
`bin/ask.mjs`; при возобновлении приёмки через ask — положить рядом, как у шага 2.

## Подшаг 1 — `1-scenarios` (требования → use cases)

```
вход     in/TASK.md (заказ, 15 решений оператора) · in/brd.md (R1–R16 + аналог) ·
         in/answers.md (ответы оператора)
наряд    order.scenarios.md — 17 779 симв (живой прогон 25.08, state.json)
роль     intake (steps/intake/intake.md), модель execution → qwen3.6-27b
выход    out/frd~scenarios.xml — 9 use case'ов (CRUD×5 + подстановка + экспорт + импорт +
         привязка), given/when/then, <ext>-ветки отказов
суд      checkFrd pass="scenarios": F1 (актёр/гарантия/шаги), F6c (разные концы) — зелёный
опорная цена  один вызов ~90 с
```

**Что смотрит оператор:** каждое требование R1–R16 имеет use case; ветки отказов различны;
решения оператора (TTL=Caffeine, merge по URI, ID генерирует система) видны в шагах.

## Подшаг 2 — `2-owners` (каждое требование → модуль-владелец)

```
вход     in/brd.md · in/answers.md (ваши 5 ответов о владельцах) · in/appgraph.xml (карта:
         модули+роли+api) · in/graph-computed.xml (типы+рёбра) · in/anchors.json (файлы аналога)
наряд    order.owners.md — 34 862 симв: кандидаты b0 (топ-4 на шаг, via-edge) + ЧЕРТЁЖ ядра
         аналога + ТИПЫ таблицей + ОТВЕТЫ оператора + two-filter триаж + леджер допущений
скрипт   до модели: b0Of — кандидатная таблица (шаг×карта, IDF-фильтр, рёбра, спорность);
         кладёт .agent/intake-b0.json (НАРЯД И СУД ЧИТАЮТ ОДНУ ТАБЛИЦУ)
         после модели: writeRtmFromArtifact — СКРИПТ собирает rtm.md из owner-строк артефакта
         (модель форму роли с одним write не может писать два файла — живой круг 25.08)
выход    out/frd~owners.xml — 24 owner-строки (владелец на каждый шаг UC, new="yes" с after=)
         out/intake-b0.json — кандидатная таблица скрипта
         out/rtm.md — матрица трассируемости (строки R1–R16, 15/16 заполнены)
суд      F17a (шаг без владельца/вопроса) · F17b (узел существует) · F17c (спорный → вопрос
         или ответ) · F17d (функция аналога унаследована) — ЗЕЛЁНЫЙ
         backward-судья (rtmJudge, на coverage): forward R15 + backward-вызов (конвертер!) +
         backward-кластер (синк-четвёрка) + backward-ответ (AgentConfiguration/RestAgentStore) —
         27 блокеров, все — реальные находки, НЕ ложные
опорная цена  один вызов ~4 мин (наряд ~35К)
```

**Что смотрит оператор:** все шаги закрыты; новые файлы несут after= (образец); споры уведены
вопросами; backward-судья назвал точку вызова и кластер — это пойдёт FEEDBACK'ом на починку.

## Что НЕ проверяется этим планом

- Юниты и компонентные тесты — линия `node --test` зелёная перед прогоном, пересказа нет.
- Живой pi с чат-моделью — прогон идёт headless-раннером (`bin/run.mjs`).
- Веса/рябь/дерево — станции после intake, по отдельному решению оператора.
