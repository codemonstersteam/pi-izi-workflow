## Первопричина долготы — четыре, в порядке вклада

**1. Хвост распределения скаутов — главный вклад.** Сумма работ роя 13 740 с на 24 вызовах, но
распределение тяжёлое: 18 вызовов по 74–416 с (медиана ≈ 360 с), а **шесть вызовов длиннее 900 с**
(943, 1153, 1226, 1466, 1506 и **2 473 с**) дают 8 767 с — 64% всей работы роя. Причина этих шести —
многокруговое чтение: наряд разрешает «open the file when the digest genuinely does not tell», и
слабая модель ходит к файлам снова и снова, каждое `read` — отдельный раунд модели с полным
контекстом (вход ≈ 65 тыс. токенов на вызов — это вход НА РАУНД, а не на клетку).

**2. Конвой пачки — ×2,2 поверх хвоста.** `parallel` = `Promise.all`: пачка из восьми мест ждёт
самого медленного. Сумма работ 13 740 с при восьми местах — идеальная упаковка ≈ 1 717 с (29 мин
не понадобится уже потому, что пачек всего шесть); фактическая полоса роя ≈ 3 800 с. Каждая пачка
стояла 15–40 минут из-за одного места, пока семь её соседей давно закончили.

**3. 45 клеток при сути задачи в ~9.** Фокус купил лишнее (разбор ниже): 7 клеток документации
и ~15 тестовых, включая микро-клетки одиночных тестовых файлов. Каждая лишняя клетка — это вызов
в 60 тыс. входных токенов и место в пачке.

**4. Spine сжёг 3 круга на разладе P8 с нарядом.** Скаут трижды писал `<suite match="*Test.java"
path="src/test/java">`, гардрейл трижды отвечал «matches no file under path» — семантика `match`
(шаблон ИМЕНИ файла) в правиле и в примере наряда читается по-разному. Это ~3 вызова и ожидание
места в трёх пачках.

## Оптимизация алгоритма — что даёт intake всё необходимое дешевле

Intake нужны не «все файлы, где встречается якорь», а: образец-паттерн, точки интеграции, spine.
Из проработки (`eddi-by-zai.md`) это фокус из ~10 клеток. Предложения по убыванию эффекта:

1. **Малым клеткам — текст файлов в наряде.** Клетка ≤ 3 файлов и ≤ 30 КБ: наряд несёт СОДЕРЖИМОЕ
   файлов, а не digest — один вызов, ноль read-раундов. Это убивает хвост 900–2 473 с (причина 1):
   микро-клетки — как раз малые, и именно они давали длинные конвои чтения.
2. **Фокус не покупает доки-клетки и микро-клетки тестов.** Тестовый файл приходит в часть дом-клетки
   (`<test path>`), сьют — из spine; доки не несут кода для планирования. Снимает ~22 клетки.
3. **Предел раундов чтения на скаута** (например, 6): сверх — обрыв связи, круг не тратится
   (механика уже есть в fold). Страховка от хвоста на больших клетках.
4. **Согласовать P8 с нарядом** одним фиксом: `match` — шаблон ИМЕНИ файла (`*Test.java`), пример в
   наряде показывает совпадение с файлом под `path`. Снимает 3 круга spine.
5. **Кэш оставить как есть** — он уже делает повторный прогон почти бесплатным (45 клеток — 24
   вызова; после правки файлов пересчитается ровно одна клетка).

Оценка: 45 → ~10–12 клеток, из них большинство малые (п.1): рою нужно 2 пачки по ~8 мест без
read-раундов ≈ 60–90 с на место → **~8–12 минут вместо 66**, токены ~×4–5 меньше. Это та же
информация для intake: образцы, интеграции, spine — ср. `eddi-by-zai.md`, где план закрыт чтением
~15 файлов без всякого роя.
