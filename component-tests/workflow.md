# Data flow полосы: что во что превращается

Что здесь: путь одного требования от сырой задачи до тикетов — на каждом шаге вход, выход, кто
работает (скрипт или роль) и чем судится результат. Подробно разложены **шаг 1** (разобран с
оператором 22.08.2026, доказан компонентным тестом) и **шаг 9** (переписан 21.08.2026); остальные
шаги названы тем, что они дают следующему.

**Обозначения.**

| знак | что значит |
|---|---|
| 🟢 | работает от старого: живые прогоны его прошли, в переделке не участвовал |
| 🟡 | разобрали с оператором в ручном режиме |
| 🚧 | после переделки подробно НЕ смотрели: либо переписан вход, либо вживую не гонялся ни разу |
| 🤖 | роль и наряд написаны машиной и по-русски — через руки оператора не проходили |
| ✍️ | оператор проработал роль вручную и перевёл на английский (`standards/role.md`, ограничение 5) |
| ✅ | **разобран с оператором и доказан компонентным тестом**: сценарии по формуле, фикстуры на диске, шов формулы зелен |

Правило, вокруг которого построено всё: **скрипт считает то, что вычислимо, роль решает то, что
вычислить нельзя, гардрейл сверяет объявленное.** Ни одна проверка не решает, как должно быть: она
говорит «ты объявил X, а Y его не знает» и называет обе стороны.

## ✅ Шаг 1 — ключ задачи

Разобран с оператором 22.08.2026 и доказан компонентным тестом:
[`steps/task/component/task.component.test.mjs`](../steps/task/component/task.component.test.mjs).
Тест — **единственное** описание поведения шага: таблица `SCENARIOS` внутри него читается человеком
(`node steps/task/component/task.component.test.mjs` печатает её Gherkin'ом) и исполняется машиной.
Второго документа с тем же содержанием нет намеренно: он разъехался бы с первым молча.

```
вход     TASK.md — сырая задача от оператора
         .agent/answers.md — ответы оператора, если ключ пришлось спросить
скрипт   inputs: файл существует; judge: непуст ПО СЛОВАМ и ≤ 300 строк (одна задача — один вход);
         cut: ключ ОБЪЯВЛЕН строкой `task: DOS-535`, а не выискивается по тексту
роль     нет — шаг целиком скрипт, 0 токенов; каталога ролей у него нет, позвать модель нечем
наряд    нет
выход    state.key · state.at.task (путь И отпечаток) · вердикт шага
гардрейл вход: класс `no-task` — файла нет; `empty` — молчание не является требованием;
         `too-long` — 306 строк при пределе 300, это пачка задач
         выход: форма ключа `^[A-Z]{2,20}-[0-9]{1,6}$`; отпечаток входа лёг — по нему шаги 2+
         узнают, что TASK.md не правили
цена     0 токенов
```

**Внешних сторон две, и модели среди них нет: файловая система и ОПЕРАТОР.** Оператор приходит через
`ask`/`checkpoint` — это человек, не роль: токенов не тратит, возвращает `approved`, а сам ответ
кладёт на диск. Поэтому у шага без роли всё равно есть рельса вопроса, и у неё свои ветви.

**Почему ключ спрашивается здесь, в первом же шаге.** Им зовутся ветка, тикет и каталог плана,
которые полоса создаёт много позже. Один вопрос на старте дешевле прерывания посередине.

### Сценарии: формула, которая исполняется

`N = 1 (штатное) + Σ (различимых ветвей в адаптере)` — по статье «Мифология тестирования:
компонентные тесты». Адаптера два, ветвей пять, сценариев шесть:

| # | ветвь | сценарий |
|---|---|---|
| 1 | штатное | ключ объявлен в задаче → ключ и отпечаток легли, модель не звалась |
| 2 | `no-task` | `TASK.md` нет вовсе → отказ называет ИМЯ файла и того, кто его кладёт |
| 3 | `empty` | `TASK.md` из одних пробелов → отказ «молчание не является требованием» |
| 4 | `too-long` | `TASK.md` длиннее предела → отказ называет ПРЕДЕЛ, ключ не лёг |
| 5 | `ask` | ключа нет нигде → шаг СПРАШИВАЕТ оператора, а не выдумывает |
| 6 | `re-ask` | ответили не ключом → переспрос под НОВЫМ именем паузы |

Состав таблицы — не дисциплина автора: последний тест файла собирает классы отказа **из кода**
подмодулей шага и сверяет с таблицей в обе стороны. Ветвь без сценария — красный тест; сценарий,
называющий класс, которого в коде нет, — тоже.

**Что этот шестой сценарий стоил.** Его в тесте не было, пока формула его не потребовала, — и он
сразу нашёл дефект: переспрос уходил под ТЕМ ЖЕ именем паузы. Хост ключует паузу по имени, значит
два хода под одним именем это ОДНА пауза: второго вопроса оператор не увидел бы никогда, а шаг
считал бы круги переспросов, которых для человека не было. Тот же дефект однажды стоил живого
прогона `46edab60`; здесь он был воспроизведён в новом коде и пойман до прогона.

### Фикстуры — каталоги на диске

`steps/task/component/fixture/{good,missing,empty,too-long,no-key,bad-key}/` — по каталогу на
сценарий, как у `pinout-openapi/component-tests`. Не строки в коде: каталог можно подмонтировать в
контейнер и прочитать глазами. У `missing/` содержание — само отсутствие `TASK.md`, и там лежит
README, объясняющий это: git не хранит пустых каталогов, и после клона тест упал бы на своём стенде,
а не на шаге.

## 🟡 Шаг 9 — четыре подшага

Два отношения, и они не выводятся друг из друга. `needs` («без чего меня не написать») даёт ПОРЯДОК
работ и ацикличен по построению. Поток («что происходит с данными») даёт ПОКРЫТИЕ и цикличен по
природе: запрос идёт вниз по слоям, ответ поднимается вверх. Три попытки вывести порядок из потока
дали круг на 11 из 12 модулей — измерено, `docs/plan.md` §0.

### 🟡 9A — словарь границы

```
вход     frd.xml · ripple.xml
скрипт   valuesSkeleton: строка на каждый конец use case и на каждый <api>/<decl> изменения;
         `closes` и уже известные тексты вписаны
роль     valuer 🤖 — заполняет пустые `text=""`, и только их
наряд    steps/plan/values/order-values.tpl
         слоты: SKELETON · FRD · PREVIOUS · FEEDBACK · BLANK · STAGING · CHECK
выход    values.xml
гардрейл checkValues: состав скелета не тронут, пустых не осталось
цена     0 токенов, если словарь зелен СЕЙЧАС — переиспользуется без роли
```

Словарь отвечает только за значения ГРАНИЦЫ: адреса, статусы, коды отказов, сущности требования.
Данные, живущие внутри изменения, объявляются в потоках и там же судятся.

### 🟡 9B — дерево модулей, порциями по четыре

```
вход     frd.xml (дельты ∪ узлы сценариев) · ripple.xml · appgraph.xml · файлы-образцы
скрипт   treeSkeleton: <module> на каждый модуль работы; вписаны path, delta, кандидаты в
         образцы и <facts> из ряби. Режется на порции по 4 модуля
         twin: на каждый модуль порции — ДВЕ выжимки кандидатов: объявление типа с
         extends/implements, аннотации, поля, сигнатуры, каждая с НОМЕРОМ строки
         neighbours: что уже решено в соседних порциях — их типы и объявления
роль     tree-designer ✍️ — на каждый модуль шесть полей: io · hides · owns · twin · needs · contract
наряд    steps/plan/tree/order-tree.tpl — 3 наряда, 78 699 симв (последовательно: соседи
         читают уже написанное)
         слоты: SKELETON (порция) · TWIN (выжимки двух кандидатов на модуль, с номерами строк) ·
                NEIGHBOURS (что решено в соседних порциях) · MINE (пути своих модулей) ·
                FRD — СУЖЕННЫЙ: дельты этой порции и её use case, плюс общие ограничения ·
                PREVIOUS · FEEDBACK · STAGING · CHECK
выход    tree.xml
гардрейл порция: раздел на каждый модуль, чужих нет, `needs` это ПУТЬ, контракт непуст
         целое:  состав = дельты ∪ узлы сценариев · один владелец типа · одно написание имени ·
                 `needs` АЦИКЛИЧЕН
```

Роль вправе дочитать образец `read(offset: номер минус 2, limit: 12)`, до восьми чтений на порцию.
Чтение целиком запрещено: тело близнеца — это 35 КБ из 55 КБ наряда, измерено первым прогоном.

### 🟡 9C — потоки, порция = один use case

```
вход     frd.xml (шаги, ветвления, отказы) · tree.xml
скрипт   flowsSkeleton: <flow> на use case и на каждое ветвление; `closes` проставлен СКРИПТОМ —
         номер шага это цитата требования, и роль однажды набрала «2а» кириллицей вместо «2a»
роль     flow-designer 🤖 — на каждую строку: модуль · вход · выход · роль шага
наряд    steps/plan/flows/order-flow.tpl — 7 нарядов, 141 046 симв, пишутся ОДНОВРЕМЕННО
         слоты: SKELETON (поток одного use case) · UC ·
                TREE — СУЖЕННОЕ: модули этого use case целиком, их `needs` одной строкой ·
                FRD — СУЖЕННЫЙ: этот use case плюс общие ограничения ·
                PREVIOUS · FEEDBACK · STAGING · CHECK
выход    flows.xml
гардрейл порция: все шаги и ветвления ЭТОГО use case закрыты, модуль назван деревом,
                 роль шага из словаря (порождаю · проношу · отвергаю)
         целое:  у значения ОДИН порождающий модуль · вход порождён либо внешний ·
                 каждый отказ порождён и доехал до статуса · модуль дерева работает в потоке
                 ЛИБО достижим по `needs` от того, кто работает
```

Последнее правило написано так намеренно: у модели данных и у интерфейса нет поведения в рантайме —
за них работает реализация. Спрашивать с объявления поведение — ошибка, которую первая версия
проверки уже сделала.

### 🟡 9D — план, скриптом и без токенов

```
вход     tree.xml · flows.xml · frd.xml · decisions.md
роль     нет — 9D роль не зовёт вовсе, и наряда у него нет
скрипт   planbook: TL;DR для человека · общие ограничения ДОСЛОВНО из требования ·
         волны из `needs` · раздел на модуль (что прячет, объявление, что закрывает, отказы) ·
         карта отказов · журнал решений
выход    task/<КЛЮЧ>/PLAN.md
гардрейл каждый модуль в плане · каждая величина `fit` дословно · каждый код отказа ·
         ни одной заглушки (TBD, TODO, «по аналогии»); отказ СНОСИТ прежний план
```

План не содержит решений, которых нет в дереве и потоках: он их индексирует. Поэтому он ничего не
стоит и терять при пересборке нечего.

### Цена шага и почему она такая

```
                 наряды      симв        замер 21.08.2026
9B  дерево        3          78 699      последовательно: порция читает соседей
9C  потоки        7         141 046      ОДНОВРЕМЕННО: use case независимы
──────────────────────────────────────────────────────────
вход шага 9      10         219 745 ≈ 63K токенов
скрипты                     0 токенов: скелеты, выжимки, 12 сверок, сборка плана
```

Было 327 812 символов (94K токенов), из них 77% — одно и то же требование и одно и то же дерево,
разосланные по десяти нарядам. Три правки, каждая со своей границей:

- **требование сужается** до дельт порции и её use case; общие ограничения (поля, отказы, величины)
  едут ВСЕГДА — без них роль выдумает своё число;
- **дерево сужается двумя кругами**: модули этого use case целиком, их `needs` одной строкой. Полное
  замыкание съедало выигрыш — 16 063 → 13 094, то есть почти ничего;
- **параллель только там, где порции независимы.** Потоки — да. Порции ДЕРЕВА — нет: каждая читает
  блок NEIGHBOURS, то есть решения соседних, и параллель отдала бы им пустой блок.

Один вызов роли на этом шаге — 4-9 минут. Семь потоков подряд это час, семь разом — те же 4-9 минут;
экономия здесь не в токенах, а в минутах, а минуты одними токенами не купить.

### Круг починки, общий для 9B и 9C

```
порция красная  → переписывается ТА ЖЕ порция с блокером; соседние не трогаются
целое красное   → адресат по ПУТЯМ в блокере; блокер без путей адресата не имеет,
                  и тогда переписываются ВСЕ порции — незнакомая находка едет дороже
зелёная порция  → не переписывается, КРОМЕ случая, когда она адресат
бюджет          → 5 кругов; та же жалоба дважды — дефект ТЕКСТА блокера, а не роли
вопрос роли     → рельса: ответ оператора уезжает в decisions.md и переживает пересборку
```

### Молчание требования

```
ответ есть у образца или соседа   → роль решает сама и называет источник
ответ противоречит требованию     → выигрывает требование, вопрос оператору
ответ ШИРЕ требования             → делай и скажи об этом строкой
решение НЕОБРАТИМО                → вопрос оператору ДАЖЕ при готовом дефолте:
                                    форма хранимых данных · публичная поверхность ·
                                    внешняя зависимость
```
