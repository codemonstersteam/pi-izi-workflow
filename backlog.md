## Наряд D34 · проход B: цепочки, гардрейл, сборка

**Форма бланка.** Роль пишет ОДНУ цепочку на сценарий; `in`/`out` узлов, `<dep>` и поток выводит
скрипт.

```
скелет:  <route scenario="S2" uc="UC2" entry="v4" nodes="…" ends="UC2/post=v5 UC2/2a=v6" steps=""/>
роль:    steps="…/fruits.html@v1 -> …/FruitResource.java@v2 -> …/fruits.html@v5"
```

**Почему не контракты.** На единственной сохранившейся готовой поставке (`t3`) все 5 входных
альтернатив восстанавливаются из чужих `out` и входов сценариев — 3 дословно, 2 как `closes="UCx/in"`.
Значит `in` роль писать не должна, и правило «`out(k) ∈ in(k+1)`» — самое дорогое правило старой
конструкции — исчезает построением. Предзаполнять `in` по `src` тоже нельзя: в готовой поставке `t3`
из 7 значений с `src` не использовано ни одного.

**Обязательств роли** — 12 на `eddi` (по числу сценариев), 2 на `t2`. Для сравнения: проход A с 24
бланками прошёл с первой попытки, старый проход A со 145 обязательствами не проходил никогда.

**Гардрейл — 4 правила.**
1. каждый `path` — узел ширины изменения, каждый `@vN` — id словаря;
2. первый шаг отдаёт `entry` своего сценария;
3. каждый конец use case отдан каким-то шагом маршрутов этого use case;
4. прямые участки цепочек ∪ рёбра карты не замыкают круг (`forwardLegs`; иначе шаг 10 падает
   `err("cycle")` без рельсы починки — прогон `f7bf154a`).

Снято как невозможное при цепочечной форме: «значение в `in` двух узлов», «непустой `dod`».

**Сборка на зелёном, 0 токенов**: `in`/`out` из цепочек, `<dep>` = рёбра ряби ∪ прямые участки,
`data-flow.md` = те же шаги по сценарию и по узлу.

**Файлы.** Новые: `steps/design/routes.mjs`, `routes.test.mjs`, `steps/design/router.md`
(переписать из `docs/attic/`), `order-routes.tpl`. Правки: `steps/design/design.mjs` (сборка),
`ext/index.mjs::design`, `workflows/izi.js::designing` — снять останов полосы.

**Приёмка.**

2. Живой прогон `t2`: `.agent/design-graph.xml` и `.agent/data-flow.md` собраны, полоса доходит до

## Наряд D35 · шаг 6 `intake`: класс без полей в FRD не пишется

Формулировка оператора, 17 авг: «нельзя в FRD писать классы без полей; каждое поле класса должно
иметь чёткий диапазон значений, а не просто тип».

**Факты живого прогона `eddi` (проход B зелёный, поставка собрана).**

| | |
|---|---|
| создаваемых узлов (`<delta new="yes">`) | 7 |
| из них классы данных | 2 — `model/Glossary.java`, `model/Term.java` |
| у `Term.java` поля объявлены | да: `key`, `value` |
| у `Glossary.java` поля объявлены | **нет ни одного** |
| читателей `<field>` во всём конвейере | **один**: `frd.mjs:488`, и тот сверяет только происхождение чисел |
| адресация поля к узлу | сломана: `in="Термин"` — слово из прозы, не путь |

То есть у одной записи содержание объявлено и ПОТЕРЯНО по дороге, у второй не объявлено вовсе, и
в тикет приедет «создай Glossary.java» без единого поля.

Второй дефект того же места: `<field name="value" type="string" domain="string"/>` — `domain`
повторяет тип и никакого диапазона не задаёт. Проверить такое поле нечем.

**Что делать.**

1. **Правило шага 6: создаваемый класс приезжает с полями.** `<delta new="yes">` на узле, который
   является классом данных, обязан иметь хотя бы одно `<field>`, адресованное этому узлу. Пустой
   создаваемый класс — блокер, а не тикет.
2. **Правило шага 6: `domain` это ДИАПАЗОН, а не тип.** `domain`, повторяющий `type` (`string`,
   `int`, `boolean`, `number`) либо пустой — блокер. Диапазон это `1-64 символов, lowercase,
   [a-z0-9_]`, перечисление значений, границы числа, формат.
3. **Адресация:** `<field in="…">` принимает ПУТЬ УЗЛА, как это уже делают `<delta node>` и
   `<scenario nodes>`. Тогда поле резолвится в файл машиной, а не глазом.
4. **Потребитель:** поля создаваемого узла едут в поставку шага 9 — в его `<module>`. Тикет
   получает «создай Glossary.java с полями …».

**Осторожность.** Пункт 3 — расширение формы значения (`CLAUDE.md` §5): обойти потребителей
`<field>` (сегодня один, `F5`) и решить, что делать с полями запроса, которые узлу не принадлежат.

**Приёмка.**
1. Замер по всем сохранённым `frd.xml` под `sandbox/`: сколько блокеров добавляет каждое из двух
   правил на каждой форме.
2. `node --test` зелен.
3. Живой прогон `eddi` с шага 6: у обеих записей поля объявлены и доехали до `design-graph.xml`.
