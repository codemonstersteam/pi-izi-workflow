## Наряд D36 · подшаг 9c: разбиение на общее и частное

**Зачем.** Единицей работы становится use case, но на `eddi` **8 узлов из 13** трогают два и более
use case, а три из них — восемь каждый. Без разбиения двенадцать дизайнеров напишут восемь файлов
по-разному. Замер уже сделан: эти 8 складываются в **2 группы** по пакету (`configs/glossary` — 5
файлов, `backup` — 3). На `t2` общих узлов нет вовсе — фаза вырождается и стоит 0.

**Что делаем.** Новое чистое ядро `steps/design/card.mjs`:
- `splitOf({ frd, map })` → `{ shared: Map<путь, Set<uc>>, groups: [{ id, paths, ucs }], own: [...] }`;
- группировка по каталогу пакета, а не по префиксу пути: `backup/IResourceSource.java` и
  `backup/impl/ZipResourceSource.java` обязаны попасть в ОДНУ группу.

io — `ext/index.mjs`: `cards({})` пишет `.agent/staging/split.json`.

**Файлы.** `steps/design/card.mjs`, `card.test.mjs`, правка `ext/index.mjs`.

**Приёмка.**
1. `node --test` зелен.
2. Замена на сохранённых: `eddi` — 8 общих узлов, 2 группы; `t2` — 0 групп; `t3` — посчитать и
   записать в тест как факт.

## Наряд D37 · подшаг 9e-карточка: вход одного дизайнера

**Зачем.** Карточка одного use case — **10 КБ против 126 КБ**, если отдавать карту и FRD целиком.
Ручной прогон подтвердил, что этого хватает: план на четыре файла, 6 из 6 названных классов в
репозитории существуют.

**Что делаем.** В том же ядре:
- `cardOf({ uc, frd, map, flow, common })` → текст карточки: use case дословно · его сценарии и
  дельты · узлы из карты · системы и `<io>` этих узлов · `<suite>` с командой · поток своих
  сценариев из `data-flow.md` · `$START_COMMON` · образец путями;
- `sampleOf(path, map)` → лестница из четырёх ступеней (`docs/design.md` §2). Правило близнеца — по
  ФОРМЕ пути: строгое «одно отличие» даёт на `eddi` ноль, мягкое находит 3 из 5.

**Приёмка.**
1. `node --test` зелен, лестница проверена по всем четырём ступеням.
2. Замена: `eddi` — 12 карточек, ни одна > 12 КБ; у каждого создаваемого узла образец найден ЛИБО
   объявлено `found="no"`; у use case с существующими узлами секция `NODES` непуста.

## Наряд D38 · подшаг 9d: общий дизайн группы

**Зачем.** Дубль `terms: List<GlossaryTerm>` вложенным классом против отдельного `model/Term.java`
уже наблюдался живьём. Общий дизайн идёт ПЕРЕД роем, чтобы дубль не возникал, а не сводился потом.

**Что делаем.** Роль `steps/design/core-designer.md` + наряд `steps/design/order-core.tpl`.
Вход: файлы группы · ВСЕ use case, которые их трогают, дословно из FRD · образец путями · **черновик
из `design-graph.xml`** — накопленный по всем use case контракт (на `configs/glossary` это 9/19 у
`RestGlossaryStore`, 12/1 у `IGlossaryStore`, 1/11 у `GlossaryStore` и ПУСТО у `Glossary.java`).
Черновик едет как заготовка и как видимая дыра: значения там местами ярлыки (`IGlossaryStore CRUD`
стоит входом у 11 строк), роль заменяет их сигнатурами, читая образец.

Выход: `docs/design/core/<группа>.md` — поля, сигнатуры, кто зовёт.
Вызов — по образцу `onePass`, параллельно по группам через `slot`.

**Приёмка.** Живой `eddi`: 2 контракта; в контракте `configs/glossary` `Term` — отдельный класс,
вложенного `GlossaryTerm` нет; у `Glossary.java` поля названы.

## Наряд D39 · подшаг 9e: рой по use case

**Что делаем.** Роль `steps/design/planner.md` (текст наряда обкатан ручным прогоном, переносится
дословно) + `steps/design/order-plan.tpl` = инструкция 2 КБ + карточка. Право `tools: [read, write]`:
образец читается по путям, тела в наряд не кладутся.

Роль **использует** `$START_COMMON` и не переопределяет; чего не хватает — объявляет строкой:

```
$START_NEEDS
<путь файла> :: <чего не хватает> :: <зачем, ссылка на шаг use case>
$END_NEEDS
```

Гардрейл — 5 структурных правил (`docs/design.md` §3).

**Приёмка.** Живой `eddi`: 12 планов, ни одного класса без полей, ни одного пункта без строки
«проверка»; живой `t2`: 1 план.
