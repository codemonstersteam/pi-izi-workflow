# Backlog — S10, сверка `task → brd` перед стартом `survey-plan`

**S11 (после этой записи) переписала конвейер на функции расширения и выбросила универсальный
харнес** — `pipeline.json`, `step.json`, манифест, квитанции и headless-раннер `bin/run.mjs`
упразднены, `workflows/izi.js` знает оба шага литералом (`docs/workflow.md`, `docs/concept.md`,
«Что отложено и почему»). Пункты ниже написаны ПРОТИВ прежней архитектуры — там, где S11 закрыла
или переизложила пункт, это отмечено фактом инлайн, остальное продолжает описывать нерешённое.

Что осталось сделать, чтобы первые два шага конвейера (`task`, `brd`) были не «код существует», а
«результат воспроизводимо доезжает и пригоден для шага 3». Разбор строится на коде репозитория и на
живых прогонах: 3 прогона в песочнице `quarkus-pi-test-385aa7ea14e4` и 24 прогона в харнесе
`izi-pi-v2-b4dade62a6ea` (`~/.pi/workflows/projects/…`), включая `smoke`/`probe*` — не по этой полосе,
исключены из выводов.

## Цель

Живой прогон `task → brd` воспроизводимо кладёт `.agent/brd.md` с квитанцией — **включая** случай,
когда `gilb` задаёт вопрос оператору, — и этот артефакт машинно пригоден как вход `survey-plan`.

## Критерий готовности (проверяется прогоном или кодом, не мнением)

1. Headless-прогон (`node bin/run.mjs`, `operatorChannel: "terminal"`) на `TASK.md` с ≥1 содержательным
   гэпом доходит до `track:"ok", artifact:".agent/brd.md"` через полный цикл
   вопрос → `bin/answer.mjs` → перезапуск — воспроизводимо, не один раз повезло.
2. Тот же прогон в интерактивном окне pi (`operatorChannel: "checkpoint"`) доходит до квитанции `brd`
   через ≥1 реальный обмен `checkpoint()` → `bin/answer.mjs` → Approve, без ручной подмены канала.
3. `node --test` зелёный (README «Прогон одной командой»).
4. `pipeline.json.external` называет `app/` не позже, чем появится первый потребитель — сам шаг
   `survey-plan`.
5. Повторный `node bin/run.mjs` в том же каталоге после правки `TASK.md` **не** пропускает `task` по
   старой квитанции — расхождение входа с квитанцией либо инвалидирует её, либо останавливает прогон
   с диагнозом, а не молчит.
6. Пере-делегация `gilb` по красному чеку не падает `AGENT_TIMEOUT` при бюджете времени, равном
   уже наблюдавшемуся на стенде (см. п.3 ниже) — не литералу без обоснования.

**S11 факт по всем шести:** пункты 1, 2, 4, 5 написаны про `bin/run.mjs`/`operatorChannel`/
`pipeline.json` — все трое упразднены (см. банер выше), критерии в этой формулировке больше не
применимы. Заменяющий факт: живой прогон S11 (`docs/workflow.md` §3, карточка `brd`) прошёл
`checkpoint()` → `bin/answer.mjs` → Approve → фолд ответа в `fit:` без ручной подмены канала (канал
теперь один) — п.2 в новой архитектуре пройден; `.agent/brd.md` тем не менее не получен —
см. п.5(старое)/находку `numbersIn`+`ISO-8601` в `README.md` «Долги» (иная причина, не прежний дефект
счётчиков). П.3 (`node --test`) зелёный. П.6 закрыт иначе, чем предполагалось: `workflows/izi.js`
теперь не передаёт `timeoutMs` вовсе (был литерал 180000, ронявший прогон) — используется дефолт
хоста, а не число, вычитанное из одного удачного прогона.

## Пункты — по тому, что блокирует старт `survey-plan`

### 1. `app/` не существует и грепабельность `subjects[]` никто не проверяет

**Что.** `survey-plan` строит матрицу «файл × якорь» по `.agent/brd.md` и `app/` (`docs/workflow.md`
строки 111-116). Ни входа, ни проверки формы этого входа сегодня нет: `app/` в репозитории отсутствует
физически (`ls app` → нет каталога), `pipeline.json.external` называет только `TASK.md`
(`pipeline.json:4-6`), а сам `newSubjects` (`steps/brd/brd.mjs:219-228`) проверяет ровно
количество/формат/повторы термина — ни одна строка кода нигде не грепает `subjects[]` по файлам,
потому что грепать сегодня негде.

**Почему это работа, а не украшение.** Без этого шаг 3 нельзя даже спроектировать тестами: неизвестно,
на каком дереве файлов проверять гардрейл «клетки покрывают файлы без пересечений». Комментарий самого
`pipeline.json:3` уже честно называет это отложенным, а не спрятанным — но отложенное само не появится.

**Улика.** `pipeline.json:3-6`; `steps/brd/brd.mjs:219-228` (`newSubjects`); `docs/concept.md:82-89`
(«нет `app/` … `survey-plan` встаёт с диагнозом `blocked`»); нет ни одного закоммиченного примера
`.agent/brd.md` — каталог в `.gitignore`, `arch/slices/brd.md` это спецификация контракта, а не
артефакт живого прогона.

**Чем закрывается.** `pipeline.json.external` называет `app/` не позже среза `survey-plan`; хотя бы
один живой прогон против репозитория, у которого `app/` есть, доказывает, что `subjects[]` из
`.agent/brd.md` действительно совпадают (`grep -rl <term> app/`) хотя бы частично — иначе якоря
существуют только на бумаге.

**Улика.** Известный дефект (три Approve = три красных чека) **починен и виден в последнем прогоне**:

Три прогона подряд с ответом оператора, три `track:"ok"` (после починки) — воспроизведено, не

### 3. `timeoutMs` пере-делегации зашит литералом и уже ронял прогон

**Что.** `workflows/izi.js:241`: `agent(order, { role: s.role, outputSchema: ENVELOPE, timeoutMs:
180000 })` — единственная политика прогона во всём файле, которая НЕ читается из `pipeline.json`, хотя
тот же файл декларирует принцип «молчаливый дефолт вернул бы число в память автора, откуда его не
проверить» для `operatorChannel`, `questions`, `checkpointRetries`, `loops` (строки 61-107) — и не
делает для `timeoutMs` того же.

**Почему это работа, а не украшение.** Это не гипотетический риск: харнес-прогон
`64d89865-971e-4899-8549-ca7d68c87e6c` (session `019fd41e-b25b-7ed2-912f-12627ab49457`) умер именно
здесь — вторая пере-делегация `gilb` (`brd attempt 2/3`) вернулась `error.code:"AGENT_TIMEOUT"`
(`state.json`, `agents[1].attemptDetails[0].error`), прогон закрылся `state:"failed"` без
`result.json`, потратив 52874 токена / $0.031 и не дав ничего.

**Улика.** `workflows/izi.js:241`; run `64d89865-971e-4899-8549-ca7d68c87e6c`,
`~/.pi/workflows/projects/izi-pi-v2-b4dade62a6ea/sessions/019fd41e-b25b-7ed2-912f-12627ab49457/runs/64d89865-971e-4899-8549-ca7d68c87e6c/state.json`.

**Чем закрывается.** `timeoutMs` переезжает в `pipeline.json` тем же приёмом, что `loops`/`questions`
(без дефолта — крах на отсутствии), со значением не ниже уже наблюдавшегося на стенде успешного
прогона (`b372e9da-…`: 113856ms суммарно на 2 попытки); повтор точной ситуации `64d89865` не падает
`AGENT_TIMEOUT`.

**Закрыто иначе (S11).** `pipeline.json` упразднён целиком, значит и предложенное «переезжает в
pipeline.json» не могло состояться буквально. Вместо этого `workflows/izi.js` (S11) не объявляет
`timeoutMs` вовсе — `agent(order, { role: "gilb", outputSchema: ENVELOPE })` без этого поля,
используется дефолт хоста. Находка (литерал без обоснования роняет прогон) закрыта тем, что литерала
больше нет; повтор `64d89865` не проверялся третьим живым прогоном намеренно (бюджет живых прогонов
исчерпан этой задачей на другом), но сам класс дефекта («число из памяти автора») этим устранён.

### 4. Квитанция не привязана ни к прогону, ни к содержимому входа

**Что.** `workflows/izi.js:349`: `[ -f .agent/receipts/${id}.json ]` — единственное условие, решающее
«шаг закрыт». `bin/receipt.mjs:34-44` пишет `{ step, at, by: "harness" }` — ни хэша `TASK.md`, ни
`runId`, ничего, что связывало бы квитанцию с КОНКРЕТНЫМ входом, который она приняла.

**Почему это работа, а не украшение.** `docs/concept.md:145-146` формулирует это как гарантию:
«Поэтому перезапуск продолжает, а не начинает, и артефакт, записанный по ошибке, шаг не закрывает» —
код этой гарантии не держит. Второй `bin/run.mjs` в том же каталоге после правки `TASK.md` пропустит
`task` по старой квитанции (`runHumanStep` вообще не вызывается — строка 349 срабатывает раньше), а
`brd` тем не менее читает АКТУАЛЬНЫЙ `TASK.md` (`runRoleStep`, `cat TASK.md`) — квитанция говорит
«вход принят», а вход уже другой. Ничто это расхождение не обнаруживает.

**Улика.** `workflows/izi.js:349`; `bin/receipt.mjs:34-44`; `docs/concept.md:145-146` (заявленная
гарантия).

**Чем закрывается.** Квитанция несёт отпечаток входа шага (либо отдельный механизм отказывает
громко, а не пропускает молча) — повторный прогон с изменённым `TASK.md` либо переоткрывает `task`,
либо останавливается с диагнозом «вход разошёлся с квитанцией», не продолжает как ни в чём не бывало.

**Закрыто иначе (S11).** Квитанций (`.agent/receipts/*.json`) больше нет — `workflows/izi.js`
(S11) не возобновляется по файлам на диске между запусками, прогон идёт до терминала за один вызов
`/izi`. Находка (квитанция не привязана к входу) закрыта тем, что закрывать больше нечего: нет
факта «шаг закрыт квитанцией», значит нет и риска, что этот факт разойдётся со входом. `docs/
concept.md` («Что отложено и почему») теперь прямо называет это отложенным, не забытым —
принцип «квитанция закрывает шаг» вернётся вместе с шагами, которым есть что возобновлять.

### 5. `subjects[]`/BRD не экспортируются иначе как прозой — но парсер уже пригоден для переиспользования

**Что.** Единственный код, читающий `.agent/brd.md` машинно сегодня — `steps/brd/validate-brd.mjs:54`,

**Почему это работа, а не украшение.** Небольшая, но реальная: без явного шага «survey-plan использует
`parseBrd`/`newBrd` напрямую» есть риск, что кто-то напишет ВТОРОЙ, независимый парсер прозы
`.agent/brd.md` — ровно та ошибка, от которой предостерегает `standards/code.md` («одно требование —
одно место»).

**Улика.** `steps/brd/brd.mjs:52-53,120-142,308-352` (`parseBrd`/`newBrd` экспортированы и чисты, без
`node:fs`); `steps/brd/validate-brd.mjs:54` — единственный вызывающий.

**Чем закрывается.** `steps/survey-plan/*.mjs` импортирует `parseBrd`/`newBrd` из
`steps/brd/brd.mjs`, а не заново разбирает прозу — это низкий приоритет и не блокирует старт (парсер
уже готов), но должно быть решено ДО написания script'а `survey-plan`, не после.

**Закрыто (S11), хоть и не для `survey-plan`.** `ext/index.mjs::checkBrd` теперь тоже импортирует
`newBrd` из `steps/brd/brd.mjs` напрямую (не парсит `.agent/brd.md` заново) — прецедент «второй
парсер не пишем» установлен фактом кода, не только пожеланием. Когда появится `survey-plan`, ему
предстоит сделать то же самое со своим `Brd`-значением — сам пункт (не плодить парсер) остаётся в
силе для него, просто первый потребитель уже показал форму.
