## Волна 1 — чистые ядра. Ни от чего не зависят

### T1 · `steps/design/tree.mjs` — дерево модулей как данные

**Зачем.** Шаг 9B: что за модули, что каждый скрывает, без чего его не написать.

**Вход:** `frd` (дельты ∪ узлы сценариев), `ripple` (decl, api, соседи), `map` (сьюты, существующие
файлы). **Выход:** скелет `tree.xml` с уже заполненными фактами · разбор · блокеры.

**Состав:**
- `treeSkeleton({ frd, ripple, map })` — `<module>` на каждый модуль изменения, заполнены `path`,
  `delta`, `io`, кандидат `twin`, `decl`/`api` из ряби. Роль дописывает `hides`, `owns`, `needs`,
  `contract`.
- `parseTree(xml)` — единственный разбор дерева на всю полосу.
- `checkTree({ text, part, family, known, portion, whole })` — правила 1-5 из `docs/plan-design.md`
  §4: порция (раздел на модуль порции · чужих нет · `needs` — ПУТЬ · сигнатура непуста) и целое
  (состав = дельты ∪ узлы сценариев · `needs` разрешается · `needs` ацикличен · один владелец типа ·
  имя типа везде одинаково).

**DoD:** формула `N_units` из `standards/code.md` соблюдена; `MODULE_CONTRACT` и
`FUNCTION_CONTRACT` на месте; блокер каждого правила несёт код, элемент и ОБРАЗЕЦ строки
(`standards/guardrail.md`).

**Шов:** юнит на каждую ветку предусловия с различимым следствием; отдельный — на «имя типа
разъехалось» (`clearLayers` против `clearFullLayers`, кража из superpowers).

### T2 · `steps/design/flows.mjs` — потоки как данные

**Зачем.** Шаг 9C: что происходит с данными, и какой шаг требования этим закрыт.

**Вход:** `frd` (use case, шаги, ветвления, отказы), `tree`. **Выход:** скелет `flows.xml` с
проставленным `closes` · разбор · блокеры.

**Состав:**
- `flowsSkeleton({ frd })` — `<flow>` на каждый use case и на каждое ветвление; строки шагов пустые,
  но `closes` уже проставлен скриптом.
- `parseFlows(xml)`.
- `checkFlows({ text, uc, tree, values, portion, whole })` — правила 6-10: порция (все шаги ЭТОГО use
  case закрыты · модуль назван деревом · роль шага проставлена · значение границы — из словаря) и
  целое (один порождающий МОДУЛЬ на значение · вход порождён либо внешний · каждый отказ порождён
  шагом «отвергаю» и доехал до статуса · модуль дерева работает в потоке ЛИБО достижим по `needs`).

**DoD:** последнее правило написано так, чтобы не спрашивать поведения с объявления — это ошибка,
которую первая версия проверки уже сделала (`docs/plan.md` Ш8).

**Шов:** юнит «объявление доказано через `needs`» и юнит «два модуля порождают одно значение».

## Чего в наборе нет

- Головы (композиционного корня) — в java-проекте её может не быть, а поток есть всегда.
- Поля `calls:` в любом виде — три смысла в одном поле были маятником.
- Вывода очереди работ из потока данных — поток цикличен по природе.
- Карточек партий и разбиения на партии.
- Полных блоков кода в плане — близнец с живыми сигнатурами дешевле и точнее.
