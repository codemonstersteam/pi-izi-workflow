# Data flow конвейера izi — до Gate 1

Что во что превращается, кто это проверяет и куда ложится. Форма разбора — та же, которой этот
конвейер описывает чужой проект (`sandbox/runbox/eddi/.agent/mvp/data-flow.xml`): **вход → проверки →
обработка → выход → артефакт**.

Порядок работ здесь НЕ задаётся — он в `plan-app-graph.xml`, отношение `needs`. Здесь только поток.

`✅` — входит в первую поставку (конвейер до 9C). `⏳` — объявлено, пишется после разбора.

## Ход конвейера: один объект состояния

По полосе едет **один объект**, который каждый шаг трансформирует. Внутри — пути, отпечатки,
счётчики и вердикты; **документов шага внутри нет**, тексты читаются на месте.

```json
{ "cwd": "/…/eddi", "key": "DOS-535", "run": "3f2a91c0",
  "budgets": { "loops": 3, "intakeLoops": 6, "questionRounds": 5,
               "checkpointRetries": 2, "maxParallel": 8, "reviewRounds": 2, "orderCap": 800000 },
  "closed": ["task", "brd", "scope", "graph", "intake", "weight", "ripple"],
  "at": { "brd":  { "path": ".agent/brd.md",   "sha1": "a1b2…" },
          "frd":  { "path": ".agent/frd.xml",  "sha1": "c3d4…" },
          "ripple":{ "path": ".agent/ripple.xml","sha1": "e5f6…" } },
  "portions": [ { "id": "UC1", "staging": ".agent/staging/flows~UC1.xml",
                  "status": "green", "round": 2, "blockers": "" },
                { "id": "UC2", "staging": ".agent/staging/flows~UC2.xml",
                  "status": "todo",  "round": 1, "blockers": "" } ],
  "asked": 2,
  "question": { "of": "UC2", "name": "intake-q2", "items": ["…"], "retry": 1 },
  "verdicts": [ { "step": "plan/tree", "scope": "portion", "id": "1", "round": 1,
                  "ok": true, "blockers": "", "at": ".agent/staging/tree~1.xml" } ] }
```

Четыре решения этой формы, и каждое куплено дефектом:

**`at` держит путь И ОТПЕЧАТОК.** «Вход: `frd.xml` зелен» — это не проверка, а комментарий, пока
никто не сверяет содержимое. Шаг `close` считает sha1 при продвижении, шаг-потребитель сверяет его
ПЕРВЫМ ходом. Без этого правленый руками между прогонами артефакт проезжает весь остаток полосы, а
`closed` продолжает утверждать, что шаг зелен. Механика была спроектирована ровно так ровно в одном
месте — токен `gate1`, привязанный к дайджесту плана, — и не обобщена на остальные одиннадцать входов.

**`portions` — СПИСОК, а не два счётчика.** У 9C порция адресуется строкой (`flows~UC1`), у `scope` —
идентификатором клетки, и семь конвертов приезжают РАЗОМ. В скаляры `portion`/`portions` это не
записывается: некуда положить семь статусов, семь кругов и семь наборов блокеров. Список закрывает
заодно три других вопроса — адресат блокера целого (`status: "todo"` ставится ИМЕНОВАННЫМ порциям),
пропуск зелёной порции (`green` не переписывается) и вопрос от одной порции при живых соседях.

**`round` — у порции, не у шага.** Иначе первая порция съедает бюджет всего шага: два круга на неё,
и порции 3 и 4 не пробуются ни разу.

**`question` живёт в состоянии.** Без поля рельса `ask` недостижима: `next` его читает, а выставить
его некому. `name` здесь не украшение — хост ключует паузу по имени, и два хода с одним именем это
ОДНА пауза, второго вопроса оператор не увидит.

Владелец формы — модуль `state`, и только он. Ни песочница, ни шаг состояние не придумывают:
невалидное состояние **не создаётся** (valid by construction), возвращается отказ. Конструктор —
не только у состояния: `instruction`, `verdict`, `err` строятся своими конструкторами по той же
причине. `fold` обязан возвращать `put(state, patch)`, а не объектный литерал со спредом — иначе
гардрейл конструктора срабатывает один раз за прогон, а следующие N состояний создаются в обход него.

Границы-часовые (`round`, `portion`) конструктор пропускает на единицу дальше предела: состояние
«круги исчерпаны» и состояние «порции кончились» обязаны СУЩЕСТВОВАТЬ — на них стоят обе
терминальные ветви `next`, `escalate` и `done`.

## Ход одного шага: пятёрка, одна на все шаги

```
        ┌──────────────────────────────────────────────────────────────────┐
state → │ inputs → cut → order → ask → judge → route │ пока route не скажет │ → state'
        └──────────────────────────────────────────────────────────────────┘
```

| подмодуль | кто | что делает | 0 токенов? |
|---|---|---|---|
| `inputs` | скрипт | **суд ВХОДА**: есть ли артефакт, разбирается ли, совпал ли sha1 | да |
| `cut` | скрипт | сколько порций и что в каждой; скелет ответа | да |
| `order` | скрипт | слоты + шаблон → текст наряда; слот без данных — отказ, не пустота | да |
| `ask` | **роль** | `role` (одна порция) или `roles` (порции разом, ≤ ширины роя) | нет |
| `judge` | скрипт | гардрейл: судья на правило, вердикт по порции и по целому | да |
| `route` | скрипт | следующая порция · круг починки · склейка · продвижение · `done` | да |

Наружу шаг выставляет **два вызова**, и граница между ними одна: **`next(state)` решает и готовит
доставку, `fold(state, event)` принимает ответ и судит.**

- `next` читает вход и собирает наряд; пишет ровно две вещи — чистит staging-путь порции перед
  вызовом и кладёт `.agent/pending.json` перед вопросом. Не зовёт модель, не судит, не продвигает.
  Чистка staging не мелочь: файл прошлого круга, оставшийся на пути доставки, судится как ответ
  этого круга — круг потрачен, шаг закрыт непочиненным.
- `fold` разбирает СОБЫТИЕ прежде всего остального: `say` — состояния не меняет; `ask` — читает
  ответ с диска по номеру (`approved` это барьер над фактом, а не сам факт); `track:"err"` — обрыв
  связи, вопрос роли или запрос к диску: staging не трогается, **круг не тратится**; и только
  `track:"ok"` идёт в суд.
- **Артефакт пишет РОЛЬ, а не `fold`.** Конверт несёт ПУТЬ; документ по RPC не едет. `fold` сверяет,
  что роль записала туда, куда её послали, и что файл непуст.

**Пятёрка тотальна:** `inputs`, `cut`, `order`, `judge`, `route` не бросают. Битый XML — это вердикт
`invalid`, а не исключение: исключение уходит через RPC мимо всей ROP-цепочки и уносит прогон на
сорок минут из-за одного незакрытого тега.

**Вердикт каждого хода обязан лечь в состояние.** Чего нет в состоянии — того не видит тест, и
«артефакт лёг» перестаёт означать «гардрейл принял». Проверяется это не наличием ключа, а длиной:
`verdicts` после хода длиннее ровно на число разобранных конвертов.

## Шаги

Форма разбора одна: **вход → суд входа → обработка → выход → суд выхода → артефакт**. Суд входа —
не формальность и не комментарий: он существует у КАЖДОГО шага, и у каждого есть свой юнит
«входного артефакта нет / он не разбирается / его sha1 не совпал → отказ с именем файла». Правило
одно на всех и потому не повторяется в каждом разделе:

> **Шаг не верит предшественнику на слово.** Первым ходом он сверяет отпечаток каждого своего
> входа с тем, что записал `close` продвинувшего шага. Расхождение — отказ с именем файла, а не
> тихая работа по чужому документу. Это закрывает три двери разом: правку руками между прогонами,
> артефакт с рельсы ошибки и артефакт от прошлой задачи.

### ✅ task — ключ задачи
- **вход**: `TASK.md`. **Проверка входа**: файл непуст; отсутствие — отказ, а не пустая строка.
- **обработка**: скрипт достаёт ключ.
- **выход**: `{ key }`. **Проверка выхода**: ключ соответствует форме проекта.
- **артефакт**: едет в состоянии; файла нет.

### ✅ brd — измеримое требование
- **вход**: `TASK.md` + ключ. **Суд входа**: `TASK.md` читаем и его sha1 совпал с закрытым `task`;
  «шаг закрыт» само по себе ничего не доказывает.
- **обработка**: роль `gilb`, один наряд.
- **выход**: `brd.md`. **Проверка**: нумерация `R1..RN` сплошная, каждое требование измеримо, язык
  артефакта = язык заказа.
- **артефакт**: `.agent/brd.md` — **только после зелёного вердикта**; до того `.agent/staging/brd.md`.
- **декомпозиция**: одна порция. **сшивка**: —

### ✅ scope — карта репозитория роем
- **вход**: `brd.md` + дерево файлов. **Суд входа**: `brd.md` разбирается и его sha1 совпал; дерево
  непусто.
- **обработка**: `cut` режет дерево на клетки → `roles`, все клетки **разом** (порции независимы).
- **выход**: `graph-parts/*.xml`. **Проверка**: у каждой части есть клетка, части не пересекаются,
  пустых нет.
- **артефакт**: `.agent/graph-parts/` — по файлу на клетку.
- **сшивка**: делает следующий шаг.

### ✅ graph — одна карта
- **вход**: части. **Суд входа**: у каждой клетки есть часть И эта часть проходит гардрейл части
  СЕЙЧАС — «когда-то была зелёной» шага не закрывает. Скрипт, 0 токенов.
- **выход**: `appgraph.xml`. **Проверка**: карта покрывает все клетки, дубликатов путей нет.
- **артефакт**: `.agent/appgraph.xml`.

### ✅ intake — требование, обжаренное о карту
- **вход**: `brd.md`, `appgraph.xml`, ответы оператора. **Суд входа**: оба артефакта разбираются и
  их sha1 совпали с закрытыми шагами.
- **обработка**: четыре пласта — четыре наряда, **последовательно**: пласт видит прошлый.
- **выход**: `frd.xml`. **Проверка**: двадцать правил FRD (`F0…F14` с подпунктами, 49 различимых
  блокеров — измерено по коду), судья на правило; **молчание требования — вопрос оператору, а не
  выдуманный дефолт**, и это отдельный компонентный сценарий, а не строчка внутри успеха.
- **артефакт**: `.agent/frd.xml`.
- **сшивка**: пласты дописываются в один документ, целое судится отдельно от пласта.

### ✅ weight · ripple — вес и задетое
- **вход**: `frd.xml` (+ `appgraph.xml` для ripple). **Суд входа**: разбор и sha1.
- **выход**: `mode`, `ripple.xml`. **Проверка**: вес из закрытого словаря; каждый задетый путь есть в карте.
- **артефакты**: `.agent/mode`, `.agent/ripple.xml`.

### ✅ plan/values — словарь значений границы
- **вход**: `frd.xml`. **Суд входа**: разбор и sha1.
- **выход**: `values.xml`. **Проверка**: значение границы имеет форму `МЕТОД путь` или `код КОД`;
  внутренние коды отказа в словарь не пускаются.
- **артефакт**: `.agent/values.xml`. Зелёный с прошлого прогона — роль **не зовётся**, 0 токенов,
  НО ровно при трёх условиях разом: sha1 входа тот же, состав скелета тот же, и словарь проходит
  гардрейл СЕЙЧАС. Без них правка требования оставляет старый словарь, а `plan/flows` получает
  блокер `F11`, который роли нечем закрыть: значения нет в словаре, а словарь она не пишет. Условия
  списаны с кэша частей `scope`, где это правило уже куплено живым прогоном.

### ✅ plan/tree — дерево модулей работы
- **вход**: `frd.xml`, `ripple.xml`, `appgraph.xml`, файлы образцов из репозитория.
  **Суд входа**: все три артефакта разбираются, их sha1 совпали; образец берётся **живой** и режется
  дайджестом **с номерами строк** — роль дочитывает точечно, а не тянет файл целиком.
- **обработка**: `cut` — по четыре модуля на порцию, **последовательно**: каждая порция читает, что
  решили соседи.
- **выход**: `tree.xml`. **Проверка** (T1..T5): путь существует или объявлен `Added`; `needs`
  указывает на **объявление**, а не на вызов; владелец называет свой тип; `needs` **ациклично** —
  свойство целого, порция его видеть не может.
- **артефакт**: `.agent/tree.xml`; staging — `.agent/staging/tree~N.xml`.
- **сшивка**: порции склеиваются, ацикличность проверяется только на целом.

### ✅ plan/flows — потоки данных
- **вход**: `tree.xml`, `values.xml`, `frd.xml`. **Суд входа**: все три разбираются, sha1 совпали;
  отсутствие `values.xml` — отказ шага, а НЕ красный `F11` на каждой порции.
- **обработка**: порция = **один use case**, порции независимы → `roles`, все разом.
- **выход**: `flows.xml`. **Проверка** (F1..F11): у значения ровно один **порождающий** модуль;
  каждый шаг требования закрыт; отказ имеет код; граничное значение есть в словаре.
- **артефакт**: `.agent/flows.xml`; staging — `.agent/staging/flows~UC1.xml` (порция адресуется
  ИДЕНТИФИКАТОРОМ use case, не номером — на этом и держится список порций в состоянии).
- **сшивка**: покрытие требования проверяется на целом.

### ⏳ plan/book · review · gate1
Объявлены в `plan-app-graph.xml`; пишутся после того, как разберём 9C.

## Круг починки — один на все шаги

```
роль ответила → judge отбил → route: round+1 У ЭТОЙ ПОРЦИИ, blockers → order берёт ШАБЛОН ПОЧИНКИ
   → наряд починки несёт: нумерованный список находок с АДРЕСОМ правки + прошлый ответ роли
   → скелета в нём НЕТ: роль правит свой ответ, а не пишет заново
   → round порции > loops → отказ escalate с последним вердиктом
```

Четыре правила круга, и каждое обязано быть выражено в состоянии — иначе его нечем проверить:

| правило | чем выражено |
|---|---|
| красная порция переписывается ТА ЖЕ, соседние не трогаются | `status` у каждой порции отдельно |
| зелёная не переписывается, КРОМЕ случая, когда она адресат | `route` возвращает список адресатов, им ставится `todo` |
| блокер без путей адресата не имеет → переписываются ВСЕ | адресаты = все порции; незнакомая находка едет дороже |
| та же жалоба дважды — дефект ТЕКСТА блокера, а не роли | `route` сравнивает `blockers` с прошлым вердиктом ТОЙ ЖЕ порции |

Выбор «первый заход или починка» — это решение `route`, и оно **наблюдаемо**: инструкция несёт имя
шаблона, а тест на него смотрит. Сегодня этот выбор живёт в песочнице и проверяется только живым
прогоном по 4–9 минут за круг.

## Возобновление: один источник истины

«С чего продолжать» решает **трейс**, а не наличие файлов и не снимок состояния. Сегодня на этот
вопрос отвечают три разных механизма — ровно тот дефект, ради которого затеяна переработка, и
завести вместо них два (журнал и `state.json`) значило бы не починить, а переименовать.

```
runlog.xml            ← пишется КАЖДЫЙ ход: источник истины
.agent/state.json     ← кэш последнего состояния; расходится с трейсом → отказ с именем шага
sha1 в `at`           ← артефакт правили руками → шаг переигрывается, что бы ни говорил `closed`
```

Прогон с нуля уносит прошлое состояние в `.agent/prev/` (ответы, открытый вопрос, разговор) и
**чистит `.agent/staging/`**: незаконченный черновик не наследуется никогда. Продолжение —
наоборот, ответы и открытый вопрос сохраняет: они принадлежат работе, которую оно продолжает.

Обрыв между записью staging и вердиктом не должен стоить порций: снимок пишется после КАЖДОГО хода,
а не после закрытого шага, и порция со `status:"green"` при возобновлении не переписывается.

## Трейс прогона

Каждый ход пишется в `.agent/runs/<runId>/runlog.xml`: что поступило на шаг, какой наряд ушёл роли,
что она ответила, сколько токенов, куда легло, какой вердикт. Файл нужен трижды: восстановить
прогон, найти дефект — и **достать записанный ответ модели для заглушки теста**, чтобы его не
добывать отдельно.

Каталог по прогону, а не один файл на проект: второй прогон иначе либо приписывает второй корень
`<run>` и делает XML невалидным, либо затирает трейс первого — а трейс первого объявлен источником
заглушек для всех компонентных тестов.

Пропущенная запись трейса неотличима от «вердикта не было», поэтому отказ записи не проглатывается
молча: следующая удавшаяся запись несёт `<gap lost="N"/>`. Без этого приёмка «ни один артефакт не
лёг с красным вердиктом — проверено по трейсу» не имеет силы доказательства.
