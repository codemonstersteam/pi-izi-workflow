# После сборки плана: критик → фиксер → гейт

Что здесь: проход по `workflows/izi.js` от собранного `PLAN.md` до подписи оператора, по шагам.
Каждый шаг — вход, выход, пред- и постусловия, роль со ссылкой на её наряд, скрипты, гардрейлы и
то, что гардрейл возвращает МОДЕЛИ. Всё выверено по коду 20.08.2026, не по замыслу.

**Задача этого отрезка одна:** довести план до состояния, в котором исполнитель, читающий ТОЛЬКО
свой наряд, может сесть и написать код. Конвейер выше (шаги 1-9) к этому моменту закрыт — его
артефакты материал, а не предмет работы. Единственная законная отмотка объявляется человеком на
гейте.

---

## Шаг 1 — сухая нарезка (10б)

    вход      task/<KEY>/PLAN.md · .agent/frd.xml · .agent/appgraph.xml · .agent/ripple.xml
    выход     ничего на диск — только вердикт
    скрипт    ext/index.mjs::tickets({dry:true}) · steps/tickets/tickets.mjs::ticketsOf
    роль      нет

`pre:` план собран, ключ задачи объявлен в `TASK.md`.
`post:` доказано, что из плана режется исполнимый набор нарядов — с волнами и командами проверки.

**Гардрейл.** Судит и режет ОДИН и тот же код, поэтому «проверено одно, нарезано другое» невозможно.
Отказ → `from = 9`, отметка `rework` в журнале, жалоба едет дизайнеру блоком `FEEDBACK`.
**Та же жалоба второй раз — эскалация:** роль её не понимает, круги тратить не на что.

## Шаг 2 — величины (`placeValues`)

    вход      <nfr> требования · PLAN.md · .agent/data-flow.md (документом) · адресная книга
    выход     правка в КАРТОЧКЕ партии → пересобранный PLAN.md
    роль      steps/planreview/plan-fixer.md · наряд steps/planreview/order.fix.tpl
    скрипты   planFeedback({nfrs:true}) · planCard({}) · planFix(judge:"card") · planbook

`pre:` план собран и режется.
`post:` каждая величина, которую есть чем узнать, стоит в плане — и в его ИСТОЧНИКЕ.

Величина узнаётся числом с единицей, кодом или именем с точкой (`steps/plan/raises.mjs::measuresOf`).
Словесная величина («по образцу соседнего модуля») не проверяема — правило о ней МОЛЧИТ.

У `<nfr>` нет адреса: связь «glossary-cache-ttl → GlossaryService» видна только по смыслу цепочки.
Поэтому модуль ищет МОДЕЛЬ по `data-flow.md`, а правку применяет машина по якорю.

**→ модели:** строка `nfr: <subject> = <fit> (источник …)` в блоке `FEEDBACK`.

## Шаг 3 — луп (10в): критик → фиксер → гардрейлы

Бюджет `PLAN_ROUNDS = 5`. Круг устроен так.

### ① критик

    вход      planReview({}) → { at, brd, frd, plan, known }
    наряд     steps/planreview/order.tpl — BRD · FRD · PLAN · PLANPATH · KNOWN · OPERATOR · STAGING
    роль      steps/planreview/plan-critic.md
    выход     .agent/staging/planreview.txt — строки `R<n> | KIND | <путь> | <что добавить>`

`pre:` путь доставки ОЧИЩЕН (`clearStaged`) — файл прошлого круга не может сойти за ответ этого;
наряд помещается в окно модели (`sized`, потолок 800 000 симв).
`post:` вердикт лежит файлом. Пустой файл — законный ответ «находок нет»; молчание — нет.

`OPERATOR` — слова человека с гейта, ВХОДОМ, а не второй веткой. Конверт роли текста не несёт
(`ENVELOPE`, `additionalProperties:false`): работа доставляется только файлом.

### ② маршрут — `planRoute({verdict})`

Решает `steps/planreview/planreview.mjs::routeOf` по СОСТОЯНИЮ артефактов, а не по слову критика:

| состояние | маршрут | почему |
|---|---|---|
| путь есть в `PLAN.md` | `plan` | правка по якорю в карточке |
| пути в плане нет, требование его знает | `design` | не отработал шаг 9 — план переигрывается |
| пути не знает ни план, ни требование | `frd` | модуль входит в план только через `<scenario nodes>` |

Отдаёт ещё `paths` — узлы, названные находками: по ним подставляются ФАКТЫ.

### ③ факты и адрес правки

    nodeFacts({paths})  → объявления файлов и их вызовы из .agent/graph-computed.xml
    planCard({node})    → карточка партии, ВЛАДЕЮЩАЯ этим модулем

`PLAN.md` — документ ПРОИЗВОДНЫЙ: `planbook` копирует разделы из карточек. Правка в документе живёт
до первой пересборки, поэтому фиксер правит ИСТОЧНИК. Находки разводятся по карточкам: якорь чужой
карточки не найдётся.

### ④ фиксер

    наряд     steps/planreview/order.fix.tpl — TARGET · PREVIOUS · FEEDBACK · FACTS · FLOW · KNOWN · STAGING
    роль      steps/planreview/plan-fixer.md
    выход     .agent/staging/planfix.txt → planFix({target, patch, judge:"card"})

`FEEDBACK` — один блок, строки помечены источником: `critic:` (что нашёл критик), `nfr:` (величина),
`guardrail:` (чем был отвергнут ПРОШЛЫЙ ответ самой роли).

Роль не выдумывает три вещи: **путь** берёт из адресной книги, **сигнатуры и `calls:`** — из фактов,
**якорь** — из `PREVIOUS`. Очередь работ и зависимости она не пишет вовсе: их считает нарезка.

**Запись повторяется на месте** (`WRITE_TAKES = 2`): провайдер обрывает вызов `write`, роль считает
работу сданной, файл пуст. Круг лупа дороже — в нём сверху вызов критика.

### ⑤ гардрейлы правки — ДО записи

`planFix judge:"card"` — транзакция:

1. правка применяется В ПАМЯТИ (`applyPatch`); якоря нет — отказ, файл не тронут;
2. `hiddenHeads` — заголовок раздела обязан стоять на нулевой колонке;
3. карточка пишется, `planbook` пересобирает `PLAN.md`, `tickets({dry:true})` судит;
4. красное — **откатываются оба файла**: карточка из памяти, план — пересборкой.

**→ модели** одной строкой `guardrail:`, и она называет причину: якоря нет · заголовок с отступом ·
план перестал резаться.

`post:` на диске лежит только то, что прошло суд; отметка шага 9 переставлена на новый план — иначе
лестница сочтёт шаг сломанным и следующий запуск пересоберёт план поверх работы лупа.

### ⑥ потерянный модуль — скриптом

    frdAdopt({path, req, what}) → adoptNode(...) → planFix(judge:"frd")

Роль не участвует: путь назвал разборщик, use case — строка `<carried req>`, сценарий у него один,
текст дельты — сама находка. Скрипт дописывает путь в `nodes` сценария и `<delta>` рядом с
последней; правка судится полным `checkFrd`, и **вменяется ей только НОВЫЙ ущерб** — чужой долг
артефакта (правило, заведённое после его закрытия) на неё не вешается.
Не по чему выбрать сценарий — честный отказ, и находка уходит в `stuck`: фиксеру плана она не едет,
он закрыл бы её разделом-сиротой.

Успех → `return { replay }` → лента ставит `from = 9`, план пересобирается. **Правки круга при этом
не теряются: они в карточке.**

### ⑦ выход из круга

    находок нет И долгов нет            → план идёт к гейту
    правка не легла                     → находки в `owed`, замечание в `missed`, следующий круг
    круги исчерпаны                     → план идёт к гейту, лог называет НЕ ЗАКРЫТОЕ поимённо

**Луп есть, и он один.** Отмоток конвейера у него нет: `replay` — не отмотка, а пересборка того же
шага 9 из починенного требования.

## Шаг 4 — гейт 1

    вход      PLAN.md · .agent/frd.xml · карта (счёт модулей, команд, ветка)
    выход     .agent/gate1.json — ключ, sha256 плана, решение
    скрипт    ext/index.mjs::gate1 · steps/design/plandoc.mjs::gateView/readGate
    роль      нет; отвечает ЧЕЛОВЕК

Презентацию собирает СКРИПТ — каждая строка вырезка или счёт. Четыре ответа:

    approve                              → токен привязан к sha256 плана
    rework: <что не так в плане>         → слова уходят критику плана, конвейер не трогается
    requirements: <что упущено>          → ЕДИНСТВЕННАЯ отмотка: from = 2, интейк переигрывает FRD
    stop                                 → полоса останавливается

`post:` план изменился после подписи — токен недействителен, и человека спрашивают заново.

## Проверка этого текста

Каждая строка выше сверена с кодом. Что нашёл проигрыш ПОСЛЕ написания первой версии и что
починено тем же заходом:

| дефект | где был | чем закрыт |
|---|---|---|
| правка ложилась в документ, а не в источник | `fixOne(target: src.at)` | `planCard` + `judge:"card"` |
| карточка выбиралась по первому пути ЛЮБОЙ находки | `planCard({node: paths[0]})` | находки разведены по карточкам |
| неусыновлённая находка уезжала фиксеру плана | `owed = [...owed, line]` | отдельный список `stuck` |
| раздел с отступом не виден нарезке | — | `hiddenHeads` в транзакции |
| оборванный `write` стоил круга лупа | — | `WRITE_TAKES = 2` |
| критик писал `(no such module)` вместо пути | наряд и роль | адресная книга + запрет |
