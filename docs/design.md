# Шаг 9 `design` — план работ по use case

Место шага в полосе — `docs/workflow.md` §3.9; грамматики артефактов — `docs/data-flow.md`. Здесь —
устройство шага целиком и статус каждого подшага.

Шаг 9 отвечает на один вопрос: **что и где нужно сделать, чтобы требование стало кодом**. Не
формальную модель потока — её мы строили и она давала «создай класс без полей»; а план работ,
написанный по одному use case за раз, который человек читает на гейте и из которого режутся тикеты.

Единица работы — **use case**. Граф приложения, подграф ряби и поставка проходов A/B остаются
навигацией: они существуют, чтобы модель не бегала по репозиторию, и едут **проекцией на вопрос**,
а не целиком.

Архив снесённой трёхпроходной конструкции — `docs/attic/design.md`, `docs/attic/design-step-by-step.md`.

## 1a. Обе поставки 9B — склад для ролей, а не документ для человека

`design-graph.xml` и `data-flow.md` пишутся не затем, чтобы их читал человек: их назначение —
кормить дизайнеров 9d и 9e, и каждый берёт из них **проекцию на свой вопрос**, а не файл.

| артефакт | целиком | кому | что достаётся | доля |
|---|---|---|---|---|
| `design-graph.xml` | 17,3 КБ | 9d, общий дизайн группы | `<module>` только файлов своей группы: `configs/glossary` 2,1 КБ, `backup` 2,7 КБ | **12-15 %** |
| `data-flow.md` | 15,9 КБ | 9e, дизайнер use case | блоки `$START_FLOW` только своих сценариев: в среднем 1,1 КБ, максимум 1,9 КБ | **7-12 %** |

85-90 % каждого файла для конкретной роли — шум. Это тот же приём, что срезал 68 % байт ряби на
проекции изменения (D29a): граф полезен ПОСЛЕ того, как его срезали до вопроса.

Сегодня у `data-flow.md` машинного читателя нет вовсе: шаг 10 берёт `dod` из `design-graph.xml`
той же функцией `unitsByPath`, а шага 14, который резал бы из потока секции тикета, не существует.
Читатель появляется в 9e — и это условие, при котором файл вообще имеет смысл писать.

## 2. Лестница образца

Дизайнер не выдумывает структуру — он копирует ту, что в репозитории уже есть. Ступени, первая
сработавшая выигрывает:

| # | ступень | замер `eddi` |
|---|---|---|
| 1 | **узел СУЩЕСТВУЕТ** — образец не нужен, контекст это он сам плюс право `read` | 6 из 13 |
| 2 | **близнец по сущности** — тот же путь для другой сущности | `configs/snippets/*` для `configs/glossary/*` — 3 из 5 |
| 3 | **сосед по каталогу того же вида** — по общему суффиксу имени, затем просто каталог | `impl/CallerNamespaceResolver.java` для нового `impl/GlossaryNamespaceResolver.java` |
| 4 | **объявленное отсутствие** `<sample found="no"/>` — проектируем от use case, и это видно человеку | — |

**Правило близнеца пишется по ФОРМЕ пути, а не по одному сегменту.** Строгое «отличие в одном
сегменте» даёт на `eddi` ноль: имя сущности сидит и в каталоге, и в имени класса
(`glossary/mongo/GlossaryStore` против `snippets/mongo/PromptSnippetStore` — различий два).

## 3. Что проверяет машина

Структурно, без суждений о смысле:

| правило | подшаг |
|---|---|
| путь из `$START_COMMON` только упомянут, не переопределён | 9e |
| каждая строка `$START_NEEDS` резолвится в файл общей группы | 9e |
| у каждого пункта плана есть путь файла и строка «проверка» | 9e |
| путь пункта принадлежит узлам своего use case, общей группе или образцу | 9e |
| каждая нехватка либо принята в контракт, либо отклонена с причиной | 9f |

Пять правил вместо сорока. Всё, что требует суждения, решает человек на гейте.

## 5. Что есть в черновике, но не в конвейере

- **сборщик карточки** — скрипт вне репозитория, 4 секции из 6 заполняются верно;
- **поиск образца** — эвристика, см. §2;
- **наряд дизайнера** — 2 КБ инструкции, проверен ОДНИМ ручным прогоном на `qwen3.6-27b`: план на
  четыре файла с полями, сигнатурами, JAX-RS путями, коллекцией `glossaries`, командами проверки и
  именами тест-классов. **6 из 6** названных им классов в репозитории существуют — модель дочитала
  образец по путям из карточки, тела в наряд не клались.

## 6. Замеры, на которых стоит конструкция

| факт | число |
|---|---|
| узлов изменения на `eddi` | 13 — 6 существуют, 7 создаются |
| узлов, которые трогают ДВА и более use case | **8 из 13**; три из них — в восьми use case каждый |
| во сколько групп по пакету складываются эти 8 | **2**: `configs/glossary` (5 файлов), `backup` (3) |
| карточка одного use case против «карта + FRD целиком» | **10 КБ против 126 КБ** |
| наблюдённая коллизия общих узлов | `terms` вложенным классом в плане UC2 против отдельного `model/Term.java` у UC6-UC8 |
| ожидаемая цена на `eddi` | 2 + 12 = 14 вызовов роли, $0.3-0.6 (9A/9B стоят $0.12; прогон izi-flow до гейта 1 — $1.07) |

Коллизия — причина, по которой общий дизайн идёт ПЕРЕД роем: дубли предупреждаются, а не сводятся
задним числом.
