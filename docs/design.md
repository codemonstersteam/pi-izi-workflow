# Шаг 9 `design` — план доработки по дереву модулей

Место шага в полосе — `docs/workflow.md` §3.9; грамматики артефактов — `docs/data-flow.md`. Здесь —
устройство шага целиком, эмуляция на живых артефактах и статус каждой фазы.

Шаг 9 отвечает на один вопрос: **как меняется каждый модуль, чтобы требование стало кодом**.

**Единица плана — МОДУЛЬ (класс), а не use case.** Решение принято 17 августа после живого прогона
`ce2ede24`, где рой по use case дал дубль: `AbstractBackupService.java` понадобился и UC10, и UC12,
а канала выразить это у планировщика не было. Когда единица — модуль, дубль невозможен по
построению: модуль лежит ровно в одной партии, и решает его один вызов роли. Use case перестаёт
быть владельцем плана и становится строкой раздела: `closes: UC10 step 2`.

Архив предыдущих конструкций — `docs/attic/design.md`, `docs/attic/design-step-by-step.md`.

## 1. Data flow

```
ВХОД
  .agent/frd.xml          use case дословно: шаги, ветки отказа, дельты, поля, сценарии с узлами
  .agent/ripple.xml       подграф изменения: <module level> + <dep path> — ТОЛЬКО существующие файлы
  .agent/appgraph.xml     репозиторий: роли, декларации, api, сьюты
  .agent/design-graph.xml черновик контрактов прохода 9B

═════════════════════════ ① ДЕРЕВО МОДУЛЕЙ — скрипт, 0 токенов ═════════════════════════
вход:   frd.xml (сценарии несут nodes), ripple.xml
задача: собрать состав изменения и рёбра между модулями
выход:  modules[] = { путь, use case, существует|создаётся, deps, level }

  ЗАМЕРЕНО: узлы изменения ≠ модули ряби. На eddi узлов 13, а рябь знает из них 6 —
  остальные 7 СОЗДАЮТСЯ, и рябь их знать не может: она проекция существующей карты.
  Состав дерева даёт FRD; рябь ОБОГАЩАЕТ его тем, что знает: deps и level.

═════════════════════════ ② ПАРТИИ — скрипт, 0 токенов ═════════════════════════════════
вход:   modules[]
задача: разложить модули по ПАКЕТУ (каталог без impl|mongo|rest|model)
выход:  partitions[] = { slug, модули, их use case, их соседи }
инвариант: модуль ровно в одной партии — отсюда невозможность дубля

  Замер eddi: 13 модулей → 4 партии
    configs/glossary   5 модулей · 8 use case · соседей 0 (все создаются)
    backup             5 модулей · 3 use case · соседей 11
    modules/llm        2 модуля  · 1 use case · соседей 12
    modules/templating 1 модуль  · 1 use case · соседей 0

═════════════════════════ ③ КАРТОЧКА ПАРТИИ — скрипт, 0 токенов ════════════════════════
вход:   партия + frd.xml + appgraph.xml + ripple.xml + design-graph.xml
задача: срезать проекции — всё, что нужно ОДНОМУ вызову, и ничего больше
выход:  .agent/staging/parts/<slug>.txt

  $START_MODULES    — <module> партии из карты (у создаваемых пусто, и так и написано)
  $START_USECASES   — use case этих модулей ДОСЛОВНО: шаги, ветки отказа, дельты, поля
  $START_NEIGHBOURS — <dep> этих модулей из ряби, ПУТЯМИ: читай сам, правь минимально
  $START_SAMPLE     — путь файла того же вида в репозитории (лестница §3)
  $START_CHECK      — команда сьюта и шаблон имени тест-класса
  $START_DRAFT      — <module> партии из design-graph.xml, черновик

  Замер eddi (живые карточки ce2ede24): 9,5-18 КБ на партию против 126 КБ,
  которые весят карта и FRD вместе.

═════════════════════════ ④ ПЛАН ПАРТИИ — РОЛЬ, 1 вызов на партию ══════════════════════
вход:   карточка партии
задача: на КАЖДЫЙ модуль партии написать, как он меняется
выход:  .agent/staging/parts/<slug>.md

  ## <путь модуля>  (новый | правится)
  what: одна фраза
  fields: <имя>: <тип> — <зачем>        (класс данных; иначе «нет собственных»)
  signatures: <имя>(<параметры>) : <тип>
  calls: <путь> — зачем               (либо «нет» — но строка ОБЯЗАТЕЛЬНА)
  sample: <путь> — что повторяем
  closes: UC1 step 1 · UC4 step 2а
  verify: <команда> · <имя тест-класса>

═════════════════════════ ⑤ ГАРДРЕЙЛ ПАРТИИ — скрипт, 0 токенов ════════════════════════
вход:   staging-файл + партия
задача: судить СТРУКТУРУ, не смысл
выход:  блокеры (пусто = зелено) → промоут в docs/design/<slug>.md

  1. раздел на каждый модуль партии
  2. ни одного модуля чужой партии (сосед — можно, он объявлен в карточке)
  3. каждый use case партии назван хотя бы в одной строке «closes»
  4. у каждого раздела есть «verify» И «calls» (пусть «нет»)
  5. каждый путь в «calls» — модуль изменения, сосед или файл карты

  красный → блокеры роли, бюджет LOOPS; зелёный → промоут

═════════════════════════ ⑥ ПОЛНОТА — скрипт, после всех партий ════════════════════════
вход:   все docs/design/<slug>.md + frd.xml
задача: убедиться, что требование не потеряно
выход:  отказ с именами либо зелёный
  · каждый модуль изменения имеет раздел
  · каждый use case FRD назван хотя бы в одном «closes»
  · каждый шаг use case и каждая ветка отказа закрыты хотя бы одним разделом

═════════════════════════ ⑦ ПОРЯДОК — скрипт, 0 токенов ════════════════════════════════
вход:   разделы всех партий + рёбра карты
задача: построить очередь работ
выход:  топологический порядок модулей либо отказ с именами

  Рёбра — из ОБЪЯВЛЕННЫХ строк «calls:», написанных тем, кто решал модуль (D42: из потока
  очередь не выводится). Рёбра карты добавляются для существующих модулей.
  Круг → отказ, и чинит его роль: строки писала она.

═════════════════════════ ⑧ СБОРКА PLAN.md — скрипт, 0 токенов ═════════════════════════
вход:   разделы + порядок
выход:  PLAN.md — все модули в порядке работ, с шапкой: сколько модулей, каких use case
        касается каждый, чем закрывается

                                ГЕЙТ ЧЕЛОВЕКА

═════════════════════════ ⑨ ТИКЕТЫ — скрипт, шаг 14 ════════════════════════════════════
1 раздел = 1 тикет:  outputs = путь модуля · blocked_by = «calls» · DoD = «verify» ·
inputs = «sample» плюс зовомые модули
```

## 2. Контракт каждой фазы — `steps/design-data-flow.md`

Что приходит на вход фазы, что она обязана отдать, кто её исполняет и чем подтверждено, что SLM это
вытянет, — в одном месте: `steps/design-data-flow.md`. Здесь этого нет намеренно: правило живёт
там, где по нему пишут код.

Оттуда же — три вывода эмуляции, которые изменили конструкцию: состав дерева даёт FRD, а не рябь
(рябь знает 6 модулей из 13); инвариант «модуль ровно в одной партии» и есть доказательство
невозможности дубля; строка `calls:` обязана быть у каждого раздела, иначе очередь работ пустая —
замер дал 2 ребра на 8 разделов.

## 3. Лестница образца

Дизайнер не выдумывает структуру — он копирует ту, что в репозитории уже есть. Ступени, первая
сработавшая выигрывает:

| # | ступень | замер `eddi` |
|---|---|---|
| 1 | **модуль СУЩЕСТВУЕТ** — образец не нужен, контекст это он сам плюс право `read` | 6 из 13 |
| 2 | **близнец по сущности** — тот же путь для другой сущности | `configs/snippets/*` для `configs/glossary/*` |
| 3 | **сосед по каталогу того же вида** — по общему суффиксу имени, затем каталог | `impl/CallerNamespaceResolver.java` для `impl/GlossaryNamespaceResolver.java` |
| 4 | **объявленное отсутствие** — проектируем от use case, и это видно человеку | 0 на `eddi` |

**Правило близнеца пишется по ФОРМЕ пути, а не по одному сегменту.** Строгое «отличие в одном
сегменте» даёт на `eddi` ноль: имя сущности сидит и в каталоге, и в имени класса.
