# Шаг 10 `plan` — план работ

Место шага в полосе — `docs/workflow.md` §3.10, обоснования — `docs/concept.md` («План, критик,
гейт»). Здесь: вход, выход, откуда берётся узел плана, откуда порядок, откуда команда проверки, о чём
шаг спрашивает оператора и на чём встаёт.

Шаг **скриптовый и при этом с оператором** — первый такой в полосе. До него оператор жил только там,
где есть роль (`brd`, `intake`, `design`); `weight`, `ripple` и `graph` отказывали терминально,
потому что применить ответ внутри шага было некому. Здесь применить его есть кому: значение ответа
кладёт в артефакт САМ скрипт, роль не участвует (`docs/concept.md`, «Взаимодействие с оператором»).

## 1. Вход, выход, участники

| | |
|---|---|
| вход | `.agent/frd.xml` (`<touched>`, `<delta>`, `<scenario>`), `.agent/appgraph.xml` (рёбра, `<test>`, `<suite>`, ответы хребта), `.agent/mode`, `.agent/design-graph.xml` + `.agent/data-flow.md` (если шаг 9 отработал), ответы оператора, факт `git` — имя транка |
| выход | `.agent/plan-index.json` — DAG узлов работы |
| роль | нет — 0 токенов |
| гардрейл | `plan({})` (функция расширения) → `steps/plan/plan.mjs::newPlanIndex` |
| бюджеты | `QUESTIONS` / `QUESTION_ROUNDS` (вопрос оператору), `LOOPS` не тратит — пере-делегировать некого |
| оператор | есть, ОДИН вопрос: ключ задачи (`TASK-id`). Всё прочее выводится — §6 |

## 2. Что показали артефакты живого прогона

Форма `runbox/quarkus-rest-json-app-v2-t3` (отдельная страница карточки фрукта; `.agent/` целиком от
прогона шагов 1–9): `mode=minor`, четыре `<delta form="Added">`, четыре `<touched>`, два сценария,
дизайн-граф из четырёх узлов, `data-flow.md` с тремя маршрутами и четырьмя списками юнитов. Карта —
15 модулей, 8 рёбер, 2 сьюта, ноль `<cycle>`, `<toggles found="no"/>`, `<branching found="no"/>`,
`<contract found="no"/>`.

Четыре расхождения между тем, что о шаге 10 написано в `docs/workflow.md` §3.10, и тем, что эти
артефакты позволяют сделать. Три из них — блокирующие: правило неисполнимо на живом входе.

| # | что не сходится | цена |
|---|---|---|
| **A** | «DAG узлов» строится по `<dep>` дизайн-графа — а `<dep>` **ненаправлен**: `ripple.mjs` проецирует ребро карты в обе стороны (`link(e.from,e.to); link(e.to,e.from)`), и в `t3` дизайн-граф даёт `FruitResource ↔ Fruit` и `FruitResource ↔ fruits.html` | топосорт невозможен на ПЕРВОМ же живом входе: два цикла из двух узлов |
| **B** | «команда проверки узла = `suite.one` с подставленным файлом теста узла» — но `<test>` в карте есть у ОДНОГО узла из четырёх (`FruitResource`); у `Fruit.java`, `fruits.html` и создаваемого `fruit-card.html` его нет и быть не может | ¾ узлов плана остаются без команды, а «узел закрыт» на шаге 15 судит именно она |
| **C** | «тронутая внешняя io-точка при найденной спеке → узел `spec`», «вес `minor` → узел тогла» — а карта отвечает `found="no"` на оба; вопрос оператору объявлен, но не сказано, чем ответ становится в артефакте | либо invented-default в узле плана, либо тихо пропущенный тогл при `minor` — то самое «способность уехала включённой» |
| **D** | «имя ветки — по соглашению ИЗ ГРАФА» — соглашение это ПРОЗА («feature/<issue>-<slug>»), из неё имя ветки машиной не выводится; на `t3` соглашения нет вовсе | имя ветки сочиняет скрипт, то есть тот же invented-default, только в git |

Пятое расхождение не блокирует, но названо: «проекция узла в тикет влезает в окно SLM» считается
формулой шага 14, а шага 14 нет — считать нечем, и обобщать под него запрещено (`CLAUDE.md`,
`$START_FORBIDDEN`). Отложено с триггером (`docs/triggers.md`).

## 3. Узлы плана — из ШИРИНЫ изменения, а не из дизайн-графа

Множество узлов работы уже посчитано шагом 8 и называется **шириной**: `<touched>` ∪ узлы
`<delta node>`, минус тестовые узлы (`docs/ripple.md` §3). План берёт то же множество и берёт его
**из того же кода** — `changeWidth({frd, tests})` выносится из `newRipple` в экспорт
`steps/ripple/ripple.mjs`, второй копии правила не заводится (`standards/code.md` §1).

Почему не дизайн-граф: он существует только при `design=needed`. Вход шага объявлен как
«`design-graph.xml` ЛИБО `frd.xml`», и единственный источник, который есть ВСЕГДА, — FRD. Дизайн-граф
даёт узлу контракт и `delta`, но не список узлов.

`kind` назначается по тому, что уже решили шаги 6–8, одним предикатом на строку:

| `kind` | когда | сколько на `t3` |
|---|---|---|
| `doc` | путь узла ширины оканчивается на `.md`/`.adoc`/`.rst` | 0 |
| `code` | всякий прочий узел ширины | 4 |
| `scenario` | `<scenario>` FRD, чьи `nodes` пересекают больше одного узла `code` **ИЛИ** хоть один узел, не закрывающий себя сам | 2 (`S1`, `S2`) |
| `toggle` | `mode == "minor"` И в карте `<toggles mechanism="…"/>` | 0 — механизма в репозитории нет |

`spec` в этом срезе **не заводится** — §6.

**Одноузловой сценарий узлом не становится — пока его узел закрывает себя сам.** Есть свой `<test>` в
карте ⇒ различают юниты этого узла (`$START_TESTS` того же пути в `data-flow.md`), и второй владелец
у одного теста не нужен. Нет своего теста (страница, шаблон) ⇒ владельца нет вовсе, и сценарий им
становится, даже будучи одноузловым. Цена обратного правила названа фактом — §12.

## 4. Порядок — направленные рёбра КАРТЫ, а не `<dep>`

Расхождение A чинится сменой источника. Рёбра `appgraph.xml` направлены и посчитаны скриптом
(`<edge from to>`, `from` использует `to`), поэтому зависимость узла плана — это `to` его исходящих
рёбер, а порядок исполнения — топосорт по ним. На `t3` это даёт ровно то, что и должно:

```
Fruit.java (level 4) ─◀── FruitResource.java (level 3) ─◀── fruits.html (level 1)
                                    ▲
                       fruit-card.html (новый, рёбер карты нет)
```

Четыре правила, и все четыре — подстановка, а не суждение:

1. **`code → code`**: ребро карты `from → to`, оба конца — узлы плана ⇒ `from` зависит от `to`.
2. **Создаваемый узел** (`<delta new="yes">`) рёбер карты не имеет по определению: он зависит от
   ВСЕХ своих `<dep>`-соседей из дизайн-графа, которые есть в карте. Ненаправленность `<dep>` здесь
   безвредна — новый узел позже любого существующего, направление известно заранее.
   Шаг 9 пропущен ⇒ дизайн-графа нет ⇒ у создаваемого узла зависимостей нет вовсе, и это объявлено,
   а не домыслено.
3. **`scenario` зависит от всех узлов, которые различает** — он зеленеет последним, владелец у теста
   ровно один (`docs/concept.md`, «API-first — ребро, а не обещание»).
4. **`code` с дельтой зависит от узла `toggle`** — способность включает флаг, значит флаг заведён
   раньше способности. Тем же ребром, что `spec` в концепте: очередь держит DAG, а не память.

**Циклы не разрешаются здесь.** Карта объявляет `<cycle modules="…">` на шаге 5; узел плана внутри
объявленного цикла — терминальный отказ `cycle` с именами модулей. Разрывать цикл, который
репозиторий имеет годами, шаг 10 не станет — это отдельная работа со своим гейтом, ровно как
отсутствующий тест-сьют на шаге 5.

## 5. Команда проверки — из `<test>` и `<suite>`, а «нечем закрыть» — отказ

Расхождение B: команда выводится только там, где карта назвала `<test>`. Остальное — не догадка, а
**объявленное покрытие через сценарий**.

| узел | команда | на `t3` |
|---|---|---|
| `code` с `<test path suite>` | по команде на КАЖДЫЙ `<test>`: `suite.one` с подставленным `{class}`/`{path}`; `one` пуст ⇒ `suite.cmd` целиком, и это записано в узле | `FruitResource`: `mvn test -Dtest=FruitResourceTest` + `mvn verify -Pnative -Dit.test=FruitResourceIT` |
| `code` без `<test>` | своей команды НЕТ (`check: []`), и узел обязан быть различён хотя бы одним узлом `scenario` — иначе отказ `uncovered-node` | `Fruit`, `fruits.html`, `fruit-card.html` — все три различает `S1` или `S2` |
| `scenario` | `suite.cmd` ЦЕЛИКОМ каждого сьюта, объявленного у различаемых узлов (файла теста ещё нет — подставлять в `one` нечего); НИ ОДИН узел теста не объявил ⇒ все `<suite>` карты | `mvn test` + `mvn verify -Pnative` |
| `toggle` | те же команды, что у сценариев, различающих выключаемые узлы: тогл проверяется сценарием «выключено ⇒ прежнее поведение», а не своим тестом | те же две |
| `doc` | команды нет; документ судит человек на гейте | — |

`{class}` — базовое имя файла без расширения, `{path}` — репо-относительный путь. Оба подставляются
скриптом; шаблон назвал скаут на шаге 4, и второго словаря форм прогона не заводится.

**Сценарий без единого теста у своих узлов берёт все сьюты карты.** Сквозной сценарий проверяется
прогоном приложения, а какие сьюты у репозитория есть — факт, установленный шагом 5. Набор грубый
(шаг 16 всё равно гоняет все), зато выведенный и записанный в узел: оператор видит на гейте, во что
обходится закрытие сценария. Отказ `no-suite` остаётся ровно для карты, где сьютов нет вовсе, — а
такую карту шаг 5 не выпускает.

**Почему `uncovered-node` — отказ, а не пометка.** Узел без команды и без сценария нечем закрыть на
шаге 15 и нечем поймать на шаге 16: «сделано» скажет только роль, то есть самосертификация, запрещённая
правилом 2 концепта. Отказ терминальный: чинится это на шаге 6 (сценарий, различающий узел), где есть
рельса починки.

## 6. Вопрос оператору ровно ОДИН — ключ задачи

Спрашивается только то, что **не выводится ни из репозитория, ни из стандарта**: идентификатор
задачи. Всё остальное — имя ветки, её префикс, база, тогл — выводится, и потому не спрашивается.

| вопрос | когда | чем становится ответ |
|---|---|---|
| **ключ задачи** (`TASK-id`) | ВСЕГДА | `branch.task`; из него имя ветки, и он же едет параметром в тикет (14) и в сообщение коммита (17) |

Формулировка — константа модуля, байт в байт одинаковая от прогона к прогону, поэтому ответ на диске
узнаётся дословным сравнением (`askOperator`, `core/answers.mjs`), как у роли:

> Ключ задачи для этой работы? Формат `TASK-номер` — 2–20 заглавных латинских букв, дефис, число
> 1..999999 (например `DOS-42`). Он станет именем ветки `feature/DOS-42`, приедет в каждый тикет и в
> сообщение коммита.

**Ответ проверяется кодом, а не надеждой.** Регулярка `^[A-Z]{2,20}-[0-9]{1,6}$` живёт в ОДНОМ месте —
константе `steps/plan/plan.mjs`, и тест сверяет её с навыком `steps/plan/git-conventions.md`; не
подошло ⇒ это ещё один круг вопроса, а не запись мусора в артефакт (`standards/code.md` §7:
проверяемый антецедент проверяется КОДОМ). Ключ, набранный человеком, — единственное место среза, где
значение приходит извне; всё прочее имеет источником файл.

**Переспрос обязан быть ДРУГИМ вопросом.** Ответ не подошёл ⇒ вопрос уезжает заново, но с
отвергнутым значением и причиной внутри. Иначе переспроса не существует вовсе: `askOperator` считает
вопрос отвеченным по его тексту, ответ на диске уже лежит, и круги сгорают вхолостую — цена известна
фактом, §12. Ответ при этом узнаётся по ПРЕФИКСУ вопроса, поэтому первый вопрос и любой переспрос
адресуют одно значение, а текст отказа служит инструкцией по починке.

### Имя ветки выводится по стандарту, а не спрашивается

Стандарт — навык `git-conventions` из `izi-flow`, тот самый, что `docs/concept.md` объявляет
наследуемым в первой строке. Он приведён к форме этого репозитория и **урезан до исполнимого
сегодня** — `steps/plan/git-conventions.md`: формат коммита, тело PR и ревью описывают шаги 13–17,
которых нет, а соглашение, которое никто не проверяет, есть украшение (`standards/role.md`). Они
приедут со своим шагом, в тот же файл. Из навыка берутся ровно две вещи:

```
имя = <префикс>/<TASK-id>          префикс: mode == "patch" ⇒ bugfix, иначе feature
база = транк                       факт git, не мнение
```

Префикс — производная ВЕСА, а не новое суждение: `patch` есть «только `Fixed`», то есть исправление
дефекта; `minor`/`major` — функциональность. Второго словаря для этого не заводится.

**База — факт.** Внутренний io-помощник `gitTrunk(root)` в `ext/index.mjs` (не глобал песочницы —
воркфлоу транк не читает, его читает функция `plan`) возвращает имя транка:
`git symbolic-ref --short refs/remotes/<remote>/HEAD`, при отсутствии remote — `main` либо `master`
среди локальных рефов, при отсутствии обоих — отказ `no-trunk` (не «текущая ветка»: текущей может
быть что угодно). На `t3` — `main`, remote отсутствует. Сама ветка здесь НЕ режется: это шаг 13.

`remote` в артефакт НЕ едет: шаг 13 тянет его заново и СВЕЖИМ, сразу после `fetch`, и пишет в свой
`branch.json`. Копия здесь устарела бы к моменту использования — тот же довод, по которому
`fanin`/`fanout` не копируются в подграф ряби (`docs/ripple.md` §4).

**Соглашение репозитория в имени НЕ участвует.** `<branching branches commits>` карты, если найдено,
копируется в план полем `branch.repoConvention` и печатается в лог — расхождение со стандартом судит
человек на гейте, а не разбирает скрипт. Разбирать прозаический шаблон (`feature/<issue>-<slug>`)
значит завести классификатор шаблонов имён ради ветки, которую всё равно режет шаг 13.

### Тогл берётся из карты, а не у человека

Вопроса о тогле нет вовсе. Механизм — тот же `found`-ответ хребта, что раннер тестов, и решается он
так же:

| `<toggles>` в карте | что делает план |
|---|---|
| `found="no"` | узел `toggle` НЕ заводится, `gaps: ["toggle"]`, лог называет пробел вслух |
| `mechanism="…"` | узел `toggle` с этим механизмом, `source: "graph"`; каждый узел `code` с дельтой от него зависит |

**Приоритет удалённо переключаемому механизму** объявлен, но выразить его сегодня не на чем: хребет
несёт ОДИН элемент с одним атрибутом (`<toggles mechanism="…"/>`, `steps/scope/part.mjs::SPINE_ANSWERS`),
выбора между двумя механизмами в грамматике не существует. Расширение до списка с признаком
`remote="yes|no"` стоит правки роли скаута, наряда хребта, `part.mjs` и `graph.mjs` — и ни одного
живого репозитория с двумя механизмами не наблюдалось. Отложено с триггером (`docs/triggers.md`):
первый репозиторий, где механизмов больше одного.

**Почему «не найден ⇒ нет», а не вопрос.** Тогл — не решение о продукте, а свойство репозитория:
если выключать нечем, то нечем, и заводить первый тогл — самостоятельная работа со своим гейтом,
ровно как заводить первый тест-сьют (`docs/concept.md`, «Исключение из „не найден“ — тесты»). Пробел
объявлен в артефакте и в логе; молчания не остаётся.

**Спека — тем же правилом:** `<contract found="no"/>` ⇒ узла `spec` нет, `gaps: ["spec"]`, лог. Узел
появится вместе с репозиторием, у которого спека и её валидатор есть, и будет измерен на нём.

## 7. Контракт шага

```
.agent/frd.xml + .agent/appgraph.xml + .agent/mode [+ .agent/design-graph.xml] + ответы + git
   │  plan({})                ext/index.mjs — единственный io: чтение, gitTrunk, запись/СТИРАНИЕ одного
   ▼  parseFrd(xml)           steps/intake/frd.mjs — тот же разбор, второй копии грамматики нет
   ▼  parseMap(xml)           steps/intake/map.mjs — узлы, тесты, рёбра
   ▼  parseDesign(xml)        steps/design/design.mjs — `<dep>` создаваемого узла, если шаг 9 был
   ▼  changeWidth({frd,tests})steps/ripple/ripple.mjs — ШИРИНА, вынесенная из newRipple
   ▼  newPlanIndex({ frd, map, mode, design, trunk, answers })   steps/plan/plan.mjs — ЧИСТОЕ ядро
   ▼
Result<{ index, nodes[], order[], gaps[] }, "no-mode" | "no-width" | "cycle" | "uncovered-node"
                                          | "no-suite" | "no-trunk" | "ask">
   ├── ok   → `.agent/plan-index.json` + log: `plan: узлов 6 (code 4, scenario 2), ветка …, пробелы …`
   ├── ask  → вопрос о ключе задачи едет в askOperator, ответ ложится в .agent/answers.md,
   │          шаг перезапускается тем же вызовом — как круг вопросов у intake
   └── err  → `.agent/plan-index.json` СТЁРТ, полоса встаёт `blocked` с уликой
```

Стирание артефакта при отказе — тот же довод, что на шагах 7 и 8 (`docs/weight.md` §4): `newRun`
уносит в `.agent/prev` состояние прогона, но не артефакты, и вчерашний план пережил бы сегодняшний
отказ.

### Грамматика `.agent/plan-index.json`

JSON, а не XML: артефакт пишет скрипт и читают скрипт (14) и человек (12) — грамматики, которую
разбирала бы роль, здесь нет. Прецедент — `.agent/survey-plan.json`.

```json
{
  "grammar": 2,
  "mode": "minor",
  "branch": { "task": "DOS-42", "name": "feature/DOS-42", "base": "main", "source": "operator-answer" },
  "gaps": ["toggle", "spec"],
  "order": ["src/.../Fruit.java", "src/.../FruitResource.java", "src/.../fruits.html",
            "src/.../fruit-card.html", "scenario:S1", "scenario:S2"],
  "nodes": [
    { "id": "src/main/java/org/acme/rest/json/FruitResource.java", "kind": "code",
      "new": false, "delta": ["GET /fruits/{id} (Added)", "GET /fruits (Added)"],
      "why": "эндпоинт по имени",
      "dod": ["GET /fruits/{id} -> Fruit", "GET /fruits/{id} -> 404 NOT_FOUND"],
      "deps": ["src/main/java/org/acme/rest/json/Fruit.java"],
      "check": [ { "suite": "unit", "cmd": "mvn test -Dtest=FruitResourceTest" },
                 { "suite": "component-native", "cmd": "mvn verify -Pnative -Dit.test=FruitResourceIT" } ],
      "coveredBy": [] },
    { "id": "src/main/resources/META-INF/resources/fruit-card.html", "kind": "code",
      "new": true, "delta": ["GET /fruit-card.html (Added)"],
      "deps": ["src/.../FruitResource.java", "src/.../Fruit.java"],
      "check": [], "coveredBy": ["scenario:S1"] },
    { "id": "scenario:S1", "kind": "scenario", "scenario": "S1",
      "deps": ["src/.../FruitResource.java", "src/.../Fruit.java", "src/.../fruit-card.html"],
      "check": [ { "suite": "unit", "cmd": "mvn test" },
                 { "suite": "component-native", "cmd": "mvn verify -Pnative" } ] }
  ]
}
```

Узла `toggle` на `t3` нет — механизма в репозитории не найдено, и пробел объявлен в `gaps`. Его форма
там, где он есть: `{ "id": "toggle", "kind": "toggle", "mechanism": "<из <toggles mechanism>>",
"source": "graph", "deps": [], "check": [<команды сценариев>] }`, и каждый узел `code` с дельтой
получает `"toggle"` в своих `deps`.

**`dod` и `why` — то, чем тикет СДАЁТСЯ (grammar 2).** `check` это команда ЗАКРЫТИЯ: она говорит, чем
узел проверяют, и до появления теста зелена. `dod` — юниты узла, «1 happy + Σ ветвей», выведенные
шагом 9 (`steps/design/design.mjs::unitsByPath`) и ПЕРЕНЕСЁННЫЕ сюда, а не посчитанные заново: тикет
режется из плана, и без DoD исполнителю не сказано, какие тесты причитаются. Шаг 9 пропущен ⇒
`dod: []` — объявлено, как `deps: []` у создаваемого узла. `why` — слова самого FRD (`<touched why>`)
о том, зачем узел тронут; без него узел, названный только `<touched>`, приезжает в тикет немым.

Цена молчания измерена прогоном `d8ef8c60`: узел ресурса нёс команду `mvn test -Dtest=FruitResourceTest`,
в классе которой не было ни новой операции, ни её ветки отказа, — команда зелена ДО работы; узел
страницы приехал с `delta: []` и не сказал исполнителю ничего, хотя FRD объявлял работу дословно.
Оба факта уже лежали на диске.

`id` узла-файла — репо-относительный путь, тот же ключ, что у карты, FRD и ряби. У узлов, которых в
карте нет, ключ префиксован родом (`scenario:S1`, `toggle`) — файла за ними не стоит, и путь им
выдумывать не из чего.

## 10. Чего шаг не делает

Не режет ветку (13) и не пишет тикеты (14) — он их ИМЕНУЕТ и упорядочивает. Не пересматривает вес
(7), рябь (8) и контракты узлов (9). Не судит качество плана — это критик, шаг 11. Не режет узел по
бюджету окна тикета: формула проекции живёт в шаблонах шага 14, которых нет, и считать её сейчас
значит обобщать под несуществующий шаг (`docs/triggers.md`). Не заводит ни первую спеку, ни первый
тогл: чего в репозитории нет, того нет — пробел объявляется, а работа по нему заводится отдельно.

## 11. Швы

Один тест на правило, которое может тихо деградировать (`docs/workflow.md` §4):

- порядок берётся из НАПРАВЛЕННЫХ рёбер карты: `FruitResource` после `Fruit`, `fruits.html` после
  `FruitResource`. Краснеет ровно тогда, когда источником делают `<dep>` (расхождение A: взаимные
  `<dep>` `t3` дадут цикл)
- создаваемый узел (`new="yes"`) без рёбер карты получает зависимости из `<dep>` дизайн-графа; шаг 9
  пропущен ⇒ `deps: []`, а не отказ
- узел `code` без `<test>` и БЕЗ сценария → `uncovered-node`; он же со сценарием → `check: []` и
  `coveredBy`. Краснеет при возврате правила «команда всегда выводится из `suite.one`» (расхождение B)
- `one` пуст → команда сьюта целиком, и `suite` назван в узле (регрессия к молчаливой деградации
  стоимости)
- `mode=minor` + `<toggles found="no"/>` → узла `toggle` нет, `gaps` содержит `toggle`; тот же вес с
  `<toggles mechanism="…"/>` → узел есть, `source: "graph"`, и каждый узел `code` с дельтой от него
  зависит. Краснеет, если механизм начнут спрашивать у оператора или сочинять
- ключ задачи: `DOS-42` проходит, `dos-42` / `DOS-` / `D-1` / пусто — нет, и это ещё один круг
  вопроса, а не запись в артефакт; имя ветки при `mode=patch` — `bugfix/…`, иначе `feature/…`
- шов навыка: константа регулярки в `steps/plan/plan.mjs` встречается в `steps/plan/git-conventions.md`
  ДОСЛОВНО — краснеет, когда правят одно место из двух (приём `steps/brd/brd.test.mjs`)
- путь `*.md`/`*.adoc`/`*.rst` в ширине → `kind: "doc"`, `check: []`, сценария не требует (на `t3`
  таких узлов ноль — шов синтетический, и это законно: он краснеет от правки классификатора)
- сценарий на ОДНОМ узле кода узлом плана не становится; на двух и больше — становится и зависит от
  обоих
- `<cycle>` среди узлов плана → `cycle`; ноль сьютов у сценария → `no-suite`
- io-шов в `ext/index.test.mjs`: отказ ⇒ на диске нет `.agent/plan-index.json`, даже если он лежал от
  прошлого прогона. Доказывается реинтродукцией: убрать стирание — краснеет
- шов вопроса: формулировка вопроса скрипта БАЙТ В БАЙТ стабильна между вызовами — иначе ответ на
  диске не узнаётся и оператора переспрашивают вечно (цена этого известна: прогон `46edab60`)

## 12. Живое доказательство (S29) и что оно вскрыло

Форма `runbox/quarkus-rest-json-app-v2-t3`, прогон `03b598c7-ba1d-4bec-9903-5beece74f583`, сессия
`019ff78f`. Полоса дошла до десятого шага за один заход: 5 запусков ролей, 203 641 токен. Числа
читаются из `journal.json`, не из вывода модели:

```
intake: deltas=2 unknown=0 scenarios=2 touched=3
weight: mode=minor из GET /fruits/{name} (Added), GET /fruit-card.html (Added)
ripple: design=needed узлов 3 из 17 (затравок 2)
design: узлов 3, маршрутов 3, списков юнитов 3
plan:   ask → checkpoint plan-q1 → ответ оператора
```

**Что подтвердилось.** Вопрос скриптового шага доехал до оператора ДОСЛОВНО, рельса
`setPending → checkpoint → answers → clearPending` отработала на шаге без роли, а отказ СТЁР
`.agent/plan-index.json`. Пять узлов вместо шести, обещанных §8: тот FRD решил задачу через
query-параметр и `Fruit.java` не тронул вовсе — оба числа верны, они про разные FRD.

**Дефект 1: круги сгорают без вопроса.** Оператор ответил `T3-1` — ключ, который регулярка отвергает
(до дефиса только буквы). Дальше журнал показывает механику дословно:

```
plan/1 → ask · setPending · checkpoint plan-q1 → true · ответ записан · clearPending
plan/2 → ask · setPending · answers · clearPending      ← БЕЗ checkpoint
plan/3 → ask · setPending · answers · clearPending      ← БЕЗ checkpoint
plan/4 → круг 4 > 3 → err(question) «кругов уточнения больше 3»
```

`askOperator` судит «отвечено» по ТЕКСТУ вопроса, шаг судит ответ РЕГУЛЯРКОЙ. Ответ на диске лежит —
значит переспроса не будет никогда: три круга ушли за секунды, оператора спросили один раз и не
сказали, почему ответ не взяли. Починка: переспрос несёт отвергнутое значение и причину, то есть
является ДРУГИМ вопросом; ответ узнаётся по ПРЕФИКСУ (`KEY_QUESTION`), поэтому и первый вопрос, и
любой переспрос адресуют одно значение. Текст отказа стал инструкцией по починке — то же правило,
что шаг 6 получил после прогона `6889fc3f` (`docs/design.md` §9).

**Дефект 2: два правила этого шага противоречили друг другу.** FRD различил `fruits.html` сценарием
над ОДНИМ узлом. Страница дельты не несёт (контракта не двигает, `docs/ripple.md` §3) и `<test>` в
карте не имеет — иметь не может. Правило §3 выбрасывало одноузловой сценарий, правило §5 требовало
сценарий для узла без теста: план отказал `uncovered-node` на FRD, который описал работу верно.
Третья грань того же: у сценария, чьи узлы теста не объявили, неоткуда взять команду — `no-suite`.
Починка — §3 и §5 в нынешней формулировке: сценарий владеет тестом там, где владельца иначе нет, а
его команда при отсутствии тестов у узлов берётся из всех `<suite>` карты.

Оба дефекта — этого среза, оба нашёл ПЕРВЫЙ живой прогон, и ни один не был виден юнитам: фикстура
шла от FRD прошлого прогона, где `fruits.html` входил в трёхузловой сценарий. Швы на оба —
`steps/plan/plan.test.mjs`, доказаны реинтродукцией.

**Зелёный повтор — прогон `c6bc2e54-c222-4541-9f76-0eb4d7dc4113`, сессия `019ff7d4`.** Та же форма,
починки на месте, 15 минут, 5 запусков ролей, 164 112 токена (вдвое быстрее и дешевле первого: обе
клетки разведки взялись из кэша `.izi/parts`, скаут не звался ни разу). Числа из `journal.json`:

```
function/plan/1 → { ok:false, ask:true, subject:"Ключ задачи…" }     вопрос уехал оператору
function/plan/2 → { ok:true, branch:"feature/IZI-3", base:"main",
                    nodes:5, code:3, scenario:2, gaps:["toggle","spec"] }
result.json     → { track:"ok", artifact:".agent/plan-index.json" }
```

Порядок вышел `FruitResource → fruits.html → fruit-card.html → S1 → S2` — ни одного цикла на живом
дизайн-графе, где `<dep>` взаимны, что и есть доказательство §4. Обе починки сработали: ключ прошёл
с первого раза (переспрос не понадобился), а `fruits.html` — узел без дельты и без своего теста —
закрыт сценарием `S1`, а не отказом. Пробелы `toggle` и `spec` объявлены в артефакте и в логе.

Шаги 6-8 дали числа, **совпавшие с первым прогоном байт в байт** (`deltas=2 unknown=0 scenarios=2
touched=3`, `mode=minor`, подграф из 3 узлов) — при том, что роль задала ДРУГИЕ шесть вопросов и
получила другие ответы. Расхождение приезжает из требования, а не из формулировок роли.

**Цена наблюдения.** Провайдер (`openrouter/qwen/qwen3.6-27b`) обрывал роль пять раз подряд
(`Provider error: This operation was aborted` на `gilb`, `scout`, `intake`×2, `designer`), каждый раз
