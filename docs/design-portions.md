# Шаг 9 порциями: что режется, что судится и когда

Что здесь: data flow шага 9 по шагам — с порциями, их проверкой в момент написания и склейкой.
Выверено по коду 20.08.2026. Правило, вокруг которого всё построено: **проверка стоит там, где можно
починить, и как можно раньше; одна проверка — ровно один раз.**

Граница «резать / не резать» — три условия ВМЕСТЕ:
① выход роли больше ~50 строк · ② есть независимая единица · ③ боль ЗАМЕРЕНА (минуты, обрывы,
потеря всей работы). Два из трёх — не режем.

---

## Шаг 9A — словарь значений (`valuer`)

    вход       .agent/frd.xml · .agent/ripple.xml
    выход      .agent/values.xml (50 строк на eddi)
    скрипт     ext::design{skeleton} → steps/design/values.mjs::valuesSkeleton
    роль       steps/design/valuer.md · наряд steps/design/order-values.tpl
    порции     НЕТ — выход 50 строк, боль не замерена

`pre:` шаг 6 закрыт, шаг 8 отработал.
`post:` каждая строка скелета на месте, пустые заполнены.

**Гардрейл** `checkValues`: состав считает скрипт — строка пропала → «строки vN нет в файле»;
строка есть, но не читается (сырой `<` в значении атрибута) → **отдельный блокер** с заменой
(`&lt;`), потому что «строки нет» о видимой строке — ложь, и роль уходит в петлю.

**→ модели:** блокеры + её собственный прошлый файл + скелет.

## Шаг 9B — цепочки (`router`), ПОРЦИЯМИ

    вход       .agent/frd.xml · .agent/values.xml
    скрипт     ext::design{skeleton} → routesSkeleton → splitRoutes(cap=4)
    пишет      .agent/staging/chains-skeleton.xml  и порции …~1 …~2 …~3 …~4
    роль       steps/design/router.md · наряд steps/design/order-chains.tpl
    порции     ДА: 13 маршрутов → 4 порции (замер: один вызов = 27 КБ наряда, 4-9 минут, зависания)

**Единица — маршрут.** Цепочка идёт от начала use case до его конца и о соседних не знает: резать
можно где угодно, лишь бы каждая доехала целой.

Цикл по порциям, и в КАЖДОЙ итерации:

    ① наряд порции: SKELETON = её кусок (2 КБ вместо 6,8 КБ), PREVIOUS = её прошлый ответ
    ② роль пишет .agent/staging/chains.xml~<n>
    ③ СУД ПОРЦИИ СРАЗУ: design({pass:"chains", path: mine, slice: skeleton~<n>})
       правила: шаги непусты · узлы только из nodes сценария · значения только из словаря ·
                последний шаг отдаёт конец use case
       красное → блокеры возвращаются ЭТОЙ порции, `n--`, соседние не трогаются

    после всех порций:
    ④ chainsJoin — склейка. Порция не написана → ОТКАЗ с её номером, не тихая потеря
    ⑤ СУД ЦЕЛОГО: design({pass:"chains", path, composed:true}) — ТОЛЬКО состав:
       не пропал ли маршрут, не появился ли лишний. Шаги и узлы не судятся повторно
    ⑥ зелено → assemble → .agent/design-graph.xml + .agent/data-flow.md

`post:` пара собрана; `unstepped` пуст — через каждый узел изменения прошла цепочка.

## Шаг 9 фазы ①②③ — партии и карточки (`parts`)

    вход       .agent/frd.xml · .agent/ripple.xml · .agent/appgraph.xml · .agent/data-flow.md
    скрипт     ext::parts → partsOf (партии) → groupsOf (порции по ЦЕПОЧКАМ)
    пишет      .agent/staging/parts/<slug>.txt      — карточка партии
               .agent/staging/parts/<slug>~<n>.txt  — карточка порции
               .agent/staging/parts/<slug>~<n>.flow — цепочки ЕЁ модулей (flowFor)
    роли       нет, 0 токенов

**Почему по цепочкам.** Строка `calls:` раздела — факт потока: кто идёт следом, того и зовут.
Разлучить соседей по цепочке значит отобрать у роли единственный источник этой строки.
Замер на eddi: 12 модулей → 3 порции, и они легли по слоям работы сами собой (CRUD · модель и
подстановка · экспорт-импорт).

## Шаг 9 фаза ④ — план партии (`core-designer`), ПОРЦИЯМИ

    роль       steps/design/core-designer.md · наряд steps/design/order-part.tpl
    порции     ДА: 12 модулей → 3 порции (замер: один вызов = 63 КБ наряда, 155 строк, 5-9 минут,
               обрывы, пять красных кругов подряд)

Цикл по порциям, в КАЖДОЙ итерации:

    ① наряд порции: CARD = карточка порции · FLOW = ЕЁ цепочки · PREVIOUS = её прошлый ответ
       ГЛАВНОЕ ПРАВИЛО стоит В НАЧАЛЕ наряда и повторено В КОНЦЕ: `calls:` берётся ИЗ ЦЕПОЧЕК,
       с примером верно/неверно. Середину наряда слабая модель читает по диагонали — проверено
       трижды на живых прогонах
    ② роль пишет .agent/staging/parts/<slug>~<n>.md
    ③ СУД ПОРЦИИ СРАЗУ: part({slug, path: mine, slice: n})
       правила: раздел на каждый модуль ПОРЦИИ · чужих модулей нет · у каждого «зовёт» и
                «проверка» · вызов — адрес · по-английски · без HTML-сущностей
       красное → блокеры ЭТОЙ порции, `n--`, соседние (уже зелёные) не переписываются

    после всех порций:
    ④ partJoin — склейка: заголовок партии один, разделы в порядке порций, ничей текст не правится
    ⑤ СУД ЦЕЛОГО: part({slug, path, composed:true}) — ТОЛЬКО правила целого:
       все use case закрыты · дублей модулей нет · модуль связан с изменением
       (блокер называет соседа по цепочке поимённо: «перед ним идёт LlmTask.java — допиши ЕМУ»)
    ⑥ зелено → promote → task/<KEY>/design/<slug>.md

## Что где проверяется — таблица без повторов

| правило | порция | целое |
|---|---|---|
| шаги маршрута непусты, узлы из сценария, значения из словаря | ✔ | — |
| состав маршрутов (не пропал, не лишний) | — | ✔ |
| раздел на каждый модуль порции, чужих нет | ✔ | — |
| у раздела есть `calls`, `verify`, `declares`; вызов — адрес | ✔ | — |
| текст английский, без HTML-сущностей | ✔ | — |
| все use case закрыты по шагам | — | ✔ |
| дублей модулей между порциями нет | — | ✔ |
| модуль связан с изменением (его зовут либо он зовёт) | — | ✔ |

Ни одна строка не стоит в обоих столбцах: это и есть «после склейки не проверять то, что уже
проверено».

## Чем доказано

`node --test` — 612 зелёных. Швы с обратным доказательством (сломал — красное, вернул — зелёное):

- порция судится СВОИМИ правилами — включил ей правила целого, тест краснеет;
- целое судит ТОЛЬКО своё — включил ему порционные правила, тест краснеет;
- склейка цепочек не судит шаги заново — убрал ранний выход, тест краснеет;
- порция карточки судится в момент написания — убрал суд из цикла, тест краснеет;
- красная порция переписывается АДРЕСНО (`n--`), соседние не трогаются;
- пропущенная порция — отказ с её номером, а не тихая потеря;
- склейка маршрутов возвращает исходник байт в байт (замер на живом скелете: 13 → 4 порции → 13).
