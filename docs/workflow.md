# Как работает workflow izi-pi

Состояние: **есть** — работает и покрыто тестами · **новое** — этим концептом добавляется.

### 1. `task` — оператор кладёт требование · human · **есть**
- **вход:** — (внешний: человек)
- **выход:** `TASK.md`
- **проверка:** `checkTask({})` (функция расширения) → `steps/task/task.mjs::checkTaskText` —
  непуст, ≤300 строк
- **оператор:** кладёт файл. Красный чек — терминальный `err(blocked)`, роль не зовётся вовсе: у
  этого шага роли нет, чинит человек

### 2. `brd` — сырое требование → измеримый BRD · role `gilb` · **есть**
- **вход:** `TASK.md`, `.agent/answers.md`
- **выход:** `.agent/brd.md` (через `.agent/staging/brd.md`)
- **проверка:** `checkBrd({ path: ".agent/staging/brd.md" })` (функция расширения) →
  `steps/brd/brd.mjs::newBrd` — у каждого требования ЕСТЬ `fit` и `verify`, число в `fit` имеет
  источник (TASK.md или ЗНАЧЕНИЕ ответа оператора, не текст вопроса), 3..7 якорей, открытых
  вопросов ноль. **S16:** правило «`fit` обязан нести измеримый токен» снято решением оператора —
  живой прогон `ed1d4094` показал ложный красный на предикатном критерии (`регистронезависимое
  вхождение подстроки`) и сжёг на нём все три пере-делегации. Качество формулировки судит человек,
  гардрейл судит состав


### 3. `survey-plan` — раскладка разведки · script · **есть** (S15)
- **вход:** `.agent/brd.md` (только `subjects[]`), дерево файлов от cwd прогона минус список
  пропуска (сам харнес, точечные каталоги, зависимости) — не каталог `app/`: имя каталога кода
  диктовать репозиторию нельзя, разбор — `docs/survey-plan.md` §1
- **выход:** `.agent/survey-plan.json` — клетки роя: `{files, bytes, subjects, gaps, cells[{id, kind,
  subjects, bytes, files[]}]}`; `kind: "spine"` — клетка хребта (манифест сборки, CI, конфиги,
  `README`/`CONTRIBUTING`), у неё другой наряд на шаге 4
- **проверка:** клетки покрывают ВСЕ просканированные файлы без пересечений и потерь; клетка
  закрывается по 20 файлам ИЛИ ~200 КБ — что раньше. Числа клеток не ограничены: `maxParallel` — это
  размер батча шага 4, а не потолок. Оператора на шаге нет вовсе
- **вырождение:** ноль файлов вне списка пропуска → `blocked` с диагнозом, картировать нечего
- **клетка `kind: "vendor"`:** появляется только по явному пути от оператора (ответ на вопрос шага 10
  об идиоме чужой библиотеки) — граница разведки расширяется решением человека, а не догадкой о том,
  где лежат зависимости
- **якорь помечает, а не отбирает:** `subjects[]` из BRD проставляются пометкой на файле и клетке;
  якорь, не встретившийся нигде, едет в `gaps`. Разбор — `docs/survey-plan.md` §1


### 4. `scope` — рой скаутов · role `scout` **веер** · **есть** (S17)
- **вход:** клетка плана, `.agent/brd.md`
- **выход:** `.agent/graph-parts/<клетка>.xml` — ФРАГМЕНТ грамматики графа, не документ: слияние
  делает скрипт, а свободный markdown скриптом не сливается (`docs/concept.md`, «Разведка»)
- **второй выход (script, шаг 3):** `.agent/graph-computed.xml` — рёбра, http-маршруты из аннотаций
  и род внешней системы из импорта драйвера. Вычислимое считает скрипт за 0 токенов и кладёт ОТДЕЛЬНО:
  часть — то, что сказала роль, `graph-computed` — то, что посчитала машина, слияние делает шаг 5
- **проверка:** часть замкнута грамматикой; каждый узел объявил внешние точки, поверхность и тесты —
  элементом или явным `none`; **`<dep>` в части — блокер** (рёбра не её дело); непрочитанное
  объявлено `<gap>`, а не умолчано
- **кэш:** `.izi/parts/<клетка>.{xml,json}`. Клетка пересчитывается только при изменении состава,
  содержимого (`sha1`) или версии грамматики; кэшированную часть судит тот же `checkPart` ПЕРЕД тем,
  как она закроет клетку
- **два наряда:** `kind: "survey"` — «опиши модули, их api и внешние точки»; `kind: "spine"` —
  «перечисли ВСЕ сьюты тестов: род, команда, папка, форма прогона одного файла; назови команду
  сборки, механизм тоглов, соглашения об именах веток и о сообщениях коммитов, описание внешнего контракта
  (openapi/asyncapi/иное) с его валидатором — или объяви, что их нет». Наряд выбирается по полю
  `kind`, а не разбором строк
- **как:** скаут не грепает и не выбирает себе файлы — в наряде приезжает ВЫЖИМКА его клетки: путь,
  язык, пакет, вычисленные импорты/маршруты/драйверы и объявления с видимостью. Файл он открывает
  сам, когда выжимки мало. Батчи по `maxParallel`, потому что у pi потолок параллелизма, а не потому
  что так красивее

### 5. `graph` — сборка `appgraph.xml` · script · **есть** (G0–G7)
Полная карточка — `docs/graph.md`; здесь только место шага в полосе.
- **вход:** части роя (`.agent/graph-parts/<клетка>.xml`, читаются ПО ПЛАНУ — отсутствующая часть
  есть потерянное поддерево, и она названа), `.agent/graph-computed.xml`, `.agent/survey-plan.json`
- **выход:** `.agent/appgraph.xml`
- **модуль — это ФАЙЛ**, как и в части: имя (`path`), одна функция одной фразой (`<role>`),
  объявленный вход (`<api>`). Пакет и артефакт сборки модулями не являются — у них нет ни
  единственного входа, ни одной функции, — поэтому в графе они **адрес** (`pkg`, `<artifact>`), а не
  узел. Разбор трёх редакций этого решения — `docs/graph.md` §1
- **иерархия вычисляется, а не спрашивается:** `component` (связная компонента = вертикальный срез),
  `level` (слои Кана), `fanin`/`fanout` (зацепление), `<cycle>` — всё из рёбер, посчитанных шагом 3.
  Роли не задано ни одного нового вопроса
- **проверка:** один путь — одно имя (ключ узла — репо-относительный `path`, он же ID для шагов 6, 8
  и 10); ни один якорь плана не потерян (полный `subjects` КОПИРУЕТСЯ из плана, а не выводится из
  частей); есть хотя бы один `<suite>`. Всё прочее, что могло бы стать блокером, **объявляется**:
  ответ хребта не найден → `found="no"`, тест вне сьютов → `suite=""`, неразрешимый импорт →
  `<ambiguous>`, цикл → `<cycle>`, вызываемый узел без объявленного входа → `<gap>`. У скриптового
  шага нет рельсы починки, поэтому блокер остаётся только там, ради чего стоит остановить полосу
- **`<test>` сшивается по пути И по `match` сьюта:** два сьюта на одну папку (типовой maven:
  surefire `*Test.java`, failsafe `*IT.java`) без различителя отправили бы IT-тест командой юнитов,
  и та выполнила бы ноль тестов зелёным
- **ни одного `<suite>` → полоса СТОИТ здесь**, терминальный `blocked`: *репозиторий к работе не
  готов — тест-сьюта нет, нужна отдельная задача на его создание*. Это единственное «не найден»,
  которое не превращается в вопрос на шаге 10: тоглы, ветки и спека — решения оператора, а
  отсутствие тестов делает неисполнимыми и шаг 15 (закрывать узлы нечем), и шаг 16
- **импорт вне графа:** библиотека вне дерева прогона узлом не становится — это граница разведки, а
  не дефект; неразрешимый импорт объявляется `<ambiguous>` и поднимается вопросом на шаге 10
- **суть:** слияние — коммутативный моноид по пути модуля, поэтому порядок скаутов не важен
  (доказано: пересборка графа из тех же частей даёт файл байт в байт). Граф отвечает на ШЕСТЬ
  вопросов: что здесь **собирается**, как **тестировать**, как **менять**, как **выключают**, как
  **ветвятся и коммитят**, как описан **внешний контракт**. Имя транка сюда не входит: это факт
  `git`, который берёт шаг 10


### 6. `intake` — требование × реальность → FRD · role `intake` · **есть** (S21)
Полная карточка — `docs/intake.md`; здесь только место шага в полосе.
- **четыре прохода:** A требование · B изменение · C величины и отказы · D покрытие. Свой наряд, свои
  правила, свой бюджет кругов у каждого; карта роя едет только в B; промоут — после ПОЛНОГО суда без
  пласта. Возврат от критика адресуется проходу по ЭЛЕМЕНТУ находки
  (`steps/review/review.mjs::passOf`), и полоса идёт от него вперёд до D
  (`steps/intake/passes-data-flow.md`)
- **вход:** `.agent/brd.md`, ответы оператора и `appgraph.xml` ЦЕЛИКОМ. Потолок чтения — 32К токенов
  ≈ 115 КБ, то есть ≈306 узлов при измеренных 417 Б/узел (`docs/graph.md` §7). Выше потолка шаг
  **встаёт** с числом байт: индексной формы этот срез не строит, её цена не измерена ни разу
  (`docs/intake.md` §3)
- **новое в артефакте:** `<carried req by>` — по строке на каждое требование BRD (роль проходит их по
  одному, скрипт судит `F11`); `<usecase via>` — канал самого use case, когда он не совпадает с
  актёрским (`F10`); плюс `F8` — поле, объявленное в чужой сущности, требует, чтобы её модуль был
  заявлен работой. Все три судятся ТОЛЬКО на staging и питаются вычисленным графом шага 3
- **выход:** `.agent/frd.xml` (через `.agent/staging/frd.xml`) — грамматика, а не проза: артефакт
  читают СКРИПТЫ шагов 7 и 8, а `steps/design/design.mjs::checkDesign` уже сегодня объявляет своим
  входом `{ scenarios, touched }`. Проза живёт внутри тегов (`<pre>`, `<post>`, `<step>`, `outcome`)

- **сразу за этим шагом — критик (шаг 11, §3.11):** он судит FRD против `TASK.md` и `brd.md` и
  зовётся один раз. Улика, ради которой он там стоит: требование нерегрессии «существующий вызов
  остаётся без изменений» не доезжало до FRD ничем — ни `<usecase>`, ни `<scenario>`, ни `<nfr>`, ни
  `<delta>` — и не ловилось никем, потому что `checkFrd` требований BRD физически не получал. Теперь
  их получают оба: машина — строкой `<carried>` (F11), роль — списком долга

### 7. `weight` — вес по SemVer · script · **есть** (S22)
Полная карточка — `docs/weight.md`; здесь только место шага в полосе.
- **вход:** `.agent/frd.xml` — только элементы `<delta form>`; прозу `from`/`to` шаг не читает
- **выход:** `.agent/mode` (`patch | minor | major`) — одно слово
- **проверка:** `weight({})` → `steps/weight/weight.mjs::newMode` — вес есть **максимум по формам**
  (`Added → minor`, `Changed`/`Removed` → `major`, `Fixed → patch`), свёртка коммутативна, поэтому
  порядок дельт в артефакте на результат не влияет
- **форма выбирается по эффекту для СУЩЕСТВУЮЩЕГО вызова**, а не по грамматике фразы — определения
  живут один раз, в роли шага 6 (`steps/intake/intake.md`, STRATEGY §8). Пятая форма `Fixed`
  (контракт не двигается, поведение `wrong → right`) введена S22: без неё исправление дефекта
  попадает под `Changed` и весит `major`, то есть `patch` недостижим никогда, а ветка «одноузловой
  `patch` дизайна не требует» ниже — мёртвый код (`docs/weight.md` §2-§3)
- **`Unknown` → веса нет:** терминальный `blocked`, названа КАЖДАЯ неклассифицированная операция со
  своим `why`. Стоявший с прошлого прогона `.agent/mode` при этом **стирается**: `newRun` уносит в
  `.agent/prev` состояние прогона, но не артефакты, и шаг 8 прочитал бы вчерашний вес


### 8. `ripple` — подграф изменения и нужен ли дизайн · script · **есть** (S23)
Полная карточка — `docs/ripple.md`; здесь только место шага в полосе.
- **вход:** `.agent/appgraph.xml`, `.agent/frd.xml`, `.agent/mode`
- **выход:** `.agent/design` (`needed | skip`) и `.agent/ripple.xml` — подграф изменения
- **проверка:** `ripple({})` → `steps/ripple/ripple.mjs::newRipple`. Флаг отвечает на вопрос, ради
  которого шаг 9 существует — держать контракты согласованными и отрисовать поток данных, пока работа
  не разрезана на тикеты, — а НЕ на вопрос SemVer: `major` и `minor` → `needed` всегда (контракт
  двинулся), `patch` → по ШИРИНЕ изменения. Ширина = `<touched>` ∪ узлы дельт, минус тестовые узлы
  (`docs/ripple.md` §3, расхождения A и E)
- **узел, создаваемый изменением, в подграф не входит:** вырезать вокруг несуществующего файла
  нечего; в ширину он входит, а роль шага 9 берёт его из `frd.xml`, который её наряд несёт целиком
- **подграф считается отдельно от флага:** затравки — узлы дельт ∪ `<touched>` ∪ `nodes` сценариев
  (третий источник обязателен: транзитному узлу маршрута роль шага 9 берёт контракт только отсюда),
  соседи — радиус 1 в обе стороны; в ШИРИНУ узлы сценария при этом не входят — тикета они не
  получат. Тестовые узлы в рябь не входят: тест едет в тикет со своим модулем через
  `<test path suite>` — то же правило, что F2/F3 шага 6
- **зачем второй артефакт:** подграф — вход шага 9. Весь `appgraph.xml` роли не отдаётся: рябь уже
  посчитана, а на живом репозитории граф целиком не влезет в окно

### 9. `design` — план доработки по дереву модулей · role `core-designer` · под условием · **есть** (D44-D46)
Устройство целиком — `docs/design.md`; контракт каждой фазы — `steps/design-data-flow.md`; здесь
только место шага в полосе.

**Единица плана — МОДУЛЬ (класс), а не use case.** Решение куплено живым прогоном `ce2ede24`, где рой
по use case дал дубль: `AbstractBackupService.java` понадобился двум планировщикам сразу, и выразить
это было нечем. Модуль лежит ровно в одной партии, решает его один вызов роли — дубль невозможен по
построению разбиения, а не ловится на гейте. Use case стал строкой раздела: `closes: UC10 step 2`.

- **условие:** `.agent/design == "needed"`. Отдельной квитанции пропуска нет: маркером служит сам
  файл `.agent/design`, который пишет шаг 8
- **вход:** `.agent/frd.xml` (состав изменения и use case дословно), `.agent/ripple.xml` (что
  репозиторий знает о существующих модулях: `deps`, `level`), `.agent/appgraph.xml` (роли,
  декларации, сьюты), `.agent/design-graph.xml` (черновик контрактов прохода 9B)
- **выход:** `task/<КЛЮЧ>/PLAN.md` — модули в порядке работ, разделы ДОСЛОВНО как их написала роль;
  `task/<КЛЮЧ>/design/<партия>.md` — те же разделы по партиям. Поставка живёт НЕ в `.agent/`: она
  переживает прогон, коммитится и режется на тикеты, а `.agent/` чистится `newRun` и лежит в
  `.gitignore`
- **девять фаз, роль ровно в одной:** ① дерево модулей (состав из FRD, факты из ряби) · ② партии
  (компоненты связности по общему use case; модуль ровно в одной) · ③ карточка партии (проекции:
  9,5-18 КБ против 126 КБ карты и FRD) · **④ план партии — РОЛЬ** · ⑤ гардрейл из пяти правил ·
  ⑥ полнота · ⑦ порядок · ⑧ сборка `PLAN.md`. Всё, кроме ④, — скрипт за 0 токенов
- **проверка (⑤):** раздел на каждый модуль партии · ни одного чужого · каждый use case назван в
  «closes» с номером шага из FRD · у каждого раздела «verify» и «calls» · путь в «calls»
  резолвится. Чек идёт по staging, до промоута
- **проверка (⑥⑦):** каждый модуль решён, каждый use case и каждый его шаг закрыт; очередь работ
  строится топосортом по ОБЪЯВЛЕННЫМ «calls» плюс рёбра карты. Отказ здесь чинит РОЛЬ: `planbook`
  возвращает виновные партии, и рельса перезывает именно их с блокером — гардрейл партии целого не
  видит, шаг чужой партии не его дело

### 10. `plan` — план работ · script + вопрос оператору · **есть** (S29)
Полная карточка — `docs/plan.md`; здесь только место шага в полосе.
- **вход:** `.agent/frd.xml`, `.agent/appgraph.xml`, `.agent/mode`, `.agent/design-graph.xml` (если
  шаг 9 отработал), ответы оператора, имя транка фактом `git`

### 11. `review` — критик судит ТРЕБОВАНИЕ · role `critic` · **есть** (J6)
Место в полосе — СРАЗУ ПОСЛЕ зелёного `checkFrd`, до шага 7. Зовётся РОВНО ОДИН РАЗ на артефакт.

- **вход:** `TASK.md`, `.agent/brd.md`, `.agent/staging/frd.xml` — и два чек-листа, которые
  подставляет машина (`ext/index.mjs::reviewForm`): долг (строка на каждое требование BRD,
  `owedItems`) и обратный ход (элементы артефакта, которых не называет ни одна строка `<carried>`,
  `unbackedItems`)
- **выход:** `.agent/review.xml` — `verdict="Pass|Reject"` и блокеры с адресом и уликой
- **словарь:** `requirement-not-carried · invented-value · goal-not-delivered · open-question`;
  виновник у всех — `frd.xml`, владелец починки — шаг 6. Последний код пишет МАШИНА
  (`autoFindings`), роль его не повторяет
- **адрес находки — элемент FRD:** `UC1`, `UC1/2`, `UC1/2a`, `UC1/post`, id сценария, код отказа,
  `op` дельты, `nfr:<subject>` (`frdIds` — одно выражение на этот шаг и на F9 шага 6)
- **зачем роль, если те же предметы считает машина:** гардрейл дёшев и РЕШАЕТ, но каждый его отказ
  ниже по полосе стоит роли — красный шаг 9 это круг дизайнера, красный сухой прогон это
  переписывание раздела, `rework` на гейте это перемотка всей полосы. Один вызов критика дешевле
  любого из них. Он смотрит на ТОТ ЖЕ список, что машина, плюс на то, чего машина не видит:
  значение ЕСТЬ в источнике, но источник его ЗАПРЕЩАЕТ
- **один вызов — правило, а не настройка:** критик не судит починку собственной критики. `Reject`
  даёт роли шага 6 ровно один круг, дальше судит только машина; исключение — `rework` оператора на
  гейте 1: это новый артефакт по новому решению человека, и у него свой один вызов
- **цена измерена:** ручной прогон роли на артефактах eddi — 9.5К токенов входа, $0.04, минута; две
  находки, обе недоступные машине: `resourceURI` против запрета BRD и целый UC8 (синхронизация с
  удалённым инстансом), которого не просит ни задача, ни одно из 18 требований — четыре наряда
  работы, которую никто не заказывал
- **срез:** `steps/review/{review.mjs, review.test.mjs, critic.md, order.tpl}`, io —
  `ext/index.mjs::{review, reviewForm}`

### 12. `gate1` — оператор утверждает план · human + script · **следующий**
- **вход:** `task/<КЛЮЧ>/PLAN.md`, `.agent/frd.xml`, `.agent/appgraph.xml`, транк из git
- **выход:** `.agent/gate1.json` = `{ key, plan: <sha256 PLAN.md>, answer }` — токен акцепта
- **презентация собирается СКРИПТОМ, 0 токенов** (`plandoc.mjs::gateView`): ~15 строк, где каждая
  строка — вырезка или счёт. Цель из `<frd goal>`, ветви из партий и их use case, «новых» из дерева
  модулей, «первым» из порядка ⑦, команды из строк «verify», ветка из ключа и транка. Ни одного
  нового слова: роль здесь не участвует по той же причине, по которой из `PLAN.md` снята шапка-проза
  — непроверяемое утверждение на гейте хуже его отсутствия, человек прочтёт введение и не станет
  читать разделы
- **длинное сообщение** уезжает в `.agent/pending.json` той же рельсой, что вопросы шага 2
- **ответ — слово, а не проза:** `approve` · `rework: <что не так>` · `stop`
- **`rework` всегда возвращает на шаг 6:** комментарий кладётся в `.agent/answers.md` форматом
  `core/answers.mjs`, роль `intake` переписывает FRD, гейт шага 9 стирает свои артефакты, партии
  переигрываются, новый план возвращается на гейт. Частичной правки плана в обход FRD нет: иначе план
  и требование разойдутся, а сверяет их только фаза ⑥ — по FRD
- **токен привязан к содержимому:** в нём хеш `PLAN.md`, иначе `approve` вчерашнего плана закроет
  сегодняшний. То же правило, что «проверь staging перед промоутом», перенесённое на гейт
- **ключ задачи прикалывается в токен:** `newRun` уносит `answers.md` в `.agent/prev`, значит
  отвеченный ключ живёт один прогон; объявленный строкой `task: DOS-535` в `TASK.md` живёт всегда.
  Шаг 13 читает ключ из токена, а не выводит заново — ветка и утверждённый план не могут разойтись

### 14. `tickets` — наряды исполнителям по модулям плана · script · **есть**
Контракт каждой фазы — `steps/tickets/data-flow.md`; здесь только место шага в полосе.

- **вход:** `.agent/gate1.json` (план утверждён), `task/<КЛЮЧ>/design/<партия>.md`, `.agent/frd.xml`,
  `.agent/appgraph.xml` (шаблон имени и корень тестов из `<suite>`), `.agent/branch.json`
- **выход:** `task/<КЛЮЧ>/tickets/<NN>-<имя>.md` — по наряду на тестовый и на модульный тикет
- **тикетов два рода, и порядок жёсткий: ТЕСТ раньше МОДУЛЯ.** Оба режутся из ОДНОЙ вырезки раздела,
  модульный ждёт свои тесты через `blocked_by`, и тестовый файл не входит в его `outputs` — привести
  модуль к тесту исполнитель может, привести тест к модулю нет
- **владелец шага требования один, и он выведен по ГРАФУ:** закрыватель, которого зовёт другой
  закрыватель того же шага, выбывает — его поведение наблюдается через зовущего; из оставшихся берётся
  последний в очереди работ. Ни слова о видах модулей: где-то инженеры пишут интерфейсы, где-то нет
- **единица тестового тикета — пара «модуль × use case»:** модуль, закрывающий два десятка шагов
  восьми use case, дал бы неподъёмный наряд; разрезанный по use case — наряды по две-четыре проверки
- **проверки берутся из FRD:** текст `<step>`, ветка `<ext>`, код из `<failure status>`, границы из
  `<field domain>`. Формула `standards/code.md`: 1 happy + Σ ветвей
- **имя и место теста — из карты, а не из кода шага:** `<suite match>` говорит, где у имени
  переменная часть, `<suite path>` — где корень тестов; пакет модуля сохраняется
- **проверка:** структурные правила (`steps/tickets/data-flow.md` ⑥). Отказ терминальный: роли
  нет, и расхождение тикетов с планом означает, что разошлись артефакты — и означает ещё, что шаг
  10б их пропустил: те же правила судили этот план ДО гейта
- **волны:** `wave = 1 + max(волна того, кого ждём)` — шаг 15 поднимает волну целиком
- **последняя волна — ПРИЁМКА:** наряд без выходов, чьи ворота — весь внешний сьют, и чей текст
  перечисляет граничные тесты, обязанные позеленеть. Без него набор кончался зелёными юнитами и ни
  разу не прогнанной приёмкой: граница «зеленеет сама», а прогнать её было некому (модулю внешний
  сьют запрещён правилом 14)
- **наряд везёт то, что FRD уже знает:** `<pre>` use case (состояние, которое тест обязан создать),
  код и статус отказа — владельцу шага, чью ветку они описывают, а не только границе; словарь величин
  границы сужен до полей, которые этот use case называет или чей код поднимает его ветка
- **срез:** `steps/tickets/{tickets.mjs, tickets.test.mjs, data-flow.md}`, io — `ext/index.mjs::tickets`

### 15. `implement` — исполнение тикетов · role **веер** · цикл починки · **новое**
- **вход:** `.agent/tickets/<узел>.md` — **только тикет**, ничего больше: самодостаточность тикета
  проверена шагом 14 именно затем, чтобы этот шаг не подавал роли ни граф, ни план, ни FRD
- **выход:** файлы узла в рабочем дереве ветки — код и его тесты
- **git запрещён исполнителю целиком:** `$START_FORBIDDEN` тикета запрещает любую git-команду
  (`commit`, `checkout`, `branch`, `stash`, `reset`, `rebase`), права записи — только файлы узла.
  VCS-эффекты живут в двух шагах: 13 режет ветку, 17 коммитит принятое и открывает PR. **Во время
  реализации не коммитят вовсе** — работа копится в рабочем дереве, поузлового отката средствами git
  нет, испорченный узел чинится ещё одним раундом цикла
- **TDD одним тикетом:** тест по формуле и код пишет один исполнитель; отдельный узел на тест есть
  только там, где тест и так узел (`scenario`)
- **цикл — скриптовый, роль внутри него только работает:**
  ```
  until( green(checkFile(node)) or round > 6 )      // K = 6, литерал рядом с LOOPS/QUESTIONS
     implement(ticket, feedback = lastOutput)        // РОЛЬ: файлы, ничего больше
  green ? done : ask(operator, lastOutput)           // СКРИПТ: чек и пауза, коммита нет
  ```
- **`checkFile` — тест УЗЛА, а не сьют целиком:** команду собрал шаг 10 (`suite.one` с подставленным
  файлом), поэтому раунд стоит секунды. `one` в графе пуст → гоняется сьют целиком, и цена пишется в
  лог, а не умалчивается
- **зелёный → узел закрыт**, файлы остаются в рабочем дереве без коммита; красный → вывод чека
  едет в `$START_FEEDBACK` следующей пере-делегации. Роль себя не сертифицирует: «сделано» говорит
  код возврата
- **после `K = 6`** — пауза с вопросом оператору и последним выводом чека, а не падение прогона:
  прочие узлы ветки уже сделаны и закоммичены
- **веер:** батч — узлы одного уровня DAG **без общих файлов** (файлы известны из плана), остальные
  едут следующим батчем; размер батча — `maxParallel` pi. Worktree-изоляция не берётся: она меняет
  конфликт записи на конфликт мержа, решать который некому

- **два механических гейта, с которыми шаг рождается** — оба куплены живой эмуляцией на слабой модели:
  ```
  outputs    белый список записи. Файл, появившийся вне его, откатывается, наряд краснеет.
             Счёт: модель создала 3 чужих файла (интерфейс и модель), посчитав это помощью.
  тавтология тест, чьё утверждение не зависит от кода, отклоняется. Дешёвая форма — утверждение
             над константой. Счёт: `assertTrue(true, "…")` закрыл шаг требования, ворота открылись.
  ```
  Текст тикета оба запрета уже несёт (шаг 14), но текст — это просьба; здесь она становится отказом.

### 16. `accept` — приёмка ветки · script · **новое**
- **вход:** `.agent/branch.json` (`baseSha`, базлайн), `.agent/plan-index.json`, `.agent/appgraph.xml`
- **выход:** `.agent/accept.json` — `{suites: {<id> → green|red}, covered[], extra[], verdict}`
- **проверка:** все `<suite>` графа зелёные, порядком `unit → component → contract` (плюс валидатор
  спеки, если был узел `spec`); файлы **каждого** узла плана присутствуют в диффе `baseSha` ⋃
  untracked — узел, по которому никто ничего не сделал, ловится здесь. Дифф берётся с рабочего
  дерева, а не из журнала: коммитов в реализации нет
- **красный сьют — адресно:** имя упавшего теста → путь → узел плана. Ровно один узел — вывод чека
  едет фидбеком в цикл шага 15 этому узлу. Двое, ни одного или тест не резолвится — регресс между
  узлами, виновника вычислить нечем: пауза с вопросом оператору и выводом чека
- **файл вне плана — не отказ:** при зелёном сьюте остаётся, но объявлен — едет в `extra[]` и оттуда
  в тело PR. Молчаливой правки за пределами плана не бывает
- **почему это улика:** базлайн шага 13 был зелёным до первой строчки работы, значит красное здесь —
  наше, а не наследство репозитория

### 17. `pr` — PR и ссылка оператору · script · **новое**
- **вход:** `.agent/accept.json` (**зелёный** — иначе шага нет вовсе), `.agent/plan-index.json`,
  `.agent/branch.json`
- **выход:** открытый PR от ветки к транку и **ссылка оператору в терминале pi** — конец полосы
- **коммит здесь, один на всю работу:** принята ветка целиком, история отражает принятое решение, а
  не путь к нему. Сообщение и заголовок PR — **по соглашению репозитория** (четвёртый вопрос графа;
  ответ пуст → фактом из `git log` транка), затем `push -u`
- **тело PR выведено из артефактов:** узлы плана с командами проверки · сьюты с результатом из
  `accept.json` · узел тогла с состоянием OFF · `extra[]` отдельным списком. Прозы без источника нет
- **хостинг — факт:** `git remote get-url` даёт хост, наличие `gh`/`glab` — способ. Нет ни того ни
  другого → `blocked` с именем ветки и готовой командой, чтобы человек открыл PR сам
- **оператор:** получает ссылку. Дальше — ревью человеком и мерж: полоса кончилась
