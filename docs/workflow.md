# Как работает workflow izi-pi

Реализация концепта (`docs/concept.md`) в текущем репозитории. Здесь — раскладка, программа и
карточка каждого шага. Обоснования не повторяются: они живут в концепте, этот документ на них ссылается.

---

## 1. Два шага, никакой обвязки (S11)

Оператор сказал прямо: «кто тебя просил универсальный харнес под двенадцать, убирай всю
универсальность, делай конкретные два шага». `pipeline.json`, `step.json`, манифест
(`bin/steps.mjs`), квитанции (`bin/receipt.mjs`), генерический промоут (`bin/promote.mjs`) и
headless-раннер (`bin/run.mjs`) — упразднены целиком, не переписаны. Их работу теперь делают пять
именованных функций хоста и программа в полсотни строк, которая знает оба шага по имени, а не по
данным из файла.

```
ext/
  index.mjs         pi-extension: readText · answers · checkTask · checkBrd · promote · setPending ·
                     clearPending · survey (S15) · budgets · herdrStatus (S16) — глобалы izi.js
                     (roleDirectories → steps/brd/);
                     ПЛЮС (S13) tool izi_answer, зарегистрированный через pi.registerTool на самой
                     интерактивной сессии — export default function extension(pi) одновременно
                     обычный ExtensionFactory pi (`(pi: ExtensionAPI) => void`,
                     @earendil-works/pi-coding-agent) И фабрика pi-extensible-workflows
  package.json      МИНИМАЛЬНЫЙ package.json — не пайплайну, а расширению: pi.extensions,
                     зависимость на pi-extensible-workflows (контракт хоста, объяснено в файле)

steps/task/
  task.mjs          ЧИСТОЕ правило входа: непуст, ≤300 строк — checkTaskText(text)
  task.test.mjs     тест по формуле — 1 happy + Σ ветвей антецедента

steps/brd/
  gilb.md           роль (имя файла = имя роли — так резолвит pi-extensible-workflows,
                     ext/index.mjs::roleDirectories, см. ниже)
  order.tpl         наряд роли: плейсхолдеры {TASK}, {ANSWERS}, {FEEDBACK}, {STAGING}, {CHECK}
  brd.mjs           ЧИСТОЕ ядро приёмки: newBrd(text, sources) — источники чисел: TASK.md + ЗНАЧЕНИЯ
                     ответов оператора, не текст его вопросов
  brd.test.mjs      тест по формуле

steps/survey-plan/  (S15) шаг-СКРИПТ: роли нет, значит нет ни .md-роли, ни order.tpl, ни staging —
  plan.mjs           ЧИСТОЕ ядро раскладки: newPlan({files, spine, subjects}) → клетки роя,

  plan.test.mjs      тест по формуле: happy · шов по байтам · no-files

  design.mjs         ЧИСТОЕ ядро: parseDesign · parseRoutes · expand · checkDesign · newDesign
  design.test.mjs    happy + пять правил + «ни одного <module>» + тотальность разбора

steps/scope/        (S17) шаг-РОЙ: роль scout, ДВА наряда (по полю kind клетки), одно ядро
  scout.md           роль (имя файла = имя роли; roleDirectories += steps/scope/)
  order.survey.tpl   наряд клетки kind="survey": модули, их api и зависимости
  order.spine.tpl    наряд клетки kind="spine": пять ответов графа или found="no"
  part.mjs           ЧИСТОЕ ядро: parsePart · checkPart · newPart; правила C1 · S1..S5 · P1..P3
  part.test.mjs      тест по формуле + швы наряда (плейсхолдеры) и роли (запрет называет проверку)

workflows/izi.js    вся программа: четыре рельсы, бюджеты из конфига, ok/err/exit

                     основной путь чат-tool izi_answer), которым ОПЕРАТОР может писать ответ на
                     диск руками; write-answer.mjs — общая io-запись, использует и bin/answer.mjs,
                     и izi_answer. Воркфлоу-скрипт .agent/answers.md не читает — читает функция
                     расширения `answers`

```

**Установка.**
```bash
cd ext && npm install && cd ..
pi install ./ext
```
`npm install` внутри `ext/` нужен один раз (создаёт `ext/node_modules/`, каталог в `.gitignore`) —
это проверено фактом, не предположением: `pi install ./ext` (локальный путь) НЕ гоняет `npm install`
сам, и без этого шага сессия `pi -p` падает на старте с `Cannot find module
'pi-extensible-workflows'`; разбор причины — в `ext/package.json`. После `npm install`
`pi install ./ext` подключает разом функции, `steps/brd/` как источник ролей и `prompts/` (третьим
полем того же `pi`-манифеста, `"prompts": ["../prompts"]`) — отдельный `bin/install.mjs` для этого
больше не нужен.

**Почему `gilb.md`, а не `role.md`.** `pi-extensible-workflows` резолвит роль по ИМЕНИ ФАЙЛА в
объявленном `roleDirectories` (`validation.js::scanRoleFiles`: `name = basename(entry.name, ".md")`),
не по каталогу шага и не по отдельному полю конфигурации. Расширение объявляет `roleDirectories:
[new URL("../steps/brd/", import.meta.url)]` — сам срез, а не отдельный каталог `roles/`: не-`.md`
соседи (`brd.mjs`, `order.tpl`, тест) сканеру ролей не мешают, он берёт только `*.md`. Файл, названный
`role.md`, установился бы как роль «role», и `agent({ role: "gilb" })` её бы не нашёл — проверено
фактом: живой прогон с файлом, названным верно, дал `agentLaunches: 1` в `summary.json` реального
запуска (см. §3, карточка `brd`).

## 2. Программа

`workflows/izi.js` целиком — три рельсы, `ok`/`err`/`exit`, литералы бюджетов вместо
`pipeline.json` (бюджеты тратят только первые два шага — политика прогона данными пока не нужна,
см. `docs/concept.md`, раздел «Что отложено и почему»):

```js
let LOOPS, QUESTIONS, CHECKPOINT_RETRIES;                  // S16: не литералы — izi.config.json
const b = await budgets({});                              // умолчания 3/3/2 живут в core/budgets.mjs,
if (!b.ok) exit(err("blocked", { subject: b.why }));      // сломанный конфиг = отказ, не умолчание
LOOPS = b.loops; QUESTIONS = b.questions; CHECKPOINT_RETRIES = b.checkpointRetries;

const h = await herdrStatus({});                          // S16: наблюдаемость объявляется вслух —
log(h.available ? `herdr: on pane=${h.pane}` : `herdr: off — ${h.why}`);  // herdr при недоступности
                                                          // молчит, и прогон идёт вслепую

const ok  = (fields) => ({ track: "ok", code: 0, ...fields });
const err = (kind, fields) => ({ track: "err", kind, code: kind === "crashed" ? 2 : 10, ...fields });
const exit = (result) => { throw new Exit(result); };      // throw-to-unwind из глубины цикла

async function task() {
  const t = await checkTask({});                           // функция хоста, не shell("cat …")
  if (!t.ok) exit(err("blocked", { subject: t.why }));
}

async function brd() {                                     // на зелёном чеке RETURN, не exit —
                                                           // S15: brd больше не конец прогона
  // читает order.tpl и TASK.md функцией readText, ANSWERS — функцией answers();
  // делегирует agent(order, { role: "gilb", outputSchema: ENVELOPE });
  // на вопросе — askOperator(): setPending({subject, evidence}) ДО checkpoint() (S13 — полный
  //   вопрос лежит в .agent/pending.json ДО того, как чат увидит паузу; foreground: false, значит
  //   пауза приезжает ОБЫЧНЫМ сообщением — оператор отвечает прямо в этом чате, модель зовёт tool
  //   izi_answer, потом workflow_respond) + answers() до/после (Approve без появившегося ответа =
  //   переспрос, роль не зовётся заново — не тратит LOOPS; ответ появился → clearPending());
  // на ok — checkBrd({ path: STAGING }) ПО STAGING, зелёный → promote({ from, to }) → log + return,
  //   красный → feedback в пере-делегацию — тратит LOOPS
}

async function surveyPlan() {                              // S15: шаг-СКРИПТ — ни роли, ни вызова
  const PLAN = ".agent/survey-plan.json";                  // модели, ни оператора, ни checkpoint
  const p = await survey({ path: PLAN });                  // одна функция хоста делает весь шаг
  if (!p.ok) exit(err("blocked", { subject: p.why }));     // единственный отказ — no-files
  log(`survey-plan: files=${p.files} bytes=${p.bytes} cells=${p.cells}`);   // стоимость роя ДО роя
  exit(ok({ artifact: PLAN, files: p.files, cells: p.cells, gaps: p.gaps }));
}

try { phase("task"); await task(); phase("brd"); await brd();
      phase("survey-plan"); await surveyPlan(); phase("scope"); await scope(); }
catch (e) { return e instanceof Exit ? e.result : err("crashed", { subject: String(e?.message ?? e) }); }
```

Порядок остаётся КОДОМ, а не `pipeline.json`: третья фаза — ещё одна именованная функция. Решение
принято с фактами трёх шагов на руках (`docs/survey-plan.md` §5): три ручных вызова подряд дешевле,
чем манифест плюс диспетчер плюс их тесты.

Полный файл — `workflows/izi.js`. Никакого `shell()`, `JSON.parse` или кода возврата процесса —
воркфлоу-скрипт не знает о процессах вообще, только о функциях хоста (`readText`, `answers`,
`checkTask`, `checkBrd`, `promote`, `setPending`, `clearPending`, `survey`, `budgets`, `herdrStatus`) и о встроенных глобалах pi
(`agent`, `checkpoint`, `prompt`, `log`, `phase`). `izi_answer` НЕ входит в этот список — это tool
интерактивной сессии (`pi.registerTool`, `ext/index.mjs`), а не функция песочницы воркфлоу; внутри
`workflows/izi.js` его вызвать нельзя и не нужно — его зовёт модель ЧАТА в ответ на follow-up
сообщение паузы.

Веер (шаги 4-12 — план, не реализация) сюда пока не входит: шаг 3 его только РАСКЛАДЫВАЕТ, а
батчами по `maxParallel` рой погонит уже своя программа, когда появится первый веерный срез. Тогда
же встанет вопрос, возвращать ли порядок в данные — см. `docs/concept.md`, «Что отложено и почему».

## 3. Шаги

Состояние: **есть** — работает и покрыто тестами · **новое** — этим концептом добавляется.

### 1. `task` — оператор кладёт требование · human · **есть**
- **вход:** — (внешний: человек)
- **выход:** `TASK.md`
- **проверка:** `checkTask({})` (функция расширения) → `steps/task/task.mjs::checkTaskText` —
  непуст, ≤300 строк
- **оператор:** кладёт файл. Красный чек — терминальный `err(blocked)`, роль не зовётся вовсе: у
  этого шага роли нет, чинит человек

### 2. `brd` — сырое требование → измеримый BRD · role `gilb` · **есть**
- **вход:** `TASK.md`, `.agent/answers.md`
- **выход:** `.agent/brd.md` (через `.agent/staging/brd.md`)
- **проверка:** `checkBrd({ path: ".agent/staging/brd.md" })` (функция расширения) →
  `steps/brd/brd.mjs::newBrd` — у каждого требования ЕСТЬ `fit` и `verify`, число в `fit` имеет
  источник (TASK.md или ЗНАЧЕНИЕ ответа оператора, не текст вопроса), 3..7 якорей, открытых
  вопросов ноль. **S16:** правило «`fit` обязан нести измеримый токен» снято решением оператора —
  живой прогон `ed1d4094` показал ложный красный на предикатном критерии (`регистронезависимое
  вхождение подстроки`) и сжёг на нём все три пере-делегации. Качество формулировки судит человек,
  гардрейл судит состав
- **оператор (S13):** пауза `checkpoint()` (`foreground: false`) приезжает в чат ОБЫЧНЫМ сообщением
  — модальный `ui.select`, который до S13 забирал ввод у всего окна и не давал оператору напечатать
  ничего (`foreground: true`, `pi-extensible-workflows/src/host.ts:686`), здесь не участвует.
  Оператор отвечает вопрос дословно ПРЯМО В ЭТОМ ЧАТЕ; модель вызывает `izi_answer({ text })`
  (ключ вопроса тул берёт из `.agent/pending.json`, не от модели), затем `workflow_respond({runId,
  name, approved: true})`. `bin/answer.mjs` остаётся запасным CLI-входом, не основным. Approve без
  появившегося в `.agent/answers.md` ответа не считается ответом и не зовёт роль заново
- **живое доказательство (S11, живой прогон в этом репозитории):** `agentLaunches: 1..3` в
  `summary.json` — роль `gilb` резолвится из `roleDirectories` и вызывается по-настоящему;
  `.agent/staging/brd.md` перезаписывается на каждой пере-делегации, `checkBrd` читает именно его
  (staging, не `.agent/brd.md`) на каждой проверке; предзаполненный `.agent/answers.md` (`node
  bin/answer.mjs --q="…" --text="4"`) даёт роли значение прямо на первой попытке, и оно доезжает до
  `fit:` требования дословно.

- **живое доказательство (S13, живые прогоны через `herdr`, тот же `TASK.md` — booking-задача).**
  Прогон `8bb23932-f368-4632-9b0b-75ea32eea95f`: оператор напечатал `4` прямо в чате в ответ на
  вопрос `gilb`, `izi_answer` записал ответ в `.agent/answers.md`, `workflow_respond` подтвердил
  паузу — весь обмен вопрос→ответ прошёл БЕЗ второго терминала. Этот прогон вскрыл живой дефект
  вызова (`clearPending()` без обязательного JSON-аргумента —
  `"clearPending requires exactly one JSON object argument"` в `result.json`, `askOperator` крашился
  на последней строке уже ПОСЛЕ того, как ответ был принят), почин в `workflows/izi.js`
  (`clearPending({})`). Повторный прогон с исправленным кодом, `0445e4cd-2667-43e4-8db8-9102679146fb`,
  дошёл до `.agent/brd.md`, `track:"ok"`, `requirements:4` — с `fit: формат времени — ISO-8601, …` в
  R1, доказывая заодно закрытие находки `numbersIn` (см. README «Долги») живым прогоном, не только
  юнитом. Чистый повтор с нуля (`.agent/` очищен, новая сессия), `79c0aa0a-e410-4172-a5cf-a1af6a78f8e8`
  — оператор ответил `давай 2 часа`, `.agent/pending.json` корректно снят `clearPending()` после
  подтверждённого ответа, прогон дошёл до `track:"ok"` за один заход, без ручного вмешательства.

### 3. `survey-plan` — раскладка разведки · script · **есть** (S15)
- **вход:** `.agent/brd.md` (только `subjects[]`), дерево файлов от cwd прогона минус список
  пропуска (сам харнес, точечные каталоги, зависимости) — не каталог `app/`: имя каталога кода
  диктовать репозиторию нельзя, разбор — `docs/survey-plan.md` §1
- **выход:** `.agent/survey-plan.json` — клетки роя: `{files, bytes, subjects, gaps, cells[{id, kind,
  subjects, bytes, files[]}]}`; `kind: "spine"` — клетка хребта (манифест сборки, CI, конфиги,
  `README`/`CONTRIBUTING`), у неё другой наряд на шаге 4
- **проверка:** клетки покрывают ВСЕ просканированные файлы без пересечений и потерь; клетка
  закрывается по 20 файлам ИЛИ ~200 КБ — что раньше. Числа клеток не ограничены: `maxParallel` — это
  размер батча шага 4, а не потолок. Оператора на шаге нет вовсе
- **вырождение:** ноль файлов вне списка пропуска → `blocked` с диагнозом, картировать нечего
- **клетка `kind: "vendor"`:** появляется только по явному пути от оператора (ответ на вопрос шага 10
  об идиоме чужой библиотеки) — граница разведки расширяется решением человека, а не догадкой о том,
  где лежат зависимости
- **якорь помечает, а не отбирает:** `subjects[]` из BRD проставляются пометкой на файле и клетке;
  якорь, не встретившийся нигде, едет в `gaps`. Разбор — `docs/survey-plan.md` §1
- **живое доказательство (S15, чужой проект `/private/tmp/quarkus-rest-json-app-v2-t1-3`,
  прогон `cffa2e65-4c68-48ae-840c-a32c6dd28bae`):** `track:"ok"`, `.agent/survey-plan.json`,
  `files=20 bytes=28549 cells=2` — читается из `journal.json` (`function/survey/1`), а не из того,
  что напечатала модель. `c0` = `pom.xml` + `README.md`; `mvnw`/`mvnw.cmd` и `.mvn/` в план не
  попали (`SKIP_FILES` и точечный каталог), `Legume*.java` попали — под якоря они не подходят, и
  именно это доказывает, что якорь ПОМЕЧАЕТ, а не фильтрует. Цена помётки названа фактом того же
  прогона: якорь `limit` сработал на `Dockerfile.jvm` (слово в комментарии) — ложное попадание
  стоит скауту абзаца, ложный пропуск стоил бы графу узла

### 4. `scope` — рой скаутов · role `scout` **веер** · **есть** (S17)
- **вход:** клетка плана, `.agent/brd.md`
- **выход:** `.agent/graph-parts/<клетка>.xml` — ФРАГМЕНТ грамматики графа, не документ: слияние
  делает скрипт, а свободный markdown скриптом не сливается (`docs/concept.md`, «Разведка»)
- **проверка:** часть замкнута грамматикой; у каждого узла названы **зависимости** (`<dep path>`) —
  без рёбер неисполним шаг 8; непрочитанное объявлено `<gap>`, а не умолчано
- **два наряда:** `kind: "survey"` — «опиши модули, их api и зависимости»; `kind: "spine"` —
  «перечисли ВСЕ сьюты тестов: род, команда, папка, форма прогона одного файла; назови команду
  сборки, механизм тоглов, соглашения об именах веток и о сообщениях коммитов, описание внешнего контракта
  (openapi/asyncapi/иное) с его валидатором — или объяви, что их нет». Наряд выбирается по полю
  `kind`, а не разбором строк
- **как:** скаут не грепает и не выбирает себе файлы — список приезжает в наряде. Батчи по
  `maxParallel`, потому что у pi потолок параллелизма, а не потому что так красивее

### 5. `graph` — сборка `appgraph.xml` · script · **новое**
- **вход:** части роя, план
- **выход:** `.agent/appgraph.xml`
- **проверка:** один путь — одно имя (ключ узла — репо-относительный `path`, он же ID, на который
  ссылаются шаги 6, 8 и 10); ни один якорь плана не потерян (полный `subjects` лежит в плане, а не
  выводится); **перечислены все сьюты** (`<suite id kind cmd one path>`), **названы механизм тоглов,
  соглашения о ветках и о сообщениях коммитов (их берут шаги 10 и 17) и спека внешнего контракта с
  валидатором** — или явное «не найден»; каждая
  найденная разведкой папка тестов покрыта каким-то `<suite>` либо объявлена `<gap>` — иначе
  контрактные тесты тихо выпадут из приёмки шага 16; `<test>` узла ссылается на `suite`, своей
  команды не носит
- **ни одного `<suite>` → полоса СТОИТ здесь**, терминальный `blocked` с сообщением для человека:
  *репозиторий к работе не готов — тест-сьюта нет, нужна отдельная задача на его создание*. Это
  единственное «не найден», которое не превращается в вопрос на шаге 10: тоглы, ветки и спека —
  решения оператора, а отсутствие тестов делает неисполнимыми и шаг 15 (закрывать узлы нечем), и шаг
  16 (приёмка вырождается в «мы что-то поменяли»)
- **импорт вне графа:** библиотека, лежащая вне дерева прогона, узлом не становится — это граница
  разведки, а не дефект. Импорт, не резолвящийся в узел и не имеющий ни одного вызова в
  репозитории, объявляется `<gap>` и поднимается вопросом на шаге 10 (идиому даёт оператор:
  пример · путь к исходнику · навык)
- **суть:** слияние — коммутативный моноид по пути модуля, поэтому порядок скаутов не важен. Граф
  обязан отвечать на ПЯТЬ вопросов: как проект **тестировать**, как **менять**, как в нём
  **выключают**, как здесь **ветвятся и коммитят**, как описан **внешний контракт**. «Не найден» — валидное
  значение и вопрос оператору на шаге 10, а не догадка. Имя транка сюда не входит: это факт `git`,
  который берёт шаг 10

### 6. `intake` — требование × реальность → FRD · role `intake` · **новое**
- **вход:** `.agent/brd.md`, `.agent/appgraph.xml`
- **выход:** `.agent/frd.md` — `{ contract: Delta[], scenarios[], touched[] }`, где
  `Delta = Added | Changed | Removed | Unknown(op, why)`
- **проверка:** каждый `touched` резолвится в УЗЕЛ графа (ключ — `path`); сценарий различающий
- **`Unknown` — обязательная форма, а не украшение:** роль, не сумевшая классифицировать операцию
  (узла нет, два кандидата, операция вне графа), объявляет это, а не выбирает правдоподобную дельту
- **здесь же выполнимость:** первый шаг, у которого есть оба операнда — чего хотят и что есть

### 7. `weight` — вес по SemVer · script · **новое**
- **вход:** `.agent/frd.md`
- **выход:** `.agent/mode` (`patch | minor | major`)
- **проверка:** вес выведен таблицей из формы дельты; хоть одна дельта `Unknown` → **файла нет**
- **оператор:** `Unknown` — вопрос ему с `why` из FRD, а не тихий default
- **следствие веса:** `minor` (аддитивно) тянет за собой узел тогла в плане — способность едет
  ВЫКЛЮЧЕННОЙ. Это выводится из веса, а не решается отдельно на шаге 10

### 8. `ripple` — подграф изменения и нужен ли дизайн · script · **новое**
- **вход:** `.agent/appgraph.xml`, `.agent/frd.md`, `.agent/mode`
- **выход:** `.agent/design` (`needed | skip`) и `.agent/ripple.xml` — сам подграф замыкания
- **проверка:** радиус достижимости по рёбрам графа из узлов дельты — вычислимо, роль не зовём;
  `needed`, если замыкание больше одного узла ИЛИ `mode == major`. Одноузловой `patch` дизайна не
  требует: границы модуля дельта не пересекает, ломаться композиции негде (`docs/data-flow.md` §8)
- **зачем второй артефакт:** подграф — вход шага 9. Весь `appgraph.xml` роли не отдаётся: рябь уже
  посчитана, а на живом репозитории граф целиком не влезет в окно

### 9. `design` — две проекции изменения · role `designer` · под условием · **новое**
- **условие:** `.agent/design == "needed"`. Отдельной квитанции пропуска НЕ существует: маркером
  служит сам файл `.agent/design`, который пишет шаг 8 — `skip` в нём и есть «решено пропустить»,
  отсутствие файла — «шаг 8 ещё не отработал». Различимость держится этим, а не вторым артефактом
- **вход:** `.agent/frd.md`, `.agent/ripple.xml` (подграф ряби, не весь граф)
- **выход роли:** `.agent/staging/design-graph.xml` — узлы с `delta` и `<contract in out>` в
  грамматике `appgraph.xml`, плюс **маршруты** сценариев (`<route scenario steps>`: путь узла и
  номер альтернативы его `out`)
- **выход скрипта:** `.agent/data-flow.md` — `expand` подставляет значения контрактов в маршрут;
  роль строк потока не набирает, поэтому расхождение внутри потока невыразимо
- **проверка:** `checkDesign` — пять правил, объявлены один раз в `docs/data-flow.md` §6. Красный
  чек едет блокерами в фидбек и пере-делегацию, чек идёт **по staging**, до промоута
- **шов:** правило `out(k) ∈ in(k+1)` — единственное место, где остаётся ручной ввод роли (контракты
  соседних узлов пишутся независимо); всё остальное держится подстановкой
- **срез:** `steps/design/{designer.md, order.tpl, design.mjs, design.test.mjs}`

### 10. `plan` — план работ · script · **новое**
- **вход:** `.agent/design-graph.xml` либо `.agent/frd.md`, `.agent/mode`, `.agent/appgraph.xml`
- **выход:** `.agent/plan-index.json` — DAG узлов, у каждого `kind`, плюс **имя ветки с базой**
  (свежий транк, Git-TBD) и при `minor`/незавершённой части — **узел тогла** со стейтом OFF
- **`kind` узла назначается здесь, из решений шагов 6–7:** дельта контракта → `code`; тронутый
  документ → `doc`; `minor`/незавершённое → `toggle`; сценарий FRD поверх нескольких узлов кода →
  `scenario`; тронутая внешняя io-точка при найденной спеке → `spec`
- **команда проверки узла собирается здесь:** `suite.one` из графа с подставленным файлом теста узла
  (`{class}`/`{path}`); `one` пуст → команда сьюта целиком, и это записано в узле, а не решается на
  шаге 15
- **проверка:** циклов нет; путь и команда проверки **выведены** из графа (`<test suite>` → `<suite>`),
  а не сочинены; имя ветки — по соглашению ИЗ ГРАФА, база — имя транка **фактом `git`**, снятым на этом
  шаге, а не памятью оператора; узел тогла опирается на механизм ИЗ ГРАФА; узлы `code` объявлены
  зависимыми от узла `spec` (API-first — ребро, не обещание), узел `scenario` — от всех узлов,
  которые различает; **проекция каждого узла в тикет влезает в окно SLM** (та же формула, что на
  шаге 14). «Не найден» в графе (тоглы, ветки, спека) → отказ с вопросом оператору, а не значение,
  придуманное планом; сьютов это не касается — без них полоса не дошла бы сюда (шаг 5)
- **лечение здесь, а не дальше:** узел, переросший бюджет тикета, режет этот шаг — оператор на
  гейте утверждает уже нарезанный план. Спеки в репозитории нет, а дельта трогает внешний
  контракт → вопрос оператору здесь же: завести первую спеку — решение, как и завести первый тогл
- **идиома чужой библиотеки — типизированный вопрос:** `<gap>` шага 5 (импорт без узла и без единого
  вызова в репозитории) поднимается здесь вопросом с тремя допустимыми формами ответа — **пример**
  (фрагмент → `$START_EXAMPLE`), **путь к исходнику** (входит в границу разведки, клетка
  `kind: "vendor"` ⇒ библиотека становится узлами графа), **навык** (файл/папка → секция
  `$START_SKILL` с путём как источником). Форму классифицирует скрипт: каталог → `vendor`, файл
  навыка → `skill`, иначе текст-пример. Содержимое ответа считается в бюджет окна узла

### 11. `review` — критик судит план · role `critic` · цикл починки · **новое**
- **вход:** `.agent/plan-index.json`, `.agent/frd.md`
- **выход:** `.agent/review.md` — `Pass | Reject(Blocker[])`
- **проверка:** каждый блокер назван с уликой (узел, файл, команда)
- **цикл:** `until(pass, fix)` до K раундов, дальше — оператору. Отрицательный вердикт есть данные:
  критик, нашедший блокер, отработал успешно

### 12. `gate1` — оператор утверждает план · human · **новое**
- **вход:** `.agent/plan-index.json`, `.agent/review.md`
- **выход:** `.agent/gate1.json` — токен акцепта
- **проверка:** присутствие токена, а не проза
- **оператор:** план показывается **в функциональном стиле** — узел, вход, выход, команда проверки.
  Ветка с базой и тогл с состоянием по умолчанию видны ЗДЕСЬ, а не всплывают после гейта: оператор
  утверждает и их тоже. `/izi-gate1 <правки>` кладёт замечания файлом, Approve без правок означает
  «беру план»

### 13. `branch` — короткая ветка от свежего транка · script · **новое**
- **вход:** `.agent/gate1.json` (токен акцепта), `.agent/plan-index.json` → `branch: {name, base}` —
  имя по соглашению **из графа**, база = транк; оба решены шагом 10, здесь не пересматриваются;
  `.agent/appgraph.xml` — список `<suite>` для базлайна
- **выход:** `.agent/branch.json` — `{name, base, baseSha, remote, baseline}`. `baseSha` нужен шагу
  16: диск изменений считается от базы ветки, а не от «как-нибудь»
- **базлайн — до первой строчки работы:** сразу после среза скрипт гоняет **все** сьюты графа.
  Ветка равна свежему транку, поэтому зелёный прогон доказывает релизопригодность транка (Git-TBD), а
  красный называет дефект чужим — без этого якоря красный сьют на шаге 16 не улика. Красный базлайн →
  `blocked` с именем сьюта и вопросом оператору: чужое молча не чиним
- **чистое ядро:** `steps/branch/branch.mjs::newBranch({gate, planBranch, git})`, где `git` — снимок
  фактов `{dirty, refs[], trunkSha, remote}` от io-функции расширения `gitFacts`. Ядро судит, но не
  режет; отказы: `no-gate` · `no-branch-name` · `dirty-worktree` · `branch-exists` · `no-trunk`
  (база плана не найдена среди рефов)
- **io:** функция расширения `cutBranch({name, base})` — `git fetch <remote> <base>`, затем
  `git switch -c <name> origin/<base>`; она же пишет `.agent/branch.json`
- **свежесть — факт, а не память:** ветвимся от `origin/<base>` сразу после `fetch`, отставший
  локальный транк в ветвлении не участвует вовсе. Нет remote → база = локальный `<base>`,
  `remote: null` в артефакте — объявлено, а не умолчано
- **оператор:** нет вовсе. Любой отказ — терминальный `blocked` с уликой: грязную рабочую копию и
  занятое имя ветки чинит человек и перезапускает. Роли на шаге нет → 0 токенов, окно SLM не тратится
- **шов:** убрать `fetch` перед `switch` → ветка режется от вчерашнего транка; юнит «`trunkSha` не
  равен голове удалённого транка ⇒ отказ» краснеет

### 14. `tickets` — наряды исполнителям по узлам плана · script · **новое**
- **вход:** `.agent/plan-index.json`, `.agent/frd.md`, `.agent/appgraph.xml`, `.agent/branch.json`,
  `.agent/design-graph.xml` и `.agent/data-flow.md` (если шаг 9 отработал)
- **выход:** `.agent/tickets/<узел>.md` — по одному на узел плана; порядок исполнения не изобретается,
  это топосорт, уже лежащий в плане
- **как:** проекция «узел × его сценарии из FRD × `dep`-соседи из графа» + подстановка в шаблон,
  выбранный полем `node.kind` — тем же приёмом, что два наряда разведки на шаге 4. Пять шаблонов
  `steps/tickets/tpl/{code,doc,toggle,scenario,spec}.tpl`; формулировки вычитаны человеком один раз,
  а не сочиняются на каждый тикет. Роли на шаге нет — 0 токенов
- **форма тикета — под слабый тир** (`docs/concept.md`, «Тикет читает слабая модель»): секции
  `$START_<СЕКЦИЯ>`/`$END_<СЕКЦИЯ>`, как в роли и наряде; одно правило — одна секция, пересказов нет;
  `$START_EXAMPLE` несёт вырезку **из этого репозитория**, а не из чужого домена
- **секции `code.tpl`:** `$START_CONTEXT` (узел, ветка из `branch.json`) · `$START_CONTRACT`
  (antecedent/consequent, `dep`-соседи по строке) · `$START_EXAMPLE` (сосед того же рода и его тест,
  пути ИЗ ГРАФА; для импорта, не резолвящегося в узел, — вырезка **реального вызова** из этого
  репозитория) · `$START_SKILL` (только если оператор дал навык на шаге 10; **единственная секция не
  из репозитория**, поэтому путь-источник обязателен) · `$START_TASK` (дельта из FRD) ·
  `$START_TESTS` (юниты по формуле `1 happy + Σ ветвей` — это `<dod>` тикета, отдельного шага
  «написать тесты» нет; плюс различающий сценарий) · `$START_CHECK` (команда узла из плана) ·
  `$START_FLOW` (вырезка маршрутов шага 9, где участвует узел; шаг 9 пропущен → секции нет) ·
  `$START_FORBIDDEN` · `$START_DONE`
- **разметка кода выведена, а не сочинена:** `CONTRACT` шапки файла ← `<contract>` узла из
  `design-graph.xml`, `MODULE_MAP` ← его `<dep>`-соседи, `$START_FLOW` ← `data-flow.md`. Разметка —
  протокол передачи знания следующему агенту (`docs/concept.md`, следствие 4), но у каждой секции
  обязан быть источник: секция без источника неотличима от выдумки модели
- **проверка:** тикет **самодостаточен** — ни одной ссылки на артефакт, которого в нём нет («см.
  `appgraph.xml`» для слабого тира с окном 128K есть недоступное знание, а не ссылка); каждый
  `dep` тикета разрешается в другой тикет или в существующий узел графа; секции закрыты парами
  `$START_*`/`$END_*`; пути в `$START_EXAMPLE` существуют в графе — вырезка берётся с диска, а не
  сочиняется
- **бюджет окна — не рельса этого шага:** узел, не влезающий в тикет, режет шаг 10; здесь перебор —
  утверждение инварианта, и его срабатывание означает дефект шага 10, а не работу для оператора

### 15. `implement` — исполнение тикетов · role **веер** · цикл починки · **новое**
- **вход:** `.agent/tickets/<узел>.md` — **только тикет**, ничего больше: самодостаточность тикета
  проверена шагом 14 именно затем, чтобы этот шаг не подавал роли ни граф, ни план, ни FRD
- **выход:** файлы узла в рабочем дереве ветки — код и его тесты
- **git запрещён исполнителю целиком:** `$START_FORBIDDEN` тикета запрещает любую git-команду
  (`commit`, `checkout`, `branch`, `stash`, `reset`, `rebase`), права записи — только файлы узла.
  VCS-эффекты живут в двух шагах: 13 режет ветку, 17 коммитит принятое и открывает PR. **Во время
  реализации не коммитят вовсе** — работа копится в рабочем дереве, поузлового отката средствами git
  нет, испорченный узел чинится ещё одним раундом цикла
- **TDD одним тикетом:** тест по формуле и код пишет один исполнитель; отдельный узел на тест есть
  только там, где тест и так узел (`scenario`)
- **цикл — скриптовый, роль внутри него только работает:**
  ```
  until( green(checkFile(node)) or round > 6 )      // K = 6, литерал рядом с LOOPS/QUESTIONS
     implement(ticket, feedback = lastOutput)        // РОЛЬ: файлы, ничего больше
  green ? done : ask(operator, lastOutput)           // СКРИПТ: чек и пауза, коммита нет
  ```
- **`checkFile` — тест УЗЛА, а не сьют целиком:** команду собрал шаг 10 (`suite.one` с подставленным
  файлом), поэтому раунд стоит секунды. `one` в графе пуст → гоняется сьют целиком, и цена пишется в
  лог, а не умалчивается
- **зелёный → узел закрыт**, файлы остаются в рабочем дереве без коммита; красный → вывод чека
  едет в `$START_FEEDBACK` следующей пере-делегации. Роль себя не сертифицирует: «сделано» говорит
  код возврата
- **после `K = 6`** — пауза с вопросом оператору и последним выводом чека, а не падение прогона:
  прочие узлы ветки уже сделаны и закоммичены
- **веер:** батч — узлы одного уровня DAG **без общих файлов** (файлы известны из плана), остальные
  едут следующим батчем; размер батча — `maxParallel` pi. Worktree-изоляция не берётся: она меняет
  конфликт записи на конфликт мержа, решать который некому

### 16. `accept` — приёмка ветки · script · **новое**
- **вход:** `.agent/branch.json` (`baseSha`, базлайн), `.agent/plan-index.json`, `.agent/appgraph.xml`
- **выход:** `.agent/accept.json` — `{suites: {<id> → green|red}, covered[], extra[], verdict}`
- **проверка:** все `<suite>` графа зелёные, порядком `unit → component → contract` (плюс валидатор
  спеки, если был узел `spec`); файлы **каждого** узла плана присутствуют в диффе `baseSha` ⋃
  untracked — узел, по которому никто ничего не сделал, ловится здесь. Дифф берётся с рабочего
  дерева, а не из журнала: коммитов в реализации нет
- **красный сьют — адресно:** имя упавшего теста → путь → узел плана. Ровно один узел — вывод чека
  едет фидбеком в цикл шага 15 этому узлу. Двое, ни одного или тест не резолвится — регресс между
  узлами, виновника вычислить нечем: пауза с вопросом оператору и выводом чека
- **файл вне плана — не отказ:** при зелёном сьюте остаётся, но объявлен — едет в `extra[]` и оттуда
  в тело PR. Молчаливой правки за пределами плана не бывает
- **почему это улика:** базлайн шага 13 был зелёным до первой строчки работы, значит красное здесь —
  наше, а не наследство репозитория

### 17. `pr` — PR и ссылка оператору · script · **новое**
- **вход:** `.agent/accept.json` (**зелёный** — иначе шага нет вовсе), `.agent/plan-index.json`,
  `.agent/branch.json`
- **выход:** открытый PR от ветки к транку и **ссылка оператору в терминале pi** — конец полосы
- **коммит здесь, один на всю работу:** принята ветка целиком, история отражает принятое решение, а
  не путь к нему. Сообщение и заголовок PR — **по соглашению репозитория** (четвёртый вопрос графа;
  ответ пуст → фактом из `git log` транка), затем `push -u`
- **тело PR выведено из артефактов:** узлы плана с командами проверки · сьюты с результатом из
  `accept.json` · узел тогла с состоянием OFF · `extra[]` отдельным списком. Прозы без источника нет
- **хостинг — факт:** `git remote get-url` даёт хост, наличие `gh`/`glab` — способ. Нет ни того ни
  другого → `blocked` с именем ветки и готовой командой, чтобы человек открыл PR сам
- **оператор:** получает ссылку. Дальше — ревью человеком и мерж: полоса кончилась

## 4. Тесты — минимум, но со швом

На срез: **один тест на правило, которое может тихо деградировать**, и чистое ядро по формуле
`1 happy + Σ ветвей антецедента`. `ext/index.mjs` — io-модуль (подключает `task.mjs`/`brd.mjs`/
`core/answers.mjs` к диску) и юнитами не покрывается по той же причине, что и бывшие `bin/*.mjs`
гардрейлы: доказывает его живой прогон, а не тест, играющий роль интеграционного под именем юнита.
Тест, который ни от какой правки кода не краснеет, — комментарий; такой не пишем.

## 5. Порядок разработки

Срезы идут по одному, каждый — до зелёного прогона, прежде чем начинать следующий:

```
survey-plan → scope(рой) → graph → intake → weight → ripple → design? → plan → review → gate1
             → branch → tickets(рой) → implement(рой) → accept → pr
```

Первые три дают `appgraph.xml` — после него полоса впервые знает о репозитории хоть что-то, и
дальнейшие шаги перестают быть догадкой.

**S11 разобрала генерический диспетчер (манифест `step.json`, цикл по `pipeline.order`,
универсальный `move(s)` на любой `kind`), который §1-§2 несли до этой правки** — оператор явно
велел выбросить универсальность, рассчитанную на двенадцать шагов, пока их два. Отсюда прямое
следствие для `survey-plan`: он больше не «включается в уже готовый диспетчер, знающий `script`» —
диспетчера в этом смысле не существует, есть `task()`/`brd()` по имени. Добавление `survey-plan`
означает: либо третья именованная функция-фаза рядом с `task()`/`brd()` (та же рука, тот же стиль,
ещё один литерал бюджета), либо к этому моменту цена ручного перечисления фаз превысит цену
policy-as-data и `pipeline.json`/манифест стоит вернуть — это решение принимается ТОГДА, с фактами
трёх шагов на руках, а не сейчас с фактами двух (`docs/concept.md`, «Что отложено и почему»).
