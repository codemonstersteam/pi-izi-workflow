# Концепт izi-pi — полоса TASK → PR

Наследует `izi-flow/CONCEPT.md` (стандарт) и `izi-flow-v2/arch/{intent,flow-concept}.md` (полоса),
переложенные на парадигму `pi-extensible-workflows`. Понятия берутся дословно, механизм — местный.

Реализация этого концепта в текущем репозитории — `docs/workflow.md`: раскладка срезов, программа
и карточка каждого шага. Обоснования живут здесь, механика — там.

# Часть 1. Смысл

## Задача одной фразой

Превратить сырое требование человека в **принимаемый им план работ**, где каждое решение по дороге
оставило след, проверяемый машиной.

## Конвейер — программа, часть шагов которой исполняет ЛЛМ

Это не оправдание для отсутствия проекта, а требование к нему: содержимое артефакта роли
непредсказуемо, но его **антецедент** (наряд), **консеквент** (структурированный возврат плюс
артефакт) и **судья** (гардрейл-скрипт) предсказуемы полностью.

Отсюда три правила, из которых следует всё остальное:

1. **Порядок — данные.** Последовательность лежит в `pipeline.json`, а не в прозе и не в памяти
   модели. Шага, которого нет в `order`, в конвейере не существует. **Отложено на двух шагах (S11,
   см. «Что отложено и почему» ниже): порядок `task → brd` сегодня — код (`workflows/izi.js`), не
   файл.** Принцип не выброшен — он вернётся ровно тогда, когда цена ручного перечисления фаз
   превысит цену policy-as-data, и это решается фактами будущего третьего шага, не сейчас.
2. **Артефакт судит скрипт, а не роль.** Самосертификация снята: «готово» решает код возврата
   гардрейла. Роль, нашедшая блокер, отработала успешно — отрицательный вердикт есть данные, а не ошибка.
3. **Вычислимое считает скрипт за 0 токенов.** Греп, таблица весов, слияние частей, топосортировка
   DAG — не ролевые ходы. Роль зовут там, где нужно суждение, и только там.

## Что наследуем из стандарта — семантика, не механизм

| понятие `izi-flow/CONCEPT.md` | как здесь |
|---|---|
| вертикальный срез | шаг конвейера: один вход → один артефакт → своя приёмка → своя квитанция |
| вес SemVer решает поведение | `weight` — скрипт по таблице; клетка `unknown` → файла нет, вопрос оператору |
| API-first: контракт заморожен до реализации | дельта контракта решена и наряжена **до** GATE #1 |
| корректность композицией | consequent шага N ⊆ antecedent шага N+1 |
| формула тестов | `1 happy + Σ ветвей антецедента`, едет в `<dod>` тикета, а не отдельным шагом |
| разведка — стандартный вход, не опция | репозиторий по умолчанию хаотичен: `survey` обязателен, его отсутствие — STOP |
| docs-as-code | тронутый документ — такой же узел графа, отдельного шага «обновить доки» нет |
| Git-TBD | короткая ветка от **свежего транка**, транк всегда релизопригоден; ветку называет план, режет её полоса после GATE #1 |
| feature toggle | незавершённое и всё аддитивное едет за тоглом, **OFF по умолчанию**; тогл — узел плана, а не обещание прозой |

**Реальный мир → chaos по умолчанию.** Репозиторий со стандартом, соблюдённым плохо, — норма, а не
исключение. Поэтому разведка есть **стандартный вход, не опция**: любой вес работы на существующем
репозитории начинается с неё. Отсюда же и «как»: проектируем **семантически по стандарту** —
вертикальным срезом, если он оправдан по стоимости, — но реализуем **conform** к тому, как сделан
репозиторий: компонентные тесты в его родном раннере, нативные io-точки, структуру не навязываем.
`native` — частный случай репозитория, собранного самим конвейером greenfield; greenfield эта полоса
не делает, значит и частного случая у неё нет.

## Тоггл и транк — два понятия, которые полоса обязана нести до GATE #1

Оба живут на той же оси «семантика, не механизм»: **что** — фиксировано стандартом, **как** —
вычитывается из репозитория, а не навязывается ему.

**Feature toggle.** Аддитивное изменение (`minor`) и всё незавершённое выпускаются **выключенными**.
Из этого следуют три требования к полосе, и все три — до гейта:

1. Разведка обязана назвать **механизм тоглов этого репозитория** — так же, как называет раннер
   тестов: конфиг-флаг, свойство окружения, запись в БД, готовая библиотека, или его нет вовсе.
   Механизма не нашлось — это **вопрос оператору** (завести первый тогл — решение, а не догадка),
   а не повод изобрести свой.
2. Тогл — **узел плана** со своим контрактом и командой проверки, а не строчка обещания в прозе.
   Не будучи узлом, он не попадёт в тикет и будет «забыт» ровно так же, как забываются доки.
3. Состояние по умолчанию — **OFF**, и это проверяемо: сценарий при выключенном тогле обязан
   показывать прежнее поведение. Тогл, включённый по умолчанию, — не тогл, а релиз.

**Git-TBD.** Работа идёт короткой веткой от **свежего транка**, транк всегда релизопригоден.
До GATE #1 веток не режут: полоса производит план, и **имя ветки с базой — часть плана**, а не
самодеятельность шага. Резать ветку от несвежего транка нельзя — это решается фактом (транк
подтягивается перед ветвлением), а не памятью оператора.

**Ядровой принцип: семантика, не механизм.** Полоса обязана работать на ЛЮБОМ репозитории, значит
держит суть стандарта и не диктует, чем она реализована. Практическое следствие, из-за которого это
не лозунг: чтобы выразить сценарий в идиоме репозитория, идиому надо **прочитать** — раннер,
раскладку, фикстуры, команду проверки. Не прочитав, роль навяжет чужому репозиторию свою идиому.

## Что отложено и почему

Реализация сегодня (`workflows/izi.js`, S11) несёт ровно `task` и `brd` — оператор велел выбросить
универсальность, рассчитанную на двенадцать шагов, пока их два. Это временно отодвинуло два
принципа из «Часть 1. Смысл» и «Программа» выше, не отменило их:

| принцип | где заявлен | что сегодня | почему отложен, а не выброшен |
|---|---|---|---|
| порядок — данные | правило 1 выше | код: `task()` затем `brd()`, литералы бюджетов в `workflows/izi.js` | двух шагов мало, чтобы окупить файл конфигурации и манифест — они появятся вместе с третьим шагом, когда цена ручного перечисления фаз превысит цену чтения `pipeline.json` (`docs/workflow.md` §5) |
| квитанция закрывает шаг | «Программа» выше | нет квитанций: прогон идёт до терминала за один вызов, не возобновляется по файлам | возобновляемость покупает что-то только там, где есть что возобновлять — веер, циклы починки, паузы на середине десятка шагов; на `task`+`brd` за один интерактивный вызов это не так |

Оба принципа рассчитаны на полосу из двенадцати шагов и в этом рассчёте останутся — они читаются
дальше в этом документе (карточки 3-12, `docs/workflow.md` §3) как план, а не как факт кода.

## Чего эта полоса НЕ решает

- **После PR** — ревью человеком, мерж, релиз, канареечный выкат, здоровье прода. Полоса кончается
  ссылкой на PR у оператора: дальше решает человек, а не конвейер.
- **Greenfield** — полоса проектируется под один случай: код уже есть, работа — изменение. Пустой
  репозиторий вырождает половину полосы: разведке нечего находить, дельте не от чего считаться.
  Это держит шов, а не оговорка: ни один якорь `subjects[]` не встретился в файлах прогона — шаг
  `survey-plan` встаёт с диагнозом `blocked` и картирует **ничего**. Границей служит cwd прогона
  минус список пропуска (сам харнес, `.git`, зависимости), а не каталог с заранее известным именем:
  диктовать репозиторию раскладку — ровно тот механизм, который этот раздел запрещает
  (`docs/survey-plan.md` §1). Делать вид, что полоса рассчитана на пустой
  репозиторий, дороже, чем сказать это вслух.

## Стиль разработки

`standards/code.md` — контракт модуля и функции, формула тестов, правило шва.
`standards/role.md` — скелет роли, слои, права. Оба перенесены из `izi-flow-v2` без правок.
**Минимум тестов:** шов на правило, которое может тихо деградировать, и ни одного ради покрытия.

# Часть 2. Полоса — шаги до GATE #1

`⟳` цикл починки · `?` шаг под условием · род: `script` (0 токенов) · `role` · `human`

| # | шаг | род | вход | выход | приёмка судит | оператор |
|---|---|---|---|---|---|---|
| 1 | `task` | human | — | `TASK.md` | одна задача = один вход, ≤300 строк, непуст | кладёт файл |
| 2 | `brd` | role `gilb` | `TASK.md`, ответы | `.agent/brd.md` | у каждого требования есть fit и verify, число имеет источник, 3..7 якорей (S16: правило измеримого токена снято) | отвечает на вопрос |
| 3 | `survey-plan` | script | дерево прогона, brd | `.agent/survey-plan.json` | клетки покрывают ВСЕ файлы без пересечений и потерь | — |
| 4 | `scope` | role `scout` **рой** | клетка, brd | `.agent/graph-parts/<клетка>.xml` | часть — ФРАГМЕНТ грамматики графа; у узла названы зависимости, внешние точки и выставленная поверхность (каждое — со значением или явным `none`); непрочитанное объявлено `<gap>` | — |
| 5 | `graph` | script | части, план | `.agent/appgraph.xml` | один путь — одно имя; ни один якорь плана не потерян; перечислены ВСЕ сьюты (**ни одного ⇒ СТОП**), названы механизм тоглов, соглашение о ветках и описание внешнего контракта (или «не найден»); собран раздел поверхности из `<api scope="public">`, каждый `<io>` сшит с `<integration>` по ключу конфигурации, каждый `<test path>` сшит со своим `<suite>` ПО ПУТИ (в survey-клетке id сьюта непознаваем — хребет читается тем же батчем) | сообщение при СТОПе |
| 6 | `intake` | role `intake` | brd, граф | `.agent/frd.md` | дельта опирается на УЗЛЫ графа; сценарий различающий | — |
| 7 | `weight` | script | frd | `.agent/mode` | вес выведен таблицей; хоть одна дельта `Unknown` → файла нет | вопрос при `Unknown` |
| 8 | `ripple` | script | граф, frd, mode | `.agent/design`, `.agent/ripple.xml` | радиус от тронутых узлов по рёбрам; `needed`, если замыкание больше одного узла ИЛИ вес `major` | — |
| 9 | `design`? | role `designer` | frd, подграф ряби | `.agent/design-graph.xml`, `.agent/data-flow.md` | у каждого узла дельты контракт; узел с дельтой встречен маршрутом; переход маршрута — ребро `<dep>`; `out(k)` среди `in(k+1)` | — |
| 10 | `plan` | script | design-graph \| frd, граф, mode | `.agent/plan-index.json` | DAG без циклов; путь, команда проверки и имя ветки выведены ИЗ ГРАФА; у узла есть `kind`, и его проекция в тикет влезает в окно SLM | вопрос: тогл · ветка · спека · идиома чужой библиотеки |
| 11 | `review`⟳ | role `critic` | план, frd | `.agent/review.md` | блокер назван с уликой | — |
| 12 | `gate1` | human | план, review | `.agent/gate1.json` | токен акцепта присутствует | **утверждает план** |

**Почему «оценка выполнимости» стоит на шаге 6, а не на шаге 2.** До `graph` о репозитории не
известно ничего, и вердикт «выполнимо» на шаге 2 был бы правдоподобным ответом на неизвестной
клетке. Выполнимость судит `intake` — первый шаг, у которого есть оба операнда: чего хотят (brd)
и что есть (граф).

**Почему `weight` и `ripple` — два скрипта, а не одна роль.** Оба вычислимы: вес выводится таблицей
из формы дельты, радиус — достижимостью по рёбрам графа. Платить за это токенами не за что.

**Тикеты стоят ПОСЛЕ GATE #1.** Оператор утверждает план, а не наряды: наряды — производная плана,
и писать их до акцепта значит платить за работу, которую гейт может отменить целиком.

## Программа

```js
run = () => pipe(config, steps, foldFirstStop)      // порядок исполняет скрипт, не модель

step = (s) => match(s.kind,
  script: () => shell(s.check),                     // 0 токенов
  role:   () => pipe(order(s), delegate(s), accept(s)),
  human:  () => gate(s))

delegate = (s) => (order) => agent(order, { role: s.role, outputSchema: ENVELOPE })
accept   = (s) => (env) => env.track === "ok"
  ? shell(s.check) |> green ? promote(s) >> receipt(s) : redelegate(s)   // чек ПО STAGING, до промоута
  : rail(env.kind)                                                       // question → оператор, прочее → стоп
```

Состояние живёт на диске квитанциями: `stepDone(s) ⟺ существует .agent/receipts/<s>.json`.
Поэтому перезапуск продолжает, а не начинает, и артефакт, записанный по ошибке, шаг не закрывает.

**Отложено на двух шагах (S11).** Сегодняшняя реализация (`task`, `brd`) квитанций не пишет вовсе:
`workflows/izi.js` не перечитывает состояние прогона между запусками — процесс идёт до конца или до
терминального `err` за один вызов `pi -p`/`/izi`, а не возобновляется по файлам на диске. Принцип
«квитанция закрывает шаг, не факт наличия `out`» не выброшен — он был придуман для перезапускаемого
многошагового прогона (веер, циклы починки, промежуточные паузы на десятке шагов), которого пока
физически нет: возобновляемость двух шагов за один интерактивный вызов не покупает ничего, что не
даёт сам факт «промоут произошёл или нет». Вернётся вместе с шагами, которым есть что возобновлять
(`docs/workflow.md` §5).

## Разведка (шаги 3–5) — рой скаутов

```
survey = (repo, brd) => pipe(plan(repo, brd), batches, map(scout), merge)

plan    : (Repo, Brd) -> Plan       script: ВСЁ дерево минус список пропуска, порезанное на клетки;
                                    клетка закрывается по 20 файлам ИЛИ ~200 КБ — что раньше;
                                    якоря brd ПОМЕЧАЮТ файл, но не отбирают его; нулевые якоря → gaps
batches : Cell[] -> Cell[][]        chunksOf(maxParallel)  ← потолок pi: concurrency 1..16, по умолчанию 8;
                                    это размер батча, а не потолок числа клеток
scout   : Cell ⇒ Part               РОЙ, parallel(); скаут не грепает и не выбирает себе файлы
merge   : (Plan, Part[]) -> Graph   script: коммутативный моноид по пути модуля ⇒ порядок скаутов не важен
```

**Якорь помечает, а не отбирает.** Отбор по якорям был первой редакцией и опровергнут живым фактом:
файлы, которых требование касается напрямую, под его словарь не попадают (`docs/survey-plan.md` §1).
Ложный пропуск дороже ложного попадания: лишний файл стоит скауту абзаца, потерянный — стоит графу
узла, которого никто уже не хватится.

**Часть — фрагмент грамматики графа, а не документ.** Слияние делает скрипт, а свободный markdown
скриптом не сливается. Поэтому и часть, и граф — одна грамматика, и ключ моноида объявлен один раз:

```xml
<module path="src/main/java/org/acme/rest/json/FruitResource.java">   <!-- path = ID УЗЛА -->
  <role>REST-ресурс фруктов</role>                     <!-- что это, одной строкой -->
  <api name="GET /fruits"/>                            <!-- наблюдаемые входы -->
  <dep path="src/main/java/org/acme/rest/json/Fruit.java"/>   <!-- РЁБРА: без них ripple неисполним -->
  <test path="src/test/java/.../FruitResourceTest.java" suite="unit"/>  <!-- ссылка на сьют, не своя команда -->
  <gap why="не прочитано: файл больше предела"/>       <!-- непрочитанное объявлено, а не умолчано -->
</module>
```

Сьюты объявлены **данными хребта**, а не одной строкой «раннер»: в живом репозитории их несколько —
юниты рядом с кодом, компонентные и контрактные в своих папках, у каждого своя команда и своя цена.

```xml
<suite id="unit"     kind="unit"      cmd="./mvnw -q test"              one="./mvnw -q test -Dtest={class}" path="src/test/java"/>
<suite id="it"       kind="component" cmd="./mvnw -q verify -Pit"       one=""                              path="src/it"/>
<suite id="contract" kind="contract"  cmd="./mvnw -q verify -Pcontract" one=""                              path="src/contract"/>
```

`one` — форма прогона **одного файла**, и она тоже вычитывается, а не выдумывается: `-Dtest=` у
maven, `--tests` у gradle, путь у jest/pytest, `-run` у go — общего синтаксиса нет, поэтому шаблон
называет скаут, а скрипт лишь подставляет `{class}`/`{path}`. Пустой `one` — валидное значение: шаг
15 тогда гоняет сьют целиком и пишет эту цену в лог, а не молчит.

`path` — репо-относительный путь и одновременно **идентификатор узла**: на него ссылаются `touched`
шага 6, рёбра шага 8 и узлы плана шага 10. Отсюда же приёмка шага 5 «один путь — одно имя».

`appgraph.xml` строит **скрипт**, а не роль: граф — слияние частей по правилу, а не суждение о коде.
Граф обязан отвечать на **шесть** вопросов, и каждый — потому что без него встанет конкретный шаг:

| вопрос | без ответа встанет |
|---|---|
| как проект **тестировать** — ВСЕ сьюты, каждый с командой, папкой и формой прогона одного файла | **шаг 5: ни одного сьюта ⇒ полоса СТОИТ здесь**; дальше команда проверки узла (10) и приёмка (16) неисполнимы в принципе |
| как проект **менять** | шаг 6: дельта опирается на узлы, а не на имена из головы |
| как в нём **выключают** (механизм тоглов) | шаг 10 при весе `minor`: способность едет выключенной |
| как здесь **ветвятся и оформляют коммиты** (соглашения об именах и сообщениях) | шаг 10: имя ветки — часть плана; шаг 17: сообщение коммита и заголовок PR по соглашению репозитория, а не по вкусу |
| как описан **внешний контракт** (openapi/asyncapi/иное) и чем он проверяется | шаг 10: API-first — узел спеки стоит РЕБРОМ перед узлами кода, а его команда валидации выведена, а не сочинена |
| с какими **внешними системами** он говорит (БД, брокер, чужой сервис) и каким ключом конфигурации они объявлены | шаг 8: дельта, трогающая io-точку, обязана дотянуться до её узла; шаг 10: узел `spec` заводится по тронутой внешней точке, а не по догадке |

Первый, второй, четвёртый, пятый и шестой живут не в коде, а в манифесте сборки, CI,
`CONTRIBUTING`/`README` и конфигурации — поэтому у раскладки есть отдельная клетка **хребта**
(`kind: "spine"`) со своим нарядом: не «опиши модули», а «перечисли ВСЕ сьюты тестов — команда,
папка, форма прогона одного файла; назови команду сборки, механизм тоглов, соглашения о ветках и о
сообщениях коммитов, описание внешнего контракта с его валидатором, внешние системы из конфигурации
— или объяви, что их нет».

**Поверхность — шестой вопрос со стороны кода.** Что репозиторий выставляет НАРУЖУ, в хребте не
написано: это `<api scope="public">` у модулей, и шаг 5 собирает из них раздел поверхности графа.
Без `scope` вопрос «какие API выставлены наружу» из графа не выводится вовсе — до S9/S10 `<api>` был
необязательным украшением, которое гардрейл не проверял ни одним правилом.

**Исключение из «не найден» — тесты.** Отсутствующий механизм тоглов, соглашение о ветках или спека
есть решение оператора на шаге 10; отсутствующий тест-сьют — **не решение, а негодность репозитория
к работе этой полосы**: закрывать узлы нечем, приёмка вырождается в «мы что-то поменяли». Поэтому
граф без единого `<suite>` останавливает полосу прямо на шаге 5 сообщением, которое человек читает
без расшифровки: *репозиторий к работе не готов, тест-сьюта нет — нужна отдельная задача на его
создание*. Сочинять сьют на ходу полоса не станет: это самостоятельная работа со своим гейтом. Ответ «не найден» —
валидное значение и вопрос оператору на шаге 10, а не догадка.

Имя транка сюда не входит: транк — факт `git`, который шаг 10 подтягивает сам, а не суждение роли.

## Прожарка и оценка change (шаги 6–8)

```
intake : (Brd, Graph) ⇒ Frd
weight : Frd -> Mode | None                    // None ⇒ файла нет, полоса стоит с вопросом
ripple : (Graph, Frd, Mode) -> Radius × Flag   // достижимость по рёбрам ИЗ узлов дельты
                                               // Flag = needed, если |Radius| > 1 ИЛИ Mode == major

Frd   = { contract: Delta[], scenarios: Scenario[], touched: At[] }
Delta = Added(op) | Changed(op, from, to) | Removed(op) | Unknown(op, why)
```

| в `Frd.contract` есть | вес | следствие |
|---|---|---|
| хоть один `Unknown` | **нет веса** | `.agent/mode` НЕ пишется, вопрос оператору с `why` |
| `Removed` или `Changed` | **major** | дизайн обязателен, ломающая дельта названа списком |
| только `Added` | **minor** | дизайн по умолчанию нужен; способность едет выключенной |
| ни одного | **patch** | дизайн по радиусу ряби; контракт не двигается |

`Unknown` — не украшение таблицы, а единственный способ, которым «не смог решить» доезжает до
оператора. Без этой формы правило «клетка `unknown` → файла нет» неисполнимо: `intake`, не сумевший
классифицировать операцию (нет узла, два кандидата, операция вне графа), вынужден был бы выбрать
правдоподобную дельту — ровно тот тихий default, ради запрета которого написана вся полоса.

Каждый `touched` — **узел графа**, а не имя из головы: нет узла → отказ с уликой. Сценарий обязан
**различать** (`absent → present` для minor, `wrong → right` для patch); зелёный до изменения
сценарий — находка приёмки, а не тест.

## Дизайн — две проекции одного изменения (шаг 9)

```
design : (Frd, Radius) ⇒ DesignGraph × Route[]      роль: контракты узлов и МАРШРУТ сценария
expand : (DesignGraph, Route[]) -> DataFlow         скрипт: подстановка контрактов, 0 токенов
check  : (DesignGraph, DataFlow, Radius, Frd) -> Ok | Blocker[]

Route = { scenario: Id, steps: [ "<path>#<alt>" ] }  альтернатива выбирается ИЗ контракта узла
```

Структурная проекция (`design-graph.xml`, та же грамматика, что `appgraph.xml`, плюс `delta` и
`<contract in out>`) и временна́я (`data-flow.md`, сценарий, проигранный по шагам) — ортогональны, и
их **выравнивание** проверяет скрипт: пять правил, все — принадлежность множеству или равенство
строк. Правила объявлены один раз, в `docs/data-flow.md` §6; здесь они не пересказываются.

**Роль не переписывает токены — она их выбирает.** Контракт узла написан один раз, в графе; маршрут
несёт путь узла и номер альтернативы его `out`, а значения в поток подставляет скрипт. Композиция
держится копированием машины — тем же приёмом, которым копируется ключ вопроса из `pending.json`.
Отсюда же и единственный оставшийся шов: контракты соседних узлов роль пишет независимо, поэтому
`out(k) ∈ in(k+1)` — то место, где дизайн может тихо разойтись, и оно проверяется.

**Вход — подграф ряби, а не весь граф.** Шаг 8 уже посчитал достижимость из узлов дельты; отдавать
роли `appgraph.xml` целиком незачем, а на живом репозитории он и не влезет в окно.

Тир роли — сильный, как у `gilb`, `intake` и `critic`: ограничение SLM объявлено для **тикетов**
(шаг 14), не для ролей до гейта. Устройство наряда при этом рассчитано и на слабый тир: суждение —
маршрут, а не аккуратность набора.

## План, критик, гейт (шаги 10–12)

```
plan   : DesignGraph | Frd -> PlanIndex   script: топосорт по deps; путь и команда проверки — производные
review : (PlanIndex, Frd) ⇒ Verdict       Verdict = Pass | Reject(Blocker[])
fix    : Verdict ⇒ PlanIndex              ⟳ until(pass), до K раундов, затем эскалация оператору
gate1  : (PlanIndex, Verdict) -> Approval человек; приёмка судит ПРИСУТСТВИЕ токена, а не прозу
```

План предъявляется оператору **в функциональном стиле** — тем же, что этот документ: узел, его
вход, выход и команда проверки. Проза плана оператору не показывается: если решение нельзя выразить
контрактом узла, оно ещё не решение.

План несёт **имя ветки и её базу** (свежий транк) и — при весе `minor` либо любой незавершённой
части — **узел тогла** с состоянием OFF по умолчанию. Оба выведены, а не сочинены, и оба имеют
названный источник: соглашение об именах веток и механизм тогла — **из графа** (четвёртый и третий
вопросы разведки), имя транка — **факт `git`**, подтянутый на этом шаге. Ответ графа «не найден» →
вопрос оператору здесь же, а не догадка в тикете.

**Узел плана несёт `kind`, и его назначает этот шаг** — из того, что уже решили шаги 6–7, а не из
вкуса: дельта контракта → `code`, тронутый документ → `doc`, вес `minor` либо незавершённая часть →
`toggle`, сценарий FRD, охватывающий больше одного узла кода, → `scenario`, тронутая внешняя io-точка
при найденной спеке → `spec`. Спеки в репозитории нет, а дельта трогает внешний контракт — **вопрос
оператору здесь же**: завести первую спеку есть решение, как и завести первый тогл.

**API-first — ребро, а не обещание.** Узлы `code`, реализующие io-точку, объявлены зависимыми от
узла `spec`; топосорт тогда сам ставит спеку первой, и «контракт заморожен до реализации» проверяется
DAG-ом, а не памятью исполнителя. Тем же ребром держится `scenario`: он зависит от всех узлов кода,
которые различает, поэтому зеленеет последним и владелец у теста ровно один.

**Команду проверки узла собирает этот шаг, а не исполнитель:** `suite.one` из графа с подставленным
файлом теста узла (пустой `one` ⇒ команда сьюта целиком). Сочинённая на ходу команда — тот же
invented-default, что и число без источника, только дороже: она либо не запустится, либо запустит не
то.

**Узел обязан влезать в тикет.** Проекция узла в тикет (шаг 14) считается здесь же той же формулой,
и узел, переросший окно SLM, режется планом — до гейта, чтобы оператор утверждал уже нарезанное.
Отказ на шаге 14 был бы дефектом этого шага: каждый шаг проверяет себя на пригодность для
следующего, а не сваливает разбор дальше по полосе.

## Взаимодействие с оператором — один механизм на все гейты

Оператор печатает **в терминале pi**. Барьер и данные разделены нарочно:

```
workflow ──> .agent/pending.json { step, subject, cmd }    -- что именно спрашивают
             checkpoint(...)                               -- барьер: только Approve | Reject

оператор ──> /izi-answer 20            (шаг 2, ответ на вопрос роли)
             /izi-gate1 <правки>       (шаг 12, замечания к плану)
                 ↓ шаблон промпта читает pending.json и пишет файл
             .agent/{answers.md | gate1-notes.md}
                 ↓
             следующая итерация читает файл и продолжает ТОТ ЖЕ прогон
```

Три свойства, ради которых это так, а не проще:

1. **Ключ вопроса не проходит через человека и через модель** — он копируется из файла, который
   написал сам воркфлоу. Дословность держит машина, а не аккуратность.
2. **Воркфлоу верит файлу, а не клику.** Approve без появившегося ответа — переспрос, а не движение
   вперёд, и роль при этом не зовётся: ошибка оператора не стоит денег.
3. **Вопрос не тратит бюджет пере-делегирования.** Обмены с оператором и повторы по красному чеку —
   разные счётчики, объявленные данными.

`checkpoint` в pi возвращает ровно `approved | rejected`; текста в этом канале нет вообще — поэтому
данные едут файлом, а барьер остаётся барьером.

**Паузы после GATE #1 ездят тем же каналом, своего не заводят:** вопрос об идиоме чужой библиотеки и
о «не найден» (шаг 10), красный базлайн (13), узел, не сошедшийся за `K = 6` раундов (15),
нерезолвимый регресс (16). Меняется `subject` в `pending.json`, не механизм.

## Ветка (шаг 13)

```
gitFacts : () -> Facts                    io: { dirty, refs[], trunkSha, remote }
newBranch: (Gate, PlanBranch, Facts) -> Cut | Refusal    чистое ядро: судит, не режет
cutBranch: Cut -> BranchFile              io: fetch <remote> <база> ⇒ switch -c <имя> origin/<база>
baseline : Suite[] -> Green | Red(suite)  io: прогон ВСЕХ сьютов графа на срезанной ветке

Refusal = no-gate | no-branch-name | dirty-worktree | branch-exists | no-trunk | red-baseline
```

**Базлайн снимается здесь, до первой строчки работы.** Ветка равна свежему транку, поэтому зелёный
прогон всех сьютов доказывает то, что Git-TBD требует от транка, — релизопригодность; а красный
называет дефект **чужим**, до нашей работы, и это единственный способ сделать красный сьют на шаге 16
уликой против нас. Результат едет в `.agent/branch.json` (`baseline: {<сьют> → green|red, at: baseSha}`),
красный → `blocked` с именем сьюта и вопросом оператору: чинить чужое молча полоса не станет.

**Свежесть транка — факт, а не память оператора.** Ветка режется от `origin/<база>` сразу после
`fetch`: отставший локальный транк в ветвлении не участвует вовсе, поэтому «забыл подтянуть» здесь
невыразимо. Нет remote → база = локальный `<база>`, и это записано в артефакте (`remote: null`), а
не умолчано.

**Имя и базу решил план (шаг 10), а не этот шаг.** Здесь нет суждения — значит нет и роли: 0 токенов,
окно SLM не тратится. `baseSha` едет в артефакт, потому что шаг 16 считает диск изменений от базы, а
не «как-нибудь».

Отказ терминальный: грязный worktree или занятое имя ветки чинит человек, а не конвейер, — это его
рабочая копия, и угадывать за него (спрятать? закоммитить? переименовать?) дороже, чем встать с
уликой.

## Тикеты (шаг 14)

```
ticket : (Node, Frd, Graph, Branch) -> Ticket    script: join + подстановка в шаблон по node.kind
tickets: PlanIndex -> Ticket[]                   по узлу на тикет, порядок = топосорт плана
```

**Тикет пишет скрипт, а не роль, потому что сочинять нечего.** Что делать — решил шаг 6 (дельта) и
шаг 10 (узел с контрактом, deps, `kind`, командой проверки); чем это проверяется — решил граф.
Осталась проекция «узел × его сценарии из FRD × `dep`-соседи из графа» и подстановка в шаблон —
а вычислимое считает скрипт за 0 токенов (правило 3).

Формулировки живут в **пяти шаблонах**, вычитанных человеком один раз, и выбираются полем `kind`, а
не разбором строк — тем же приёмом, что два наряда разведки (`survey` | `spine`):

| `kind` | шаблон несёт | чем закрывается |
|---|---|---|
| `code` | контракт узла, файлы и `dep`-соседи, список юнитов по формуле, сценарий FRD | команда проверки узла из графа |
| ↳ его разметка | `CONTRACT` шапки файла ← `<contract>` узла · `MODULE_MAP` ← его `<dep>`-соседи · `$START_FLOW` ← вырезка маршрутов шага 9, где узел участвует | у каждой секции назван источник |
| `doc` | какой документ, какой узел графа он описывает | проверка документа из графа |
| `toggle` | механизм тоглов ИЗ ГРАФА, состояние OFF | сценарий «выключено ⇒ прежнее поведение» |
| `scenario` | различающий сценарий FRD поверх нескольких узлов | сьют репозитория, узел зеленеет последним |
| `spec` | дельта внешнего контракта из FRD, путь спеки ИЗ ГРАФА | валидатор спеки из графа |

**Юниты — не узел, а `<dod>` узла:** формула `1 happy + Σ ветвей антецедента` едет в тикет `code`,
отдельного шага «написать тесты» не существует (таблица наследования выше). Интеграционное
поднимается до узла ровно тогда, когда перестаёт помещаться в один узел кода, — иначе тест написали
бы двое по половине.

**Самодостаточность — вся приёмка шага:** в тикете не должно быть ни одной ссылки на артефакт,
которого в нём нет. Тикет читает слабый тир с окном 128K, и «см. `appgraph.xml`» для него —
недоступное знание, а не ссылка. Перебор бюджета здесь невозможен: узел, не влезающий в окно, режет
шаг 10 (см. выше) — на этом шаге проверка бюджета есть утверждение инварианта, а не рельса.

### Тикет читает слабая модель — отсюда форма, а не вкус

Исполнитель тикета — малопараметрическая модель (порядка Qwen-класса), и она **чувствительна к
структурной плотности и однозначности**: недостаток параметров компенсируется жёсткой типизацией
контекста, а не многословием. Четыре следствия, и все четыре проверяемы скриптом:

1. **POSIX-разметка секций.** Тикет размечен `$START_<СЕКЦИЯ>` / `$END_<СЕКЦИЯ>` — тем же способом,
   каким размечены роль и наряд (`standards/role.md`, слои; `steps/brd/order.tpl`). Секция — тип, а
   не заголовок: модель не разбирает прозу, а берёт содержимое известного имени.
2. **Суверенитет правил.** Правило живёт **ровно в одной секции** и нигде больше не пересказывается —
   ни в соседней секции тикета, ни эхом из другого артефакта. Два места для одного правила у слабого
   тира дают не подкрепление, а конфликт, который он разрешает наугад. Это тот же запрет, что в
   `$START_FORBIDDEN` этого репозитория: «не восстанавливай правило прозой там, где оно уже живёт
   кодом — подставляй из одного места».
3. **Пример — из ЭТОГО репозитория.** `$START_EXAMPLE` тикета несёт вырезку соседнего модуля того же
   рода и его теста, пути которых взяты **из графа**, а не сочинены. Роль в примере получает чужой
   домен нарочно — чтобы не копировали содержание; тикет получает свой репозиторий нарочно — чтобы
   **скопировали идиому**: раннер, раскладку, фикстуры, стиль. Это и есть «реализуем conform к тому,
   как сделан репозиторий», доведённое до наряда, а не оставленное пожеланием.

4. **Семантическая разметка выведена, а не сочинена.** `CONTRACT` в шапке файла — это `<contract>`
   узла из `design-graph.xml`, `MODULE_MAP` — его `<dep>`-соседи, `$START_FLOW` — вырезка маршрутов
   шага 9, где узел участвует. Разметка нужна потому, что код сопровождает другой автономный агент,
   видящий только файл: это протокол передачи знания, а не лишние токены. Но у каждой её секции
   обязан быть источник — разметка без источника неотличима от выдумки модели, тот же довод, что у
   `$START_SKILL`. Шаг 9 пропущен (`skip` при одноузловом `patch`) → источника нет, и секция не
   заводится вовсе: отсутствующая секция честнее сочинённой.

Вырезки считаются в бюджет узла на шаге 10 наравне с остальным телом: пример, из-за которого тикет
не влезает в окно, — та же причина резать узел, что и длинный контракт.

### Чужая библиотека — факт, а не память модели

Репозиторий с нестандартными решениями — обычный случай, а не исключение, и опасен он ровно одним:
библиотека, лежащая **вне дерева прогона** (внутренний пакет, приватный реестр), в граф не попадает —
границей служит cwd минус зависимости. Узла нет, `<dep>` нет, примера нет — и слабый тир напишет «как
принято в интернете», то есть по претрейну. Два механизма закрывают это без картирования чужого кода:

1. **Пример берётся из вызывающего кода.** Импорт, не резолвящийся в узел графа, тянет в
   `$START_EXAMPLE` вырезку **реального вызова из этого репозитория**. Библиотека остаётся чёрным
   ящиком, но её идиома приезжает фактом — тем же способом, каким приезжает раннер.
2. **Вызовов нет — спрашиваем, а не гадаем.** Импорт без узла и без единого примера объявляется
   `<gap>` на шаге 5 и становится **типизированным вопросом оператору на шаге 10** (раньше он не
   блокирует, позже — уже поздно: тикет без идиомы уедет исполнителю):

| ответ оператора | следствие |
|---|---|
| **пример** — фрагмент кода | едет в `$START_EXAMPLE` тикетов с источником `operator-answer` |
| **путь к исходнику** библиотеки | путь входит в границу разведки, шаги 3–5 гоняют по нему клетку `kind: "vendor"` ⇒ библиотека становится узлами графа, дальше всё как обычно |
| **навык** — файл/папка с идиомой | подключается секцией `$START_SKILL` целиком, с путём как источником |

Форму ответа классифицирует **скрипт**: существует каталог → `vendor`, файл навыка → `skill`, иначе
текст-пример. Роль здесь не нужна — 0 токенов, ключ вопроса, как всегда, копирует машина из
`pending.json`.

`$START_SKILL` — **единственная секция тикета, не выведенная из репозитория**, поэтому источник у неё
обязателен: секция без пути неотличима от выдумки модели, а весь запрет invented-default стоит именно
на различимости этих двух вещей. Содержимое примера и навыка считается в бюджет окна на шаге 10 —
толстый навык режет узел, а не молча раздувает тикет.

## Исполнение (шаг 15)

```
K = 6                                          предел повторов на узел

close(node) =                                  ВЕСЬ цикл — скрипт; роль внутри него только работает
  until( green(checkFile(node)) or round > K )
     implement(ticket(node), feedback = lastOutput)   ⇒ РОЛЬ: пишет тест и код, git не трогает
  green ? done : ask(operator, lastOutput)            ⇒ СКРИПТ: чек и пауза; коммита здесь НЕТ

checkFile(node) = suite.one с подставленным тестом узла     команду собрал шаг 10, здесь её исполняют
batch(level)    = узлы уровня DAG БЕЗ общих файлов
```

**Git исполнителю запрещён — целиком.** Побочные эффекты VCS суверенны и живут в двух местах: шаг 13
режет ветку, шаг 17 коммитит **принятое** и открывает PR. В `$START_FORBIDDEN`
тикета стоит запрет на любую git-команду (`commit`, `checkout`, `branch`, `stash`, `reset`,
`rebase`), и права записи роли ограничены файлами её узла. Причина не гигиеническая: исполнитель,
закоммитивший красное или откативший соседа, стирает ровно тот след, по которому шаг судит, — а
судит здесь чек, не роль (правило 2).

**Во время реализации не коммитят вовсе.** Работа копится в рабочем дереве ветки; истории по узлам
не появляется, и шаги 16-17 читают **дифф от `baseSha`**, а не журнал коммитов. Следствие названо
вслух: поузлового отката средствами git нет — испорченный узел чинится ещё одним раундом цикла, а
состояние после паузы оператора живёт в рабочем дереве, не в индексе.

**Тест и код едут одним тикетом — это TDD, а не экономия.** Тот же исполнитель пишет тест по формуле
и доводит его до зелёного; отдельный узел на тест осмыслен только там, где тест и так свой узел
(`scenario`, поверх нескольких узлов кода).

**Цикл судит тест УЗЛА, а не сьют целиком:** `suite.one` подставляет файл теста, поэтому раунд стоит
секунды, а не полный прогон. `one` в графе пуст → гоняется сьют целиком, и эта цена пишется в лог —
молчаливой деградации в стоимости не бывает.

**Предел `K = 6`, дальше — оператор, а не падение прогона.** Узел, не сошедшийся за шесть раундов,
приезжает оператору с последним выводом чека: работа по остальным узлам уже лежит в дереве,
выбрасывать её из-за одного дорого.

## Приёмка (шаг 16)

```
accept : (Branch, PlanIndex, Graph) -> Accept | Regress | Ask
  suites  = все <suite> графа, порядком unit → component → contract (+ валидатор спеки, если был узел spec)
  diff    = git diff baseSha ⋃ untracked        дерево, не журнал: коммитов в реализации нет
  covered = ∀ node ∈ plan · файлы узла ∈ diff   узел, где никто ничего не сделал, ловится здесь
  extra   = diff \ файлы узлов плана            остаётся при зелёном сьюте, но объявлен
```

**Красный сьют разбирается адресно, пока это дёшево:** имя упавшего теста → путь → узел плана. Попал
ровно в один узел — вывод чека едет фидбеком в цикл 15 этому узлу. Попал в двоих, ни в одного, или
тест не резолвится — это регресс между узлами, виновника вычислить нечем, и полоса встаёт с вопросом
оператору и выводом чека. Гадать здесь дороже, чем спросить.

**Файл вне плана — не отказ, но и не тишина.** При зелёном сьюте он остаётся и едет в `accept.json`
как `extra[]`, откуда попадает в тело PR: регистрация в конфиге и генерённый файл — обычная жизнь
чужого репозитория, а вот молчаливая правка за пределами плана — нет.

**Базлайн шага 13 делает этот шаг уликой.** Все сьюты были зелены до первой строчки работы, значит
красное здесь — наше, а не наследство. Без базлайна тот же красный доказывал бы только то, что
репозиторий был сломан и раньше.

## PR — конец полосы (шаг 17)

```
pr : (Accept, PlanIndex, Branch) -> Link | Blocked
  precondition  accept.verdict == green      без зелёной приёмки шага нет вовсе
  commit(all)   один коммит на всю принятую работу, сообщение — по соглашению репозитория
  push -u       ветка уезжает на remote
  open(host)    gh | glab по факту remote и окружения ⇒ ссылка оператору в терминале pi
```

**Один коммит на всю работу.** Принята ветка целиком, а не узел за узлом, — история отражает
принятое решение, а не путь к нему. Сообщение и заголовок PR пишутся **по соглашению репозитория**
(четвёртый вопрос разведки, при пустом ответе — фактом из `git log` транка), а не по вкусу полосы:
чужой репозиторий узнаёт свой стиль коммита так же, как узнаёт свой раннер.

**Тело PR выведено, а не сочинено:** узлы плана с их командами проверки · сьюты с результатом из
`accept.json` · узел тогла с состоянием OFF · `extra[]` отдельным списком. Проза, которой нет
источника в артефактах, в тело не попадает.

**Хостинг — факт окружения.** `git remote get-url` даёт хост, наличие `gh`/`glab` — способ. Нет ни
того ни другого → `blocked` с именем ветки и готовой командой: человек откроет PR сам. Выдумывать
канал доставки полоса не станет — здесь она кончается, и последнее слово всё равно за человеком.

**Параллель ограничена файлами, а не фантазией:** файлы узла известны из плана, поэтому батч
собирается из узлов одного уровня DAG **без пересечения файлов**; остальное едет следующим батчем.
Изоляция worktree-ами здесь не нужна — она покупает параллелизм ценой конфликтов мержа, которые
кому-то придётся решать, а решать их некому.
