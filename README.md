# izi-pi

Конвейер, который превращает требование человека в план работ, проверяемый машиной на каждом шаге.

> Зачем это устроено именно так — `docs/concept.md`. Как оно работает внутри — `docs/workflow.md`.

## Что умеет и чего не делает

**Умеет**

- Читает сырое требование и делает из него измеримый BRD.
- Картирует незнакомый репозиторий: модули, связи, тесты, сборку.
- Сводит требование с реальностью кода — сценарии, дельты, режимы отказа.
- Считает вес изменения по SemVer и подграф затронутого.
- Рисует поток данных и контракты до нарезки на задачи.
- Выдаёт план: узлы работы, порядок, команда проверки каждого.

**Не делает**

- Не пишет код и не трогает рабочее дерево проекта.
- Не режет ветки, не коммитит, не открывает PR.
- Не работает с пустым репозиторием — ему нечего картировать.
- Не изобретает то, чего нет: спрашивает или объявляет пробел.
- Не решает за человека — план утверждает оператор.
- Не продолжает прогон после перезапуска: квитанций пока нет.

Полоса сегодня — **десять шагов из семнадцати**: `task → brd → survey-plan → scope → graph →
intake → weight → ripple → design → plan`. Остальные семь описаны в концепте как план, не как код.

## Стек

| Компонент | Технология |
|---|---|
| Оркестратор прогона | `pi` + расширение `pi-extensible-workflows` |
| Программа полосы | Node ESM, без зависимостей (`workflows/izi.js`) |
| Доступ к диску | расширение `ext/` — единственное место с `fs` |
| Роли (шаги с суждением) | LLM через openrouter, модель объявлена в файле роли |
| Скриптовые шаги | чистые модули `steps/*/`, 0 токенов |
| Тесты | `node:test`, без раннеров |
| Артефакты прогона | `.agent/` — XML и JSON, читаемые и человеком, и скриптом |

## Команды

| Команда | Аргументы | Что делает |
|---|---|---|
| `/izi` | — | запускает прогон в открытой сессии `pi` |
| `node bin/install.mjs` | `--to=<путь к проекту>` | ставит харнес в проект, где будет прогон |
| `node bin/answer.mjs` | `--q="<вопрос>" --text="<ответ>"` | запасной канал ответа оператора, помимо чата |
| `node --test` | — | прогоняет весь набор тестов харнеса |

## Как это работает по шагам

**`/izi` — прогон полосы**

```
| Оператор кладёт требование в TASK.md
| Роль gate решает, решаемо ли, и чем грепать → .agent/brd.md
| Скрипт режет дерево репозитория на клетки → .agent/survey-plan.json
| Рой скаутов описывает клетки              → .agent/graph-parts/
| Скрипт сливает части в карту              → .agent/appgraph.xml
| Роль intake сводит требование с картой    → .agent/frd.xml
| Скрипт взвешивает дельты по SemVer        → .agent/mode
| Скрипт считает подграф изменения          → .agent/ripple.xml
| Роль designer рисует контракты и поток    → .agent/data-flow.md
| Скрипт собирает план работ                → .agent/plan-index.json
```

Каждый шаг судит скрипт-гардрейл, а не роль: «готово» говорит код возврата. Роль, нашедшая проблему,
отработала успешно — отрицательный вердикт это данные.

**`node bin/install.mjs --to=<проект>`**

```
| Читает каталоги харнеса: workflows, steps, core, bin
| Копирует их в указанный проект
| Проверяет .gitignore на .agent/ и .izi/
| Печатает команду запуска
```

**`node bin/answer.mjs --q --text`**

```
| Читает открытый вопрос из .agent/pending.json
| Отвергает текст-заглушку вместо ответа
| Дописывает пару вопрос-ответ в .agent/answers.md
| Прогон подхватывает ответ на следующей проверке
```

**`node --test`**

```
| Собирает *.test.mjs по всем срезам
| Гоняет чистые ядра по формуле «1 happy + ветви»
| Красный тест = результат, а не повод его править
```

## Чем кончается прогон

| Код | Что значит | Виды |
|---|---|---|
| 0 | план готов, артефакты в `.agent/` | — |
| 10 | полоса встала осознанно, причина названа | `blocked`, `question`, `escalate`, `invalid` |
| 2 | сбой самого прогона | `crashed` |

`blocked` — репозиторий или артефакт не годится (нет тестов, нет веса, узел нечем закрыть).
`question` — оператор не ответил за отведённые круги. `escalate` — оператор отклонил паузу либо
кончились пере-делегации. `crashed` — упал сам харнес; чаще всего это старая сессия `pi`, и диагноз
говорит об этом прямо. Ничего не маскируется под успех: каждый отказ стирает недописанный артефакт.

## Запуск

```bash
cd ext && npm install && cd ..     # один раз на машину: расширению нужен хост-пакет
node --test                        # обязано быть зелёным до живого прогона

node bin/install.mjs --to=<проект> # поставить харнес в проект
cd <проект> && pi                  # запускать pi ИЗ каталога прогона, затем в чате: /izi
```

Расширение подключается один раз — либо `pi install ./ext`, либо путём в `~/.pi/agent/settings.json`
(поле `packages`). Второй способ удобнее при разработке: правка в `ext/` видна без переустановки.
Но видна она **только после перезапуска `pi`** — расширение читается при старте сессии, а программа
полосы на каждом прогоне. Симптом старой сессии: `<имя> is not defined`, и прогон называет починку
прямо в диагнозе.

Требование кладётся в `TASK.md` проекта. Вопросы роли приезжают обычными сообщениями в тот же чат —
второй терминал не нужен.
