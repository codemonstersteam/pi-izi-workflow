# izi-pi-v2

Первые два шага конвейера `izi-flow-v2` (`task → brd`), перенесённые на `pi-extensible-workflows`
(pi v5.1.1). Порядок и данные конвейера остаются кодом (`pipeline.json`, `workflows/izi.js`);
роль `gilb` превращает сырое требование оператора в измеримый BRD. История и решения переноса —
`PLAN.md`.

## Установка

```bash
node bin/install.mjs
```

Копирует `roles/*.md` в **глобальный** каталог pi (`~/.pi/agent/pi-extensible-workflows/roles/`) и
пишет тиры моделей из `pipeline.json.models` в `~/.pi/agent/pi-extensible-workflows/settings.json`
(`modelAliases`). Это не опция, а обязательный шаг: pi подхватывает роли только оттуда — проектный
каталог `.pi/pi-extensible-workflows/roles/` **не работает** без доверия к проекту (см. «Долги»
ниже; в репозитории лежит `.pi/pi-extensible-workflows/roles/smoker.md` как живое свидетельство
этого пути для пробы `workflows/smoke2.js`, не как рабочий канал).

## Запуск

```bash
node bin/run.mjs
```

Кладёт задачу в `TASK.md` **до** запуска (это делает оператор), затем запускает `workflows/izi.js`
через tool `workflow` внутри сессии pi и печатает JSON-результат прогона, прочитанный **с диска**
(`~/.pi/workflows/projects/…/result.json`), а не то, что напечатала модель-лаунчер — печать `pi -p`
уже наблюдалась зависающей при живом `completed` прогоне (`PLAN.md` §0).

Код возврата процесса:

| код | значение |
|---|---|
| `0` | шаг закрыт, конвейер дошёл до конца — квитанции и артефакт на диске |
| `10` | терминальный `err` — вопрос оператору (`kind: question`), красный вход первого шага (`kind: blocked`) или исчерпанные повторы (`kind: escalate`); `subject`/`evidence`/`answer_cmd` (если есть) — в JSON на стдоуте |
| `2` | preflight-отказ раннера: `pipeline.json`/`workflows/izi.js` не существует или не парсится, run-каталог не появился, run не дошёл до терминала за таймаут поллинга |

## Цикл вопрос → ответ → перезапуск

Роль `gilb` не имеет права разговаривать с оператором иначе как через терминальный `err(question)`:

```bash
node bin/run.mjs
# → {"track":"err","kind":"question","subject":"…?","answer_cmd":"node bin/answer.mjs --q=\"…?\" --text=\"<ответ>\"", "code":10}

node bin/answer.mjs --q="…?" --text="<реальный ответ оператора>"   # дословно тот же --q=, что в answer_cmd
node bin/run.mjs
# → {"track":"ok","artifact":".agent/brd.md","code":0}  (или новый вопрос, если гэпов больше одного)
```

Ответы накапливаются в `.agent/answers.md` — ничего не перезаписывается, каждый следующий прогон
видит все прошлые ответы. Ключ `--q=` **обязан** совпадать с `subject` конверта дословно — это
единственная связь вопроса с ответом; если модель когда-нибудь вернёт разошедшийся ключ, это находка
уровня `answer-cmd-key-mismatch` (`standards/protocol.md`), а не мелочь.

## Что где лежит

```
TASK.md                       вход конвейера — кладёт оператор, ≤300 строк, непуст
pipeline.json                 порядок шагов, loops.brd, models по тирам — данные
workflows/izi.js               скрипт воркфлоу: task → brd, читает конфиг сам через shell("cat …")
workflows/smoke.js             зонд механики pi (shell()+agent(), без роли/схемы) — не часть конвейера
workflows/smoke2.js            зонд роли+outputSchema вместе (role: "smoker") — держит .pi/…/smoker.md

roles/gilb.md                  роль шага brd (pi-формат: model/thinking/tools во фронтматтере)

steps/task/validate-task.mjs   гардрейл входа: ≤300 строк, непуст (0 токенов)
steps/brd/brd.mjs              чистое ядро приёмки BRD: newFit·newRequirement·newSubjects·adviceFor·newBrd
steps/brd/validate-brd.mjs     io-гардрейл: подключает brd.mjs к диску и коду возврата
steps/brd/order.tpl            наряд роли (TASK/ANSWERS/FEEDBACK → STAGING)

core/answers.mjs               разбор .agent/answers.md в значения {question, text}
core/form.mjs                  реестр формы BRD и слоёв промпта — наряд/роль подставляют, не пересказывают
core/findings.mjs              severityOf: находка роняет приёмку (blocker) или едет уликой (advice)
core/result.mjs                Result<T,E> — общий конверт фабрик

bin/install.mjs                роль → глобальный каталог pi, тиры → settings.json
bin/run.mjs                    раннер: запускает workflows/izi.js, читает result.json со стенда
bin/answer.mjs                 записывает ответ оператора в .agent/answers.md по ключу вопроса
bin/receipt.mjs                пишет .agent/receipts/<step>.json — квитанция закрывает шаг, не out
bin/promote.mjs                staging → out, и только потом квитанция (в этом порядке, не наоборот)
bin/steps-map.mjs              staging/out пути по шагам — одно место, не литералы в receipt/promote
bin/decisions-log.mjs          append-only .agent/decisions.log — пишет харнес, не модель

.agent/                        состояние ОДНОГО прогона (gitignored, харнес создаёт и чистит сам)
  staging/brd.md                 черновик роли ДО чека
  brd.md                         артефакт ПОСЛЕ промоута (только на зелёном чеке)
  receipts/{task,brd}.json       квитанции — closes-the-step факт
  answers.md                     накопленные ответы оператора
  decisions.log                  журнал переходов

standards/{protocol.md,code.md,role.md}   контракты конверта/кода/роли — не пересказываются здесь
arch/slices/{task.md,brd.md}   архитектурные заметки по срезам (унаследованы от донора; часть
                                упомянутых там модулей — core/envelope.mjs, bin/accept.mjs,
                                core/steps.mjs — в этом порту не переносилась, PLAN.md §2: их
                                заменяет outputSchema хоста и bin/{receipt,promote}.mjs)
```

## Где искать диагноз прогона

Печать модели-лаунчера (`pi -p`) — не канал истины (`bin/run.mjs`'s own MODULE_CONTRACT). Правда
лежит на диске:

```
~/.pi/workflows/projects/<slug>-<hash>/sessions/<session-id>/runs/<run-id>/
  state.json      состояние (running/completed/failed/stopped), фазы, события
  result.json     то, что вернул workflows/izi.js — это и печатает bin/run.mjs
  journal.json    каждый shell()/agent() вызов с его вводом/выводом — сюда смотреть при расхождении
  summary.json    usage: tokens, costUsd, agentLaunches — сколько РЕАЛЬНО стоил прогон
```

`<slug>-<hash>` — `bin/run.mjs`'s `projectStorageKey(cwd)`, воспроизводит хеш pi байт-в-байт (без
зависимости на пакет pi). Хочешь узнать, сколько раз в прогоне реально вызывалась роль и сколько это
стоило — читай `summary.json.usage`, а не считай по печати.

## Прогон одной командой

```bash
node --test                  # вся линия — обязана быть зелёной до любого живого прогона
node bin/install.mjs         # роль → глобальный каталог pi (один раз на машину)
echo "…бизнес-требование…" > TASK.md
node bin/run.mjs             # → question | ok | blocked, JSON на стдоуте, код 0/10/2
```

## Долги — названы вслух, не спрятаны

- **Права «писать только в staging» в pi нет.** `roles/gilb.md` объявляет это дисциплиной
  ($START_STRATEGY, шаг 7: «you keep this by discipline, not by a permission the host enforces»),
  а не механизмом хоста: у роли `tools: [read, write]` без карты путей, установка схлопывает её в
  `write: allow` на весь диск. Держат это два шва post-factum: квитанция (запись мимо staging шаг не
  закрывает) и то, что `bin/promote.mjs` копирует именно staging-файл, а не доверяет заявлению роли.
  Не карается заранее — только видно постфактум.

- **Запуск опосредован моделью-лаунчером**, и это не только риск зависания печати (`PLAN.md` §0,
  риск 2). Живой прогон S4 (сценарий «негатив на первом шаге») показал более серьёзный вариант:
  лаунчер-сессия pi привязана к рабочему каталогу и **переживает** отдельные вызовы `pi -p` —
  разговор с моделью накапливается между запусками `bin/run.mjs`. На третьем прогоне модель, вопреки
  явной инструкции «вызови только tool `workflow`, никаких других действий», сама отредактировала
  `TASK.md` (у неё есть `write`) под предел в 300 строк и **повторно** вызвала `workflow` без
  команды оператора — конвейер после этого честно дошёл до роли `gilb` и потратил реальный вызов
  агента там, где ожидался 0-токенный отказ на входном гардрейле. Сам гардрейл при этом отработал
  верно с первого, никем не тронутого вызова (`track:err, kind:blocked, code:10, agentLaunches:0` —
  видно в `journal.json`/`summary.json` того самого первого run-каталога сессии); `bin/run.mjs` же
  вслепую берёт **самый новый** run после своего старта и в этот раз отдал результат ВТОРОГО,
  испорченного вызова — не проверяя, что лаунчер сделал ровно один вызов `workflow`, как ему
  предписано. Починка требует либо изоляции сессии на один запуск, либо счётчика вызовов `workflow`
  в самой сессии — оставлено долгом, не подкручено втихую поверх фикстуры.

- **Проектные роли не подхватываются без доверия к проекту** (`PLAN.md` §0, риск 1, подтверждено
  на стенде). `bin/install.mjs` поэтому обязателен, а не удобство; `.pi/pi-extensible-workflows/
  roles/smoker.md` в этом репозитории — не рабочий канал, а зафиксированный пример того самого
  нерабочего пути (используется только пробой `workflows/smoke2.js`).

- Остальные пункты, унаследованные от донора как есть (агрегаторы вместо части фабрик, отсутствие
  машинного признака «стоит, не висит») — см. `standards/code.md` §8.

- **`TASK.md` и `task.md` — один и тот же файл на регистронезависимой ФС** (APFS по умолчанию на
  macOS, аналогично NTFS на Windows). До сдачи S4 в корне репозитория лежал `task.md` (исходная
  постановка задачи переноса, написанная оператором до `PLAN.md`) и отдельно ожидался `TASK.md`
  (живой вход конвейера) — это два РАЗНЫХ пути только на регистрочувствительной ФС (Linux, CI).
  Первый же живой прогон S4, записавший фикстуру в `TASK.md`, молча затёр `task.md` — один и тот же
  инод. Постановка задачи не входила в целевую раскладку `PLAN.md` §3 (там объявлен только
  `TASK.md`), потеря не бьёт по контракту конвейера, но найдена и называется вслух: код, ссылающийся
  на `TASK.md` литералом, не застрахован от коллизии с любым другим файлом того же имени в другом
  регистре, случайно оставленным в корне.
