# izi-pi-v2

Первые два шага конвейера `izi-flow-v2` (`task → brd`), перенесённые на `pi-extensible-workflows`
(pi v5.1.1). Порядок и данные конвейера остаются кодом (`pipeline.json`, `workflows/izi.js`);
роль `gilb` превращает сырое требование оператора в измеримый BRD. История и решения переноса —
`PLAN.md`.

## Установка

```bash
node bin/install.mjs
```

Копирует `roles/*.md` в **глобальный** каталог pi (`~/.pi/agent/pi-extensible-workflows/roles/`),
`prompts/*.md` в **глобальный** каталог prompt-шаблонов pi (`~/.pi/agent/prompts/`) и пишет тиры
моделей из `pipeline.json.models` в `~/.pi/agent/pi-extensible-workflows/settings.json`
(`modelAliases`). Это не опция, а обязательный шаг: pi подхватывает роли и проектные prompt-шаблоны
только из глобального каталога — проектные `.pi/pi-extensible-workflows/roles/` и `.pi/prompts/`
**не работают** без доверия к проекту (см. «Долги» ниже; в репозитории лежит
`.pi/pi-extensible-workflows/roles/smoker.md` как живое свидетельство этого пути для пробы
`workflows/smoke2.js`, не как рабочий канал). После установки `/izi` — команда в окне pi (pi's own
prompt templates,
`/opt/homebrew/lib/node_modules/@earendil-works/pi-coding-agent/docs/prompt-templates.md`).

## Запуск

```bash
node bin/run.mjs
```

Кладёт задачу в `TASK.md` **до** запуска (это делает оператор), затем запускает `workflows/izi.js`
через tool `workflow` внутри сессии pi и печатает JSON-результат прогона, прочитанный **с диска**
(`~/.pi/workflows/projects/…/result.json`), а не то, что напечатала модель-лаунчер — печать `pi -p`
уже наблюдалась зависающей при живом `completed` прогоне (`PLAN.md` §0).

Код возврата процесса:

| код | значение |
|---|---|
| `0` | шаг закрыт, конвейер дошёл до конца — квитанции и артефакт на диске |
| `10` | терминальный `err` — вопрос оператору (`kind: question`), красный вход первого шага (`kind: blocked`) или гардрейл `brd` исчерпал повторы либо оператор нажал Reject (`kind: escalate`); `subject`/`evidence`/`answer_cmd` (если есть) — в JSON на стдоуте. **`question` ≠ `escalate` даже когда оба код `10`**: на канале `checkpoint` `kind: question` с полем `diagnosis` означает «бюджет обменов с оператором (`pipeline.json.questions`/`checkpointRetries`) исчерпан» — роль не отказывалась и не получала плохого ответа, оператор просто не ответил вовремя; `kind: escalate` — либо `loops.brd` красных чеков гардрейла исчерпан, либо оператор явно нажал Reject. Разные причины, разный следующий шаг (см. «Два счётчика» ниже) |
| `2` | preflight-отказ раннера: `pipeline.json`/`workflows/izi.js` не существует или не парсится, `pipeline.json.operatorChannel="checkpoint"` (headless не проводит чекпоинты — см. ниже), run-каталог не появился, run не дошёл до терминала за таймаут поллинга |

## Цикл вопрос → ответ: два канала

Роль `gilb` не имеет права разговаривать с оператором иначе как через `err(question)`. КАК этот
вопрос доезжает до оператора — политика прогона, объявленная данными в `pipeline.json.operatorChannel`
(как `loops` и `models`; поле, не объявленное в файле, роняет прогон терминальным `crashed`, код `2` —
молчаливого умолчания здесь нет). Ровно два допустимых значения.

**Факт хоста, который решает выбор.** `checkpoint(input)` в песочнице `pi-extensible-workflows`
возвращает вызывающему скрипту (`workflows/izi.js`) только строку `"approved"` | `"rejected"` — и
ничего больше; интерактивная сторона видит `ui.select(prompt, ["Approve", "Reject"])`
(`~/.pi/agent/npm/node_modules/pi-extensible-workflows/src/host.ts`). **Текст ответа оператора этим
каналом не едет никогда** — он по-прежнему приезжает единственным путём, файлом `.agent/answers.md`,
который скрипт перечитывает через `shell("cat …")`. Второй факт: headless `pi -p` (им пользуется
`bin/run.mjs`) чекпоинт провести физически не может — `checkpointBridge` отказывает кодом
`RESUME_INCOMPATIBLE` ("Foreground checkpoints require UI") ещё до того, как дошло бы до Approve/Reject
(проверено живьём: пробный прогон с ровно тем вызовом `checkpoint({...})`, что в `workflows/izi.js`,
прошёл preflight — run-каталог создался — и упал на этой самой ошибке, `agentLaunches:0`, `tokens:0`).
Поэтому канал обязан выбираться, а не быть один на всех.

### `operatorChannel: "terminal"` — headless, `bin/run.mjs`

Прежнее поведение, без изменений. Прогон, упёршийся в `err(question)`, завершается терминально —
оператор отвечает и перезапускает **весь прогон**:

```bash
node bin/run.mjs
# → {"track":"err","kind":"question","subject":"…?","answer_cmd":"node bin/answer.mjs --q=\"…?\" --text=\"<ответ>\"", "code":10}

node bin/answer.mjs --q="…?" --text="<реальный ответ оператора>"   # дословно тот же --q=, что в answer_cmd
node bin/run.mjs
# → {"track":"ok","artifact":".agent/brd.md","code":0}  (или новый вопрос, если гэпов больше одного)
```

Ответы накапливаются в `.agent/answers.md` — ничего не перезаписывается, каждый следующий прогон
видит все прошлые ответы. Ключ `--q=` **обязан** совпадать с `subject` конверта дословно — это
единственная связь вопроса с ответом; если модель когда-нибудь вернёт разошедшийся ключ, это находка
уровня `answer-cmd-key-mismatch` (`standards/protocol.md`), а не мелочь.

### `operatorChannel: "checkpoint"` — интерактивное окно pi

Прогон **встаёт паузой** вместо терминального возврата: тот же live-run продолжается со следующей
итерации цикла `brd`, ничего перезапускать руками не нужно. Долг «прогон приходится перезапускать на
каждый вопрос» — закрыт на этом канале. Это значение стоит в `pipeline.json` по умолчанию: репозиторий
и песочница pi по факту используются из интерактивного окна pi, где пауза дешевле, чем перезапуск
всего прогона.

Что печатает оператор — **одно сообщение на весь прогон**, до того, как задавать `TASK.md`:

```
/izi
```

Это prompt template (`prompts/izi.md` в репозитории, установленный `bin/install.mjs` в
`~/.pi/agent/prompts/izi.md` — см. «Установка» выше и pi's own
`docs/prompt-templates.md`); он раскрывается в ровно тот же наряд модели-лаунчеру, что и раньше.
Если шаблон не установлен (`/izi` не находится автодополнением), запасной путь — напечатать текст
абзацем самому, дословно:

```
запусти workflow izi (scriptPath: workflows/izi.js, foreground: true)
```

Это же первое сообщение можно передать `pi` через argv, минуя ручной ввод в редакторе — `pi`
принимает первое сообщение сессии аргументом командной строки, так что `pi --model … "/izi"`
стартует интерактивную сессию с уже запущенным воркфлоу; удобно для алиаса.

Дальше в окне pi:

1. Прогон идёт сам до первого вопроса роли `gilb`. Появляется пауза-чекпоинт с именем `brd-q<N>` —
   в нём дословно вопрос роли, готовая команда `node bin/answer.mjs --q="…" --text="<ответ>"` и
   строка «выполните команду, затем Approve». Ничего домысливать не нужно — весь текст самодостаточен.
2. Оператор открывает терминал **этого же репозитория** и выполняет команду ровно как написано,
   подставив реальный ответ вместо `<ответ>`.
3. Оператор нажимает **Approve** в окне pi. (**Reject** на любой итерации — вопрос уходит человеку
   эскалацией, `kind: escalate`, прогон останавливается терминально, код `10`.)
4. **Approve сам по себе не факт ответа — только барьер.** `checkpoint(input)` возвращает раннеру
   ровно строку `approved`/`rejected` и ничего больше (см. «Факт хоста» выше) — оператор может
   нажать Approve, ничего не выполнив. Поэтому `workflows/izi.js` не верит клику: он снимает
   `.agent/answers.md` ДО паузы и после каждого Approve сверяет его ЖЕ с копией ПОСЛЕ —
   `core/answer-arrived.mjs` (`answerArrived(before, after, subject)`, юнит-тесты в
   `core/answer-arrived.test.mjs`; в `workflows/izi.js` — та же проверка инлайн, тем же приёмом, что
   и `core/operator-channel.mjs`, песочница без `import`). Ответом считается только: файл реально
   изменился **и** в нём появилась запись `- вопрос: …` с ключом, дословно совпадающим с `subject`
   роли. Если это не так — роль **не зовётся заново** (пере-делегация деньги стоит, переспрос — нет):
   та же самая пауза открывается снова, с явной пометкой «ответ не найден, похоже, команда не
   выполнена». Число таких переспросов на ОДИН вопрос ограничено `pipeline.json.checkpointRetries`
   (по умолчанию 2); исчерпаны — терминальный `err(question)` с диагнозом «ответ не получен за N
   переспросов», код `10` (это **не** `escalate`: роль не отказывалась и не получала плохого ответа —
   его не было вовсе).
5. Ответ подтверждён на диске → прогон перечитывает `.agent/answers.md`, собирает наряд заново и
   вызывает роль ещё раз — **это не пере-делегация по красному чеку** и `pipeline.json.loops.brd` не
   тратит (см. «Два счётчика» ниже). Если гэпов больше одного, шаг 1 повторяется со следующим
   `brd-q<N+1>`; общее число вопросов за прогон ограничено `pipeline.json.questions` (по умолчанию
   3) — исчерпан и он → терминальный `err(question)` с диагнозом «вопросов за прогон больше, чем
   позволяет pipeline.json.questions», код `10`, тоже не `escalate`.
6. На зелёном чеке прогон возвращает `{"track":"ok","artifact":".agent/brd.md","code":0}` **в том же
   окне pi** — файл `.agent/brd.md` уже на диске, `node bin/run.mjs` для этого не нужен.

Ограничение хоста: `checkpoint`'s `prompt` обрезается на 1024 байтах UTF-8 (кириллица — по 2 байта на
символ). Если собранный текст вопроса (включая пометку переспроса на шаге 4) этот предел превышает,
`workflows/izi.js` не зовёт `checkpoint()` вовсе и возвращает тот же вопрос терминально, как на канале
`terminal`, с записью в `log()` — молча придумывать сокращённый текст чужого вопроса значило бы
исказить его, а не ужать.

### Два счётчика, а не один

`pipeline.json.loops.brd` и обмены с оператором — **разные бюджеты**, разведённые нарочно (раньше
делили один счётчик — живой прогон умер именно на этом: три Approve без единого `bin/answer.mjs`
читались как три красных чека той же роли, `loops.brd` заканчивался, и терминальный `escalate`
называл причиной «повторы исчерпаны», хотя роль ни разу не получила ответа):

| счётчик | что тратит | где объявлен | исчерпан → |
|---|---|---|---|
| `loops.brd` | ТОЛЬКО красный чек гардрейла (пере-делегация роли, оплаченный `agent()`) | `pipeline.json.loops.brd` | `kind: escalate`, код `10` |
| `questions` | каждый раз, когда роль вообще задаёт вопрос за прогон | `pipeline.json.questions` | `kind: question`, код `10` — не `escalate` |
| `checkpointRetries` | переспрос ОДНОГО И ТОГО ЖЕ вопроса без ответа на диске | `pipeline.json.checkpointRetries` | `kind: question`, код `10` — не `escalate` |

Итерация цикла с вопросом (checkpoint approved, ответ подтверждён) не трогает `loops.brd` — это видно
по структуре `workflows/izi.js`: у цикла `brd` два независимых счётчика (`attempt` для `loops.brd`,
`questionsAsked` для `questions`), и только ветка красного чека увеличивает `attempt`. Оба поля не
объявлены в `pipeline.json` → терминальный `crashed`, код `2`, тем же приёмом, что уже сделан для
`operatorChannel` — молчаливого дефолта нет ни у одного из трёх счётчиков.

### Headless и `checkpoint` вместе не работают

`bin/run.mjs` перед запуском `pi -p` сам проверяет `pipeline.json.operatorChannel`: значение
`"checkpoint"` — это отказ preflight, код `2`, с диагнозом «переключите канал на `"terminal"`».
Файл `pipeline.json` при этом не трогается программой: подмена поля на лету — гонка и грязное дерево
для любого параллельного читателя того же файла (в том числе самого `workflows/izi.js`, который
перечитывает `pipeline.json` независимо, своим собственным `shell("cat …")`). Переключение — ручное
действие оператора, ровно на время headless-прогона.

## Где искать диагноз прогона

Печать модели-лаунчера (`pi -p`) — не канал истины (`bin/run.mjs`'s own MODULE_CONTRACT). Правда
лежит на диске:

```
~/.pi/workflows/projects/<slug>-<hash>/sessions/<session-id>/runs/<run-id>/
  state.json      состояние (running/completed/failed/stopped), фазы, события
  result.json     то, что вернул workflows/izi.js — это и печатает bin/run.mjs
  journal.json    каждый shell()/agent() вызов с его вводом/выводом — сюда смотреть при расхождении
  summary.json    usage: tokens, costUsd, agentLaunches — сколько РЕАЛЬНО стоил прогон
```

`<slug>-<hash>` — `bin/run.mjs`'s `projectStorageKey(cwd)`, воспроизводит хеш pi байт-в-байт (без
зависимости на пакет pi). Хочешь узнать, сколько раз в прогоне реально вызывалась роль и сколько это
стоило — читай `summary.json.usage`, а не считай по печати.

## Прогон одной командой

```bash
node --test                  # вся линия — обязана быть зелёной до любого живого прогона
node bin/install.mjs         # роль и /izi → глобальный каталог pi (один раз на машину)
echo "…бизнес-требование…" > TASK.md
node bin/run.mjs             # → question | ok | blocked, JSON на стдоуте, код 0/10/2
```

## Долги — названы вслух, не спрятаны

- **Права «писать только в staging» в pi нет.** `roles/gilb.md` объявляет это дисциплиной
  ($START_STRATEGY, шаг 7: «you keep this by discipline, not by a permission the host enforces»),
  а не механизмом хоста: у роли `tools: [read, write]` без карты путей, установка схлопывает её в
  `write: allow` на весь диск. Держат это два шва post-factum: квитанция (запись мимо staging шаг не
  закрывает) и то, что `bin/promote.mjs` копирует именно staging-файл, а не доверяет заявлению роли.
  Не карается заранее — только видно постфактум.

- **Запуск опосредован моделью-лаунчером**, и это не только риск зависания печати (`PLAN.md` §0,
  риск 2). Живой прогон S4 (сценарий «негатив на первом шаге») показал более серьёзный вариант:
  лаунчер-сессия pi привязана к рабочему каталогу и **переживает** отдельные вызовы `pi -p` —
  разговор с моделью накапливается между запусками `bin/run.mjs`. На третьем прогоне модель, вопреки
  явной инструкции «вызови только tool `workflow`, никаких других действий», сама отредактировала
  `TASK.md` (у неё есть `write`) под предел в 300 строк и **повторно** вызвала `workflow` без
  команды оператора; `bin/run.mjs` вслепую брал **самый новый** run после своего старта и в этот
  раз отдал результат ВТОРОГО, испорченного вызова, хотя первый, никем не тронутый вызов уже отработал
  верно (`track:err, kind:blocked, code:10, agentLaunches:0`). **Этот долг закрыт швом (S5):**
  `bin/run.mjs` снимает множество run-каталогов проекта ДО `spawn` и после терминального состояния
  берёт разность множеств, а не «самый новый по времени» (`newRunsSince`/`classifyNewRuns` в
  `bin/run.mjs`). Ноль новых прогонов — прежний диагноз preflight, без изменений. Ровно один — он и
  становится результатом. Два и более — раннер печатает диагноз со списком ВСЕХ найденных `runId` и
  их `state` и выходит с кодом `2`, не выбирая ни один из них: молча взять любой — соврать о прогоне.
  Дополнительно запуск `pi -p` теперь идёт с `--tools workflow,read,write` — лаунчер лишён `bash`/
  `edit`/прочего, так что даже повторный вызов не может сделать ничего опаснее второго `workflow`.

- **Модель-лаунчер по-прежнему имеет `write`.** Сузить аллоулист `pi -p` до одного `workflow` нельзя:
  `pi-extensible-workflows` использует активные инструменты корневой сессии как потолок для
  инструментов роли (`rootTools` — `~/.pi/agent/npm/node_modules/pi-extensible-workflows/src/host.ts`,
  роль `gilb` объявляет `tools: [read, write]` — `src/validation.ts`, `validateRolePolicies`), и без
  `read`/`write` в аллоулисте launcher'а сам запуск роли отвергается кодом `UNKNOWN_TOOL` раньше, чем
  успевает дойти до гардрейла. Значит доверие к лаунчеру неполное и не может стать полным этим швом:
  у него по-прежнему есть `write`, которым он может тронуть любой файл в рабочем каталоге (как и было
  в живом прогоне S4). Шов из этого пункта (снимок ДО / разность множеств / отказ на «больше одного»)
  не запрещает лаунчеру записать что-то лишнее — он только не даёт раннеру ВЫДАТЬ результат такой
  записи как честный прогон. Дальнейшее сужение потребовало бы либо карты путей для `write` на уровне
  хоста (которой в pi нет — см. первый пункт долгов выше), либо отдельной непривилегированной сессии
  только для вызова `workflow`.

- **Проектные роли не подхватываются без доверия к проекту** (`PLAN.md` §0, риск 1, подтверждено
  на стенде). `bin/install.mjs` поэтому обязателен, а не удобство; `.pi/pi-extensible-workflows/
  roles/smoker.md` в этом репозитории — не рабочий канал, а зафиксированный пример того самого
  нерабочего пути (используется только пробой `workflows/smoke2.js`).

- Остальные пункты, унаследованные от донора как есть (агрегаторы вместо части фабрик, отсутствие
  машинного признака «стоит, не висит») — см. `standards/code.md` §8.

- **`TASK.md` и `task.md` — один и тот же файл на регистронезависимой ФС** (APFS по умолчанию на
  macOS, аналогично NTFS на Windows). До сдачи S4 в корне репозитория лежал `task.md` (исходная
  постановка задачи переноса, написанная оператором до `PLAN.md`) и отдельно ожидался `TASK.md`
  (живой вход конвейера) — это два РАЗНЫХ пути только на регистрочувствительной ФС (Linux, CI).
  Первый же живой прогон S4, записавший фикстуру в `TASK.md`, молча затёр `task.md` — один и тот же
  инод. Постановка задачи не входила в целевую раскладку `PLAN.md` §3 (там объявлен только
  `TASK.md`), потеря не бьёт по контракту конвейера, но найдена и называется вслух: код, ссылающийся
  на `TASK.md` литералом, не застрахован от коллизии с любым другим файлом того же имени в другом
  регистре, случайно оставленным в корне.
