# solo — планирование и разработка одной командой

Воркфлоу для [pi](https://github.com/earendil-works/pi-coding-agent) на
[pi-extensible-workflows](https://github.com/earendil-works/pi-extensible-workflows):
модель с полным доступом к коду пишет план разработки, конвейер проверяет его судьями
и критиком, оператор утверждает и отвечает на вопросы, разработка идёт по строкам плана.

**Одна команда `/solo` превращает TASK.md в коммиты.**

## Как работает конвейер

```
TASK.md [+ PROMPT.md]                    заказ оператора в корне проекта
  │
  │  /solo  → чат-модель: ОДИН tool call workflow(solo, foreground:false) — кнопка
  ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  PLAN  (шаг 1)                                                              │
│                                                                             │
│  Роль planner (read/bash/write) читает репозиторий сама                     │
│  и пишет PLAN.md по шестираздельной артефакт-спеке:                         │
│    1. ТРЕБОВАНИЯ — цитаты TASK.md → где закрыто                             │
│    2. ИЗМЕНЕНИЯ — файл | Added/Changed | контракт | требование              │
│    3. СЦЕНАРИИ — до → после                                                │
│    4. ВЕЛИЧИНЫ — значение + источник                                       │
│    5. ГАРАНТИИ — что не должно сломаться                                   │
│    6. ОТКРЫТЫЕ ВОПРОСЫ — что решить оператору                              │
│                                                                             │
│  Судья-скрипт проверяет форму: разделы на месте, цитаты — подстроки         │
│  TASK, пути существуют или «новые» с образцом, источники непусты            │
│  Красное → круг починки с FEEDBACK                                          │
└─────────────────────────────┬───────────────────────────────────────────────┘
                              ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  PLAN-CHECK  (шаг 2)                                                        │
│                                                                             │
│  Критик (роль, read) сверяет план с кодом: ≤3 блокера или APPROVE           │
│                                                                             │
│  Открытые вопросы → В ЧАТ (followUp) с рекомендациями                       │
│  Оператор отвечает сообщением → solo_answer → ответы                        │
│  ВПИСЫВАЮТСЯ В ПЛАН («→ РЕШЕНО: …»)                                         │
│                                                                             │
│  Карточка-синтез → в чат: N требований · N строк · N файлов · N вопросов    │
│  Вопрос: «Запускаем execute? да / нет: причина»                             │
└─────────────────────────────┬───────────────────────────────────────────────┘
                              ▼  «да»
┌─────────────────────────────────────────────────────────────────────────────┐
│  EXECUTE  (шаг 3)                                                           │
│                                                                             │
│  «ПРИСТУПАЮ К РАЗРАБОТКЕ ПО ПЛАНУ — N строк Ф»                              │
│                                                                             │
│  Роль dev (read/bash/edit/write) работает по строкам Ф:                     │
│    итерация = строка Ф = коммит                                             │
│    величины — из §4 · гарантии §5 нерушимы · тесты не переписывать          │
│                                                                             │
│  Судьи:                                                                     │
│    (a) каждая строка Ф ↔ коммит                                             │
│    (b) существующие тесты только расширены                                  │
│    (c) гарантии §5 аддитивны                                                │
│                                                                             │
│  Готово → карточка «РАЗРАБОТКА ЗАВЕРШЕНА — N/N/N»                           │
└─────────────────────────────────────────────────────────────────────────────┘
```

## Data flow step by step

| шаг | вход | выход | кто работает |
|---|---|---|---|
| **plan** | TASK.md, PROMPT.md (или дефолтная спека пакета) | `.agent/staging/PLAN~draft.md` → `.agent/PLAN.md` | роль planner + судья-скрипт |
| **plan-check · critic** | `.agent/PLAN.md` | конверт APPROVE/REJECT + blockers + questions | роль critic |
| **plan-check · questions** | вопросы раздела 6 плана | `.agent/pending.json` → чат → `.agent/answers.md` → «→ РЕШЕНО» в плане | ask-рельса + solo_answer |
| **plan-check · confirm** | план с решениями | карточка + «да/нет» от оператора | card.ts + ask |
| **execute** | `.agent/PLAN.md` (с «→ РЕШЕНО») | коммиты в git проекта | роль dev + судьи a/b/c |

## Остановка и возобновление

Полоса пишет маркер `.agent/progress.json` на **каждом переходе фазы**:

```json
{ "phase": "questions", "round": 1, "reachedAt": "2026-08-27T20:52:00Z" }
```

Прогон упал или остановлен → перезапуск `/solo` читает маркер и **продолжает
с той же фазы**, а не с нуля:

| маркер | что делает новый `/solo` |
|---|---|
| нет `.agent/` | fresh — с начала |
| `phase: "plan"` | круг починки: свой черновик как PREVIOUS |
| `phase: "critic"` | критик смотрит готовый план |
| `phase: "questions"` | ответы полны и не вписаны → применить → confirm |
| `phase: "confirm"` | карточка + вопрос «да/нет» |
| `phase: "execute"` | судьи проверяют коммиты от `solveStart`-HEAD |
| `phase: "done"` | итоговая карточка |

Существование файла ≠ фаза принята: маркер — единственный источник истины.

## Установка

### Один раз на машину

```bash
git clone <этот-репозиторий> && cd solo
cd ext && npm install && cd ..
pi install ./ext
```

### В проекте оператора

Ничего не устанавливается. В корне проекта — только:

```
TASK.md          заказ (обязательно)
PROMPT.md        артефакт-спека (опционально; нет — дефолтная из пакета)
.agent/          рантайм-состояние (создаётся полосой)
```

Харнесс-файлов в проекте — **ноль**.

### Запуск

```bash
cd <каталог-проекта>
pi          # сессия pi в каталоге проекта
/solo       # запустить воркфлоу
```

Полоса идёт в фоне: чат-модель делает один tool call и дальше участвует только
как реле — передаёт ваши ответы на вопросы через `solo_answer`.

### Проверка кода

```bash
node --test   # в корне репозитория solo
```

## Метрики из живого прогона

| | solo | pi напрямую | izi (конвейер) |
|---|---|---|---|
| вызовов LLM | **4** | 7 | 15 |
| время | **~21 мин** | 3,5 мин | ~18 мин |
| план: 6 разделов | ✓ (судья + критик) | ✓ | ✓ |
| вопросы оператору | 5 (вписаны в план) | 6 (не вписаны) | 0 |
| Ф↔коммит 1:1 | ✓ (судья a) | ✓ | ✓ |
| тесты зелёные | 7/7 | 9/9 | 9/9 |
| гардрейлы | судьи + критик | нет | полный конвейер |
| харнесс в проекте | **0** | 0 | 0 |
| resume | ✓ | нет | ✓ |

## Структура репозитория

```
ext/                    пакет расширения pi (TypeScript, грузится через jiti)
  index.ts              регистрация: хост-функции + solo_answer + роли
  engine.ts             станционный движок (плоский автомат фаз)
  ask.ts                вопрос оператору в чат + файловый фолбэк
  answer-tool.ts        инструмент solo_answer (TypeBox-схема)
  answers.ts            exchange-грамматика ответов
  prompts/solo.md       команда /solo (inline JS-скрипт полосы)
  spec/PROMPT.default   дефолтная шестираздельная спека
steps/
  plan/                 шаг 1: роль planner + судья формы
  plan-check/           шаг 2: критик + вопросы + карточка + подтверждение
  execute/              шаг 3: роль dev + судьи a/b/c + итоговая карточка
standards/              стандарты кода и воркфлоу
tests/                  отчёты живых прогонов
```
