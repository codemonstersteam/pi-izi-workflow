# Маленькая задача: один вызов intake вместо шести пластов

## Data-flow: где укороченный трек встраивается в конвейер

Конвейер один и тот же — `task → brd → survey-plan → scope → graph → intake → weight → ripple →
design → plan`. Укорочение живёт ТОЛЬКО ВНУТРИ шага 6: до него и после него ни один шаг не
отличает маленькую задачу от большой. Развилка — первый ход intake, точка слияния — продвижение
`.agent/frd.xml`; потребители дальше (weight, ripple, plan) не знают, каким путём файл собран.

```
ШАГИ 1–5 — БЕЗ ИЗМЕНЕНИЙ, для любой задачи
  task      TASK.md ────────────────────► key (скрипт, 0 токенов)
  brd       TASK.md ──► normalized.md ──► brd.md + anchors.json      (3 вызова LLM)
  scope     brd.md  ──► focus.json ──► части (part~*.xml)           (рой, 3 scout)
  graph     части ──► appgraph.xml + graph-computed.xml              (скрипт, 0 токенов)
                        │
                        ▼
╔══ ШАГ 6 intake: РАЗВИЛКА (новое — точка входа, intake.step.mjs::next, первый ход) ══╗
║                                                                                     ║
║  скрипт small.isSmall (0 токенов, читает диск):                                     ║
║    java-файлы ≤ 12  И  строк-требований в normalized.md ≤ 5 ?                        ║
║                                                                                     ║
║  НЕТ (eddi: 1854 файла)                ДА (quarkus: 9 файлов, 3 строки)             ║
║    │                                     │                                          ║
║    ▼ ПОЛНЫЙ ПУТЬ (как сегодня)          ▼ УКОРОЧЕННЫЙ ТРЕК (T76)                     ║
║    6 пластов, 6 нарядов, 6 кругов:      ОДИН наряд order-one.tpl:                    ║
║      scenarios → owners →               все шесть решений в одном вызове             ║
║      contracts → data-failures →        (UC, владельцы, дельты, величины,            ║
║      coverage → critic                    carried+RTM-черновик, самокритика)         ║
║      staging/frd~<пласт>.xml ×6         staging/frd~one.xml                          ║
║    суд ПОСЛЕ каждого пласта             суд ПОСЛЕ единственного вызова:              ║
║      (judgePass, по правилам пласта)      ПОЛНЫЙ двор одним прогоном                 ║
║                                           (checkFrd все F-правила + rtmJudge)        ║
║                                                                                     ║
║  ОБА ПУТИ СХОДЯТСЯ В ОДНОЙ ТОЧКЕ СУДА:                                               ║
║    ЗЕЛЁНЫЙ ──► promote ──► .agent/frd.xml  (тот же route.mjs, тот же файл)           ║
║    <question> в артефакте ──► та же ask-рельса (T64): пауза → answers.md → круг 2     ║
║    КРАСНЫЙ:                                                                           ║
║      полный путь ──► круг починки СВОЕГО пласта (как сегодня, +T70 маршрутизация)     ║
║      укороченный ──► ПАДЕНИЕ НА ПОЛНЫЙ ПУТЬ: блокеры разносятся по RULE_PASS          ║
║                       (F3c→contracts, F17a→owners, rtm:→owners…) и дальше            ║
║                       механизм 6 пластов чинит по одному, как сегодня                 ║
╚═══════════════════════════════════════════════════════════════════════════════════╝
                        │
                        ▼
ШАГИ 7–10 — БЕЗ ИЗМЕНЕНИЙ: weight → ripple → design → plan читают .agent/frd.xml,
  не зная и не проверяя, каким путём он собран.
```

Три свойства этой схемы — строительные, их нельзя нарушать:

1. **Развилка внутри шага, не в цепочке.** Голова полосы (`workflows/izi.js`) не меняется
   вовсе: у неё один шаг `intake`; маленькость — решение ГОЛОВЫ ШАГА на первом `next()`.
2. **Слияние — файл и суд.** Итоговый артефакт и его проверки одинаковы на обоих путях:
   «один вызов» экономит вызовы модели, но НЕ проверки — судится полный двор F-правил
   и двусторонняя RTM-матрица.
3. **Быстрый путь не прячет дефект.** Любой красный блокер укороченного трека уезжает в
   полный путь с именем своего пласта (словарь правило→пласт уже существует — RULE_PASS,
   им же работает маршрутизация T70). Починка идёт штатными кругами, budgets те же.

Замер-повод: живой прогон `quarkus-rest-json-app-v2-t1-3` (FRUIT-1, 26.08.2026). Полный отчёт —
`component-tests/quarkus-rest-json-app-v2-t1-3-test.md`,(data-flow-таблица с метрами каждого шага).

## Замер: что заплатили за тривиальную задачу

| | quarkus FRUIT-1 | eddi DOS-535 (для сравнения) |
|---|---|---|
| заказ | 3 строки, 3 требования | 16 строк, 16 требований |
| репозиторий | 9 java-файлов | 1 854 файла |
| итоговый артефакт frd.xml | 2,3 КБ, 1 use case, 1 дельта | 17,4 КБ, 10 use case, 13 дельт |
| вызовов LLM до frd.xml | **15** | ~14 |
| биллинговых токенов | **~203k** (in 153k · out 50k; cached 701k) | ~230k |
| чистое время агентов | **~45 мин** (22 мин без сетевой аномалии) | ~50 мин |

Вывод из замера: **стоимость конвейера не зависит от размера задачи.** Множитель — не заказ, а
арматура: 6 пластов intake, каждый несёт весь накопительный артефакт и форму роли (701k cached —
повторы формы), + brd (3 вызова) + рой scope (3 scout) + вопрос/починка/критик. На eddi эта цена
окупается детерминизмом (суд поймал 4 корня, RTM-суд направлял починки). На задаче в один endpoint
плата та же, а выигрывать нечего.

## Идея (T76): маршрут «маленькая задача» — intake ОДНИМ вызовом, суд ТОТ ЖЕ

### Порог срабатывания (решает скрипт, не модель)

Оба условия считаются с диска за 0 токенов ДО первого наряда intake:

- `repoJavaFiles <= 12` — файлы кода под границей survey-plan (quarkus: 9; eddi: 1854 — порог
  отсекает его с запасом ×150);
- `requirements <= 5` — строки normalized.md (quarkus: 3; eddi: 16).

Пороги НЕ настраиваются конфигом: две константы в коде, калиброванные двумя эталонами
(quarkus-лёгкий / eddi-тяжёлый), как `anchorMaxFiles` в шаге 2. Новорождённое правило без
эталона — invented-default.

### Data-flow: как это работает

```
normalized.md + дерево файлов
  │  скрипт: java-файлы ≤ 12 И строк-требований ≤ 5?
  ├─ НЕТ → полный путь: 6 пластов, как сегодня (ничего не меняется)
  ▼ ДА
order-one.tpl — ОДИН наряд: все шесть решений сразу
  │   use cases (по R) → владельцы (по карте/кандидатам b0) → дельты-формы →
  │   величины/отказы → carried + черновик RTM → самокритика в одном конверте
  │   споры шагов и пробелы — <question> В АРТЕФАКТЕ, как сегодня (T64 → пауза)
  ▼
staging/frd~one.xml
  │  суд: ПОЛНЫЙ двор одним прогоном — checkFrd (все F-правила, forPass = все пласты
  │  сразу) + rtmJudge (двусторонняя матрица, собранная из артефакта тем же скриптом)
  ├─ ЗЕЛЁНЫЙ → promote frd.xml (тот же route.mjs)
  ├─ вопрос в артефакте → та же ask-рельса (T64), ответы уезжают {ANSWERED}, круг 2
  └─ КРАСНЫЙ → ПАДЕНИЕ НА ПОЛНЫЙ ПУТЬ с FEEDBACK в первый красный пласт
      (RULE_PASS уже знает, какому пласту принадлежит каждый блокер — этот словарь
       уже существует и обслуживает маршрутизацию T70)
```

**Инвариант, который нельзя нарушить: гардрейл решает, не роль.** Один вызов — это не «модель
сертифицирует себя»: судится тот же полный двор F-правил + RTM, что и сегодня; меняется только
число ВЫЗОВОВ, не число ПРОВЕРОК. Красный = падение на полный путь, где каждый пласт получит
свой круг починки, — быстрый путь не имеет права оставить дефект.

### Что это даёт (прогноз по замеру quarkus)

- 6 вызовов intake → 1–2 (один круг + возможный круг вопросов): −9k in / −5k out на артефакт
  и −5 × кэш-повторов формы;
- слоёв-копий нет: модель пишет только СВОЙ текст, а не переписывает пять принятых слоёв
  (замер субагента: вывод — главное узкое место, T72 об этом же);
- время intake ~22 мин → ~4–6 мин (один длинный вызов + суд 0 с);
- brd и scope на маленькой задаче уже дёшевы (3+3 вызова, но наряды маленькие) — их не трогаем.

### Правки

| где | что |
|---|---|
| `steps/intake/small.mjs` (новый) | `isSmall({ javaFiles, reqRows })` — порог; `PASSES_ONE = ["one"]` |
| `steps/intake/order-one.tpl` (новый) | один наряд: шесть решений, слоты те же данные ({CANDIDATES}, {BLUEPRINT}, {OWED}…), форма артефакта — та же грамматика frd |
| `steps/intake/judge.mjs` | режим `pass="one"`: `forPass` не фильтрует (все правила), rtm-суд подключён |
| `steps/intake/intake.step.mjs` | порог на старте; красный `one` → маршрутизация блокеров по RULE_PASS на полные пласты (обобщение T70) |
| `steps/intake/frd.mjs` | RULE_PASS уже несёт соответствие правило→пласт — переиспользуется без правок |

### Seam (принимается пере-внедрением дефекта)

1. Компонентный: маленькая форма (9 файлов, 3 R) → наряд ОДИН, зелёный артефакт → promote без
   шести staging-файлов.
2. Компонентный: тот же наряд, артефакт с F3c+F17a → блокеры уезжают на contracts/owners
   соответственно (не на «one»), полный путь подхватывает.
3. Компонентный: eddi-форма (1854 файлов) → `isSmall` = false, порядок пластов прежний.
4. Живой: quarkus-форма начисто → frd.xml байт-эквивалентен по суду (не по тексту), токены
   и время падают кратно; расхождение с прогоном 26.08 разбирается с оператором.

### Этапы

1. Порог + наряд + суд `one` + падение на полный путь (юниты + компонентные 1–3).
2. Живой прогон quarkus начисто, сверка метров с замером 26.08 (цель: ≤1/3 токенов intake).
3. Толь­ко после двух зелёных живых прогонов — подумать о low thinking для простых пластов
   полного пути (отдельное решение, отдельный замер).

## Что НЕ делаем

- НЕ урезаем суд: один вызов — не послабление проверок; любой красный уходит в полный путь.
- НЕ заводим вторую грамматику артефакта: frd.xml тот же, потребители (weight/ripple/plan)
  не должны знать, каким путём он собран.
- НЕ трогаем brd/scope: их цена на маленькой задаче уже мала, а срезка роёв ломает
  доказанную механику фокуса.
- НЕ делаем порог конфигом: две эталонные задачи — два конца шкалы, промежуточные значения
  нечем измерять.
